# 0단계. 기획서 정밀 분석

> 대상: `planning/service-plan-v2.4.md`(서비스 기획서 v2.4), `planning/tech-plan-v0.5.md`(기술 기획서 v0.5)
> 분석일: 2026-10-04

## 1. 한 줄 요약

현장직 팀장(회사당 1명)이 프로젝트(현장)별 **투입 인원·공수·작업일지·자재·사진·자료**를 수첩처럼 기록하는 **멀티 회사(테넌트) 웹앱**.
돈(금액·급여)은 다루지 않고, 직원은 로그인하지 않는다. 회사 간 데이터 격리가 최우선 요구사항이다.

## 2. 두 문서의 역할

| 문서               | 역할                                           | 이 프로젝트에서의 위치 |
| ------------------ | ---------------------------------------------- | ---------------------- |
| 서비스 기획서 v2.4 | 무엇을 만드는가 (기능·업무 규칙·정책)          | 기능 요구사항의 기준   |
| 기술 기획서 v0.5   | 무엇으로·어떻게 만드는가 (스택·구조·격리 구현) | 구현 방식의 기준       |

충돌 시 기능은 서비스 기획서, 구현은 기술 기획서를 따른다.

## 4. 도메인 모델 (서비스 기획서에서 추출한 엔티티)

```
Company ──1:1── AdminAccount ── Session/Device, EmailVerification, ConsentLog
   │
   ├─ Settings(기준시간·월 기준일수·공수 방식·경고 기준·표시 이름)
   ├─ Master 목록: 직종, 작업 구분, 공종, 자재 분류, 자격 종류, 직원 구분
   ├─ Partner(고객·협력업체·공급처)
   ├─ Employee ── EmployeeDocument(자격·서류, 만료일)
   ├─ Project(코드·상태·기간·보증) ── StatusHistory, PeriodHistory, ProgressHistory
   │    ├─ Assignment(투입: 직원 × 기간 × 계획 공수)
   │    ├─ WorkLog(프로젝트 × 일자) ── WorkLogEntry(직원별 공수·작업 구분) ── 자재 기록, 사진
   │    ├─ MaterialRecord(반입/사용/반출/폐기) ── Material(목록)
   │    ├─ Photo, Document(버전), Memo, ChangeRequest(변경·추가 작업), RepairRequest(보수)
   │    └─ MonthLock(월 공수 확정)
   ├─ Inbox(메모함: 프로젝트 미지정 메모·사진)
   ├─ Notification, AuditLog(회사/운영자 분리)
   └─ 파일 객체(S3): company/{id}/project/{id}/…
```

상세 테이블 설계는 별도 문서(기술 §17 "데이터 모델 기획")에서 단계별로 진행한다.

## 8. 최대 위험 3가지와 선제 대응

1. **Prisma 7 + RLS**: Prisma가 RLS·`SET LOCAL`을 지원하지 않아 직접 SQL과 `withCompany` 헬퍼로 보완해야 한다.
   → 기술 0단계에서 **스파이크로 먼저 검증**하고, 두 회사 격리 테스트를 통과해야 다음 단계로 간다.
2. **현장 입력 부담(3분 목표)**: 서비스가 쓰이지 않으면 데이터가 비어 의미가 없다.
   → 일지 일괄 입력과 업로드 대기열을 2단계에서 **실측**하고, 실사용 시험에서 검증한다.
3. **1인 개발 범위 팽창**: 기능이 많다.
   → 서비스 §16 단계를 넘는 기능은 실사용 이후로 미루고, 단계마다 완료 기준을 테스트로 고정한다.
