## 1.0.1 패치

### 1. pnpm 점검 경고 정리

**증상**: 서버에서 `docker compose run --rm ops pnpm operator …`를 실행하면 명령은 정상 동작하지만 아래 경고가 출력된다.

```text
Error: ERR_PNPM_PACKAGE_MANAGER_REMOVE_MODULES_DIR
  × installing dependencies
  ╰─▶ Failed to remove /app/node_modules/eslint from the modules directory: Permission denied (os error 13)
[WARN] The install that runs before scripts failed, so your node_modules may be out of sync with your lockfile.
```

**원인**

- 이 프로젝트가 쓰는 pnpm은 11 이상이라 `npm_config_*` 환경 변수를 더 이상 읽지 않는다. `docker-compose.yml`의 `ops`·`migrate`에 넣어 둔 `npm_config_verify_deps_before_run: 'false'`가 무시된다
- 그래서 pnpm이 명령 전에 "의존성이 최신인지 점검해 필요하면 설치"하는 기본 동작(`verifyDepsBeforeRun: install`)을 한다
- 컨테이너 안 `node_modules`를 일반 사용자(`node`)가 지울 수 없어 그 설치가 실패하고, pnpm은 "설치가 실패해도 명령은 그대로 실행"하도록 만들어져 있다. 그래서 오류처럼 보이지만 실제 작업(회사 생성, 백업, 마이그레이션)은 정상이다

**영향**: 서비스·데이터에는 영향이 없다. 출력이 어지럽고, 점검 때마다 몇 초를 낭비하며, 설치가 일부 성공하면 `node_modules`가 반쯤 바뀔 위험이 이론상 있다. 현재는 서버 단축어(`fn-ops`)가 이 경고 줄을 숨긴다

**해결**: `docker-compose.yml`의 `ops`·`migrate`에서 변수 이름을 `PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN: 'false'`로 바꾼다 (pnpm 문서: `pnpm_config_*` 접두사, 값 `false`는 점검을 끔)

**확인**: 서버에서 `fn-ops pnpm operator list`와 `deploy.sh`의 마이그레이션 단계에 위 경고가 나오지 않는다. `deployScripts.test.ts`에 compose 변수 이름 시험을 더한다. 경고가 사라지면 `deploy/server-aliases.sh`의 숨김 필터는 남겨 두어도 무해하다

### 2. DB 직접 보기 경로 정리

**현재**: DB 컨테이너는 외부 포트를 열지 않는다. WebStorm 같은 DB 도구로 보려면 SSH 터널로 컨테이너 내부 주소(`172.x.x.x`)에 접속해야 하는데, 컨테이너를 다시 만들면 주소가 바뀌어 불편하다. 접속 계정은 모든 회사를 우회해서 볼 수 있는 소유 계정뿐이다

**계획**

- `docker-compose.yml`의 `db`에 `127.0.0.1:5432:5432`만 열어 서버 안에서만 접근되게 하고(외부 비공개 유지), 터널 대상을 `localhost:5432`로 고정한다. `server-check.sh`의 "DB 포트가 바깥에 열려 있지 않음" 검사는 `127.0.0.1` 바인딩을 허용하도록 조정한다
- 조회 전용 DB 계정 `field_note_readonly`를 새 마이그레이션으로 추가했다: 앱 계정과 같은 회사 격리(RLS)에서 SELECT만 가능하고 회사는 `set_config('app.company_id', …)`로 지정한다. 세션·비밀번호 해시·2단계 인증 키 테이블은 접근할 수 없다. 운영자도 업무 데이터를 열람하지 않는다는 기존 원칙에 맞춰 전체 읽기가 아닌 회사 지정 방식으로 정했다
- `docs/07-feature-reference.md`의 "서버 운영"에 WebStorm 접속 방법을 더한다

**주의**: 새 계정을 만들면 격리 시험 목록(운영자·로그인 전용·작업 큐 계정과 같은 방식)에 등록해야 하고, 회사 간 격리(RLS)를 적용할지 전체 읽기로 둘지 먼저 정한다

### 3. 회사 즉시 삭제 운영자 명령

**현재**: 해지는 14일 유예 뒤 `purge-due`가 지운다. 시험 계정처럼 바로 지워야 할 때는 소유 계정으로 SQL을 직접 실행한다 (`company_id`가 있는 모든 테이블에서 지우고 회사 행을 지우는 한 트랜잭션, 먼저 `ROLLBACK`으로 시험)

**계획**: `pnpm operator delete-company --company-id <ID> --confirm-name "회사 이름"`을 만든다

- 회사 이름이 일치할 때만 실행, 지우기 전 테이블별 행 수를 보여 주고 `--dry-run`을 지원
- 업무 데이터 삭제와 함께 객체 저장소의 `company/<회사 ID>/` 파일도 지운다 (`demo-reset`의 파일 삭제 로직 재사용)
- 회사 행이 지워져 `operator_actions`에는 남길 수 없으므로(외래 키) 실행 기록을 화면에 출력한다. 시연 회사는 대상에서 제외한다
- 이 일은 소유 계정이 필요해서 운영자 계정이 아닌 별도 권한 설계가 필요하다 (`demo-reset`처럼 소유 계정 연결 사용)

### 4. 공개 시연 샘플 날짜를 오늘 기준으로 맞추기

**현재**: 샘플 날짜가 2026년 6~11월로 고정이라 시간이 지나면 "이번 달" 화면이 비어 보인다

**계획**: `demo-reset`이 샘플의 모든 날짜를 기준일(예: 가장 최근 일지)에서 오늘로 평행이동해 넣는다. 매일 새벽 초기화가 돌 때마다 오늘 기준으로 갱신된다. 보증·만료 알림 같은 날짜 계산이 어긋나지 않는지 시험으로 확인한다

## 1.1.0 기능: 업로드를 임시 보관 후 폼 저장 때 확정 (중요)

**현재**

- 문서 올리기·직원 서류 폼은 파일을 선택 상태로만 두었다가 **폼의 저장 버튼**을 누를 때 업로드한다
- 작업일지의 사진 단계와 변경·추가 작업의 증빙은 파일을 고르는 **즉시 업로드**한다 (현장에서 연결이 끊겨도 사진이 유실되지 않게 하려는 설계)
- 객체 키는 처음부터 최종 경로(`company/{회사}/project|employee/{ID}/{파일ID}/original|thumbnail`)이고, 확정 여부는 DB 상태(`PENDING`·`READY`·`REJECTED`)로 구분한다

**목표**: 파일을 올리면 **임시 상태**로 두고, 폼을 최종 저장해야 확정한다. 확정하지 않은 파일은 **24시간 뒤 자동 삭제**한다. 앱이 닫히거나 새로고침해도 올라간 파일을 다시 쓸 수 있고, 취소한 파일은 남지 않는다

**설계 방향**

- 폴더를 옮기지 않고 **DB 상태**로 구분한다: 올라왔고 검사도 통과했지만 어디에도 연결되지 않은 `STAGED` 상태를 두고, 폼 저장 때 프로젝트·일지에 연결하면 `READY`로 바꾼다. 이동 중 실패로 중복·유실이 생기지 않는다
- 24시간 만료 정리는 `maintenance.ts`의 방치된 `PENDING` 정리와 같은 방식으로 더한다 (R2 수명 규칙은 최소 1일이라 같은 기준의 안전망으로 쓸 수 있다)
- 연결이 끊긴 동안의 보관은 서버가 아니라 **기기의 업로드 대기열**(`photoUploadQueue`)이 맡는다. 서버 임시 보관은 "이미 올라갔는데 폼 저장 전에 이탈한 경우"를 해결한다
- 폼이 임시 파일 ID를 초안(IndexedDB)에 함께 기억해 다시 열었을 때 이어서 저장할 수 있게 한다
- 대상 화면: 작업일지 사진 단계, 변경·추가 작업 증빙, 문서 올리기, 직원 서류 (동작을 하나로 통일)

**정한 것**

1. 임시 파일의 용량은 회사 저장 한도에 포함한다. 막힐 때 사용자에게는 명확한 문구, 개발자에게는 로그만 남긴다
2. 임시 파일(사진)은 미리보기를 허용한다
3. 폼 취소·뒤로가기·화면 이동처럼 의도한 이탈은 확인 창 뒤 즉시 삭제한다. 새로고침·비정상 종료는 지우지 않아 이어서 작성할 수 있다. 삭제가 실패하면 24시간 만료가 정리한다
4. 만료는 기기에서 업로드 시각으로 계산한다 (`visibilitychange` 때 비교, 주기 확인·서버 상시 확인 없음). 저장할 때 서버가 최종 판정해 `409 STAGED_FILE_EXPIRED`를 돌려주면 화면이 해당 사진으로 스크롤해 그 파일만 다시 올리게 하고 나머지 입력은 유지한다

**진행**: API(`feat-upload-staging-api`)와 웹의 공용 뼈대(`apps/web/src/staging/`: 임시 파일 목록·초안 복구·만료 계산·이탈 확인·삭제)를 문서함(새 문서·새 버전)과 직원 서류(등록·수정)에 적용했고 저장 현황의 임시 파일 줄도 넣었다. 변경·추가 작업 증빙과 작업일지 사진 단계는 고르는 즉시 등록하는 동작(저장 버튼 없음)이라 임시 보관 화면을 따로 두지 않고, 등록 실패·취소 때 올려 둔 파일을 바로 지운다

## 1.1.0 기능: Swagger 정비와 API 문서

**현재**: `swagger-ui-express`가 `/api/docs`에 이미 붙어 있지만 `NODE_ENV=development`일 때만 켜진다(`apps/api/src/main.ts`). 문서의 원본은 라우트 정의에서 생성되는 `packages/shared/openapi/openapi.json`이다. 사용법을 적은 문서는 없다

**계획**

- 각 엔드포인트의 설명·요청 예시·오류 응답·인증 필요 여부를 Swagger에서 읽을 수 있게 보강한다 (태그별 묶음, 필드 설명, 예시 값)
- 로그인 쿠키·멱등 키·Origin 검증처럼 호출에 필요한 조건을 Swagger 상단 설명에 적는다

- **별도 문서 `docs/13-api-docs.md`**: 문서가 만들어지는 과정(라우트 정의 → zod-to-openapi → `openapi.json` → 프론트 타입), Swagger 여는 법, 새 엔드포인트에 설명을 다는 규칙, `openapi:generate`·`openapi:check` 사용법, 어떤 변경에서 테스트가 실패하는지

## 1.1.0 도구: Postman 컬렉션 (로컬·운영 구분)

**요구**: 내 Postman 계정의 **Personal 작업 공간에만** 만들고 공유하지 않는다. 로컬용과 상용 서버용을 구분하고, 입력해야 할 값과 필요한 조건을 각 요청의 설명에 적는다

**설계 방향**

- 컬렉션 원본은 `openapi.json`에서 만든다 (손으로 따로 관리하지 않음). 요청 설명은 Swagger 설명을 그대로 가져온다
- 컬렉션은 하나, 환경(Environment)은 둘: `field-note-local`(`http://localhost:3000`), `field-note-prod`(`https://<SITE_ADDRESS>`). 로그인 아이디·비밀번호는 환경의 **secret 변수**로 두고 값은 저장소·채팅에 남기지 않는다
- 로그인 응답 쿠키를 이후 요청이 쓰도록 하고, 변경 요청에 필요한 헤더(Origin·멱등 키)는 사전 요청 스크립트로 채운다
- 운영 환경에서 데이터를 바꾸거나 지우는 요청은 설명 첫 줄에 경고를 둔다
- 연결은 **Postman MCP**로 정했다 (`.mcp.json`에 추가, 버전 고정). Postman API 키는 사용자가 Postman에서 발급해 본인 PC 환경 변수에만 설정하고 저장소·채팅에 남기지 않는다
- 만들기 전에 Postman MCP 도구가 세션에 연결됐는지, 대상이 **Personal 작업 공간**인지 확인한다 (팀·공개 작업 공간에는 만들지 않는다)
- 가이드는 `docs/13-api-docs.md`에 함께 적는다: MCP 등록과 키 설정, 컬렉션·환경 가져오기와 갱신, 로컬/운영 전환, 로그인 후 호출 순서, 입력 값 설명

## 1.1.0 도구: API 문서를 열어 보는 방법

- **로컬 데이터용**: `pnpm dev` 후 `http://localhost:5173/api/docs` (또는 api 직접 `http://localhost:3000/api/docs`). 로컬 DB 시드 데이터에 대해 "Try it out"까지 동작한다
- **운영 서버 API 확인**: 운영 서버는 `/api/docs`를 열지 않는다. 로컬 Swagger의 서버 선택(Servers)에 운영 주소를 더하는 방법은 쿠키·Origin 검증 때문에 호출이 막히므로 쓰지 않고, 호출 시험은 Postman 운영 환경으로 한다. 문서 읽기만 필요하면 로컬 Swagger가 같은 `openapi.json`을 보여 준다
- 서버 없이 보는 법: `packages/shared/openapi/openapi.json`을 Swagger Editor 등에 붙여 넣는다 (구성은 `docs/13-api-docs.md`)

## 1.2.0 리팩토링과 문서 정리

> 목적은 **코드 안정화와 현재 상태의 완성도 향상**이다. 디자인 리뉴얼·화면 보강은 이 계획에 넣지 않고 시기도 정하지 않는다. 동작은 바꾸지 않는다 (기능 추가 없음)

**1. 구조 점검과 단순화**

- `apps/api/src`는 기능별 폴더가 약 45개이고 `apps/web/src`도 기능별로 나뉘어 있다. 파일이 한두 개뿐인 폴더, 역할이 겹치는 폴더, 지나치게 잘게 쪼갠 모듈을 찾아 합치거나 옮긴다 (후보: `ops`·`operator`·`maintenance`·`repair`, `file`·`photo`·`storage`의 경계)
- `packages/shared`로 올릴 규칙과 서버 전용 코드를 다시 가른다. 서버와 목업이 함께 쓰는 순수 함수 원칙은 유지한다
- 영역별 PR로 나누고 각 PR에서 `typecheck·lint·test·build`와 격리 시험을 통과시킨다. 이동에 따른 import 경로 변경 외에 로직은 건드리지 않는다

**2. 컨벤션 점검**

- `pnpm check:comments --all`로 서술형·마침표 주석과 출처 안내(`§`, 문서 번호)를 전수 점검해 고친다
- 인라인 한글 오류 문구가 `errorMessages.ts` 밖에 남았는지, jbeat-conventions 이름 규칙을 어긴 곳이 없는지 확인한다
- 쓰이지 않는 export·파일·의존성을 정적 도구로 찾고 사람이 확인한 뒤 제거한다

**3. 문서 정리**

- 저장소에 **커밋된** 문서 중 쓰임이 끝난 것을 가려 지운다. 후보: 완료된 리뉴얼 계획(`08-renewal-plan.md`, `09-renewal-plan-3.md`, `05-ui-ux-renewal.md`, `06-field-ux.md`), 번호가 겹친 `05-*`, 초기 `00-analysis.md`. 지우기 전에 `03-progress.md`나 `07-feature-reference.md`로 살릴 내용이 있는지 확인하고 다른 문서·코드의 링크를 함께 고친다
- `.gitignore`로 제외된 개인 메모(`DEPLOY-*.md` 등)는 정리 대상이 아니다
- `docs/03-progress.md`(1,000줄 이상)는 줄이는 방법을 정한다 (버전별 요약만 남기고 상세는 git 기록에 맡김)

**4. README에 폴더 구조 안내**

- 최상위와 `apps/*`·`packages/*`·`deploy`·`docs` 트리를 보여 주고 폴더마다 한 줄 주석으로 역할을 적는다
- 구조를 바꾼 뒤 마지막 단계에서 쓴다 (리팩토링 결과와 어긋나지 않게)

## 후속 (코드 변경 없이 확인할 일)

- **법률 검토**: 수탁·위탁·국외 이전 표기가 법령 요구를 충족하는지, 요청 처리 기한(10일)이 맞는지 전문가 확인. 이 항목이 풀리면 문서 상단의 초안 안내를 없애고 약관 판을 올린다
- **접속 기록 보관 기간**: 법령상 보관 의무가 있는 경우의 기간과 방법 확정
- **소셜 로그인**: 카카오·네이버·구글 앱 등록 뒤 서버 `deploy/.env`에 키를 넣는다 (`docs/07-feature-reference.md`의 "소셜 로그인")
- **자동 배포 여부**: 지금은 서버에서 `deploy.sh <태그>`를 직접 실행한다. 자동화하려면 서버 접속 키를 GitHub에 맡기는 위험이 생기므로 필요가 생길 때 판단한다
- **백업 암호화 키 보관**: `BACKUP_ENCRYPTION_KEY`·`TOTP_ENCRYPTION_KEY`를 서버 밖에 보관했는지 정기적으로 확인한다
