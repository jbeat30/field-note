# UI/UX 개선 분석, 기획 (0.8.0)

> 작성: 2026-10-13, 범위: 0.8.0 UI/UX 리뉴얼 U-8 이후, 진행 상태는 `03-progress.md`

U-1~U-7로 디자인 토큰, 공통 컴포넌트, 카드 구조를 깔았지만, 실제로 써 보니 **화면 구조(정보 구조, 배치, 상세 화면의 디테일)** 가 아직 부족하다는 피드백이 있었다. 이 문서는 전체 화면을 점검한 결과와 개선 설계, 작업 순서를 정한다.

## 1. 점검 방법

- 목업 모드로 로그인한 뒤 앱 화면 25개(홈, 프로젝트 목록/카드/등록, 메모, 일보, 문서, 자재, 변경, 보수, 보증, 요약, 사진, 월 공수, 검색, 메모함, 일지, 직원 목록/카드, 인력 배치, 명부 목록/카드, 알림 설정, 기록 조회, 목록 관리)를 데스크톱(1440px), 모바일(390px)로 캡처해 눈으로 확인했다
- 기준: ① 한눈에 파악되는가 ② 다음 행동이 어디 있는지 보이는가 ③ 같은 일을 같은 모양으로 하는가 ④ 현장(모바일, 한 손)에서 쓸 수 있는가

## 4. 설계 기준 (패턴)

- **하위 화면 머리**: `BackLink`(제목 위) → `PageHeader`(제목, 설명, 주 버튼). 다른 이동 링크는 헤더 오른쪽 버튼 또는 탭으로
- **기간 이동**(`PeriodNav`): `[‹] [기간 표시, 눌러서 달력] [›]  [오늘]`. 버튼은 44px 아이콘 버튼
- **날짜 입력**(`DateInput`): 직접 입력(`YYYY-MM-DD`)과 달력 선택 둘 다 가능, `min`, `max` 반영, 값 형식은 기존과 같아 폼 코드는 바꾸지 않는다
- **행(Row) 패턴**: 왼쪽 = 이름, 보조 정보, 상태 배지, 오른쪽 = 아이콘 동작 1~3개. 텍스트 버튼은 "추가, 저장" 같은 주 동작에만
- **수치 카드**: 큰 숫자 + 작은 라벨 + 필요하면 변화, 경고 배지
- **긴 화면 분할**: 5개 이상 구역이 이어지면 탭 또는 2열. 선택한 탭은 주소 `?tab=`에 둔다
- 접근성: 아이콘 버튼은 `aria-label`, 터치 영역 44px, 색만으로 상태를 전하지 않는다. 스토리 접근성 검사(`pnpm test:stories`)가 기준

## 8. 목록 조회 방식 (서버 쪽 나누기, 정렬)

데이터가 많아져도 목록이 느려지지 않도록 프로젝트 목록부터 서버 방식으로 바꿨다. 다른 목록(직원, 명부, 기록)도 같은 방식으로 옮길 수 있다.

- **API** `GET /projects`: `page`(1~), `pageSize`(기본 20, 최대 100), `sortBy`(recent, name, status, client, manager, plannedStart, plannedEnd), `sortDir`(asc, desc)를 받고 `{ items, total, page, pageSize }`를 돌려준다. 같은 값끼리는 최근 등록순(등록 순서 = 코드 번호 순서)으로 이어 붙여 쪽을 넘겨도 순서가 흔들리지 않는다
- **표** `DataTable`(TanStack Table, `manualSorting`, `manualPagination`): 표는 정렬, 쪽 상태만 들고, 바뀌면 부모가 서버에 다시 조회한다. 열 머리를 누르면 오름→내림→원래(최근 등록) 순서
- **검색어**: 입력이 300ms 멈춘 뒤에만 조회에 반영(`useDebouncedValue`). 상태, 고객 등 선택 필터는 바로 조회. 조건이 바뀌면 1쪽으로
- **요청 취소**: 조회 키가 바뀌면 이전 요청은 `signal`로 취소하고 결과도 버린다 (TanStack Query). 새 쪽을 받는 동안 이전 쪽을 흐리게 유지
- **선택 상자, 이름 조회용**(`useProjectChoices`): 한 번에 받을 수 있는 최대 100건. 프로젝트가 그보다 많아지면 검색형 선택 상자로 바꿔야 한다
- 이름 정렬은 DB 정렬 규칙(collation)을 따른다. 한글 가나다 순서가 필요하면 운영 DB의 collation을 확인할 것
