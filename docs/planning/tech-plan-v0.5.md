# 현장 팀 프로젝트 관리 서비스 — 개발 환경·기술 기획서 (v0.5)

> 서비스 기획서(v2.4)의 요구사항을 구현하기 위한 **기술 기획**이다. 기능 요구사항은 서비스 기획서가 기준이고, 이 문서는 "무엇으로, 어떤 구조로, 어떤 규칙으로 만들 것인가"를 정한다.
> **버전 확인일: 2026-10-04** (npm 레지스트리 `latest` 태그, Node 공식 릴리스 일정 기준). 버전은 개발 시작 시점에 한 번 더 확인하고 이후 **정확한 버전으로 고정**한다.

| # | 원칙 | 의미 |

## 3. 버전 정책과 보류 사항

### 3.1 정책
- 모든 의존성은 **정확한 버전으로 고정**하고(캐럿 `^` 없이) `pnpm-lock.yaml`을 커밋한다. `.nvmrc`·`package.json`의 `engines`로 Node 버전도 고정한다.
- 업데이트는 **월 1회 정기 점검**(패치·마이너), 메이저 업데이트는 별도 작업으로 한다. 보안 취약점은 수시로 확인한다.
- 정식 릴리스만 쓴다. `latest` 태그라도 rc·beta이면 쓰지 않는다.

### 3.2 최신이지만 쓰지 않는 것 (이유와 재검토 시점)

| 항목 | 최신 | 보류 이유 | 재검토 |
|---|---|---|---|
| **TypeScript 7.x** | 7.0.2 | typescript-eslint 8.71의 지원 범위가 6.1 미만이라 **린트가 보장되지 않음** | typescript-eslint가 7을 지원하면 |
| **Node.js 26** | 26.10.0 | 2026-10-28에 LTS가 될 예정이라 지금은 아직 LTS 전 | **LTS 전환 후** 24 → 26 올리기 검토(26은 2029-04까지 지원). 24도 2028-04까지 지원되므로 급하지 않음 |
| **Prisma 8** | 8.0.0-rc.19 (**npm `latest` 태그가 이 rc를 가리킴**) | rc(정식 아님). 태그 없이 `pnpm add prisma`하면 rc가 설치될 수 있음 | 정식 8.0 이후. 그때까지 **7.10.0 고정** |
| **PostgreSQL 19** | — | 새 메이저는 첫 마이너가 나온 뒤 도입이 안전 | 안정화 후 |

> 위 표 외에 Node 22(유지보수 단계, 2027-04 종료)는 새로 시작하는 프로젝트에 쓰지 않는다.

## 4. 전체 구조

```
[관리자 휴대폰·PC 브라우저 (PWA)]
        │ HTTPS (같은 도메인)
        ▼
[리버스 프록시: Caddy]  ── / → 정적 파일(React 빌드)
        │                  /api → Express
        ▼
[API 서버 (Node 24 + Express)] ── 같은 프로세스 안에 작업 처리기(pg-boss worker)
        │            │
        ▼            ▼
 [PostgreSQL 18]   [S3 호환 객체 저장소]
  · 업무 데이터         · 사진·작업자료 원본·썸네일
  · 세션·작업 큐        (브라우저가 직접 업로드·다운로드, 짧은 만료 주소)
  · 감사 기록
```

- **모듈형 단일 서버(모놀리스)**: API와 작업 처리기를 한 코드베이스로 두고, 나중에 필요하면 프로세스만 분리한다.
- **같은 도메인에서 서비스**(웹과 /api): CORS가 필요 없고 쿠키 보안이 단순해진다.
- **Redis 없음**: 세션·작업 큐·속도 제한 모두 PostgreSQL로 처리한다(규모가 작은 지인 대상 서비스에 충분). 이용이 늘어 병목이 확인되면 도입한다.

```
field-team-pm/
├─ apps/
│  ├─ web/            React 앱 (Vite). `.storybook/` 설정과 `*.stories.tsx`는 이 안에 둔다
```

- 백엔드는 **기능 모듈 단위**로 나눈다: `auth`, `companies`, `employees`, `projects`, `worklogs`, `materials`, `files`, `notes`, `notifications`.

## 6. 프론트엔드 설계

### 6.1 구조
- **SPA(브라우저 렌더링)**: 로그인 후 쓰는 업무 도구라 검색 노출이 필요 없다. 서버 렌더링은 쓰지 않는다.
- 폴더는 **기능 단위**(`features/projects`, `features/worklogs` …)로 나누고, 각 기능 안에 화면·API 훅·스키마를 둔다.
- 라우트 단위로 **코드 분할(lazy)**해 첫 화면 용량을 줄인다. 사진첩·캘린더처럼 무거운 화면은 필요할 때 불러온다.

### 6.2 상태 관리 규칙 (React Query vs Zustand)

| 구분 | 도구 | 넣는 것 | 넣지 않는 것 |
|---|---|---|---|
| 서버 상태 | **React Query** | 프로젝트·직원·일지·자재·사진 목록과 상세, 집계 | 화면 열림/닫힘 |
| 화면·임시 상태 | **Zustand** | 빠른 추가 버튼 열림, 선택한 날짜·필터, **작성 중 일지·메모 초안** | 서버에서 받은 데이터 복사본 |

- **서버 데이터를 Zustand에 복사하지 않는다**(두 곳이 어긋나는 문제를 막는 규칙).
- 쿼리 키는 `[리소스, 범위, 조건]` 형식으로 통일하고 키 생성 함수를 한 곳에 둔다.
- **낙관적 업데이트**: 메모 추가, 투입 체크처럼 가볍고 실패해도 되돌리기 쉬운 것에만 쓴다. 일지 저장은 서버 확인 뒤 반영한다.
- **작성 중 초안**: Zustand의 persist로 IndexedDB(idb-keyval)에 저장한다. 앱을 닫거나 연결이 끊겨도 입력이 남고, 서비스 기획서의 "임시 저장" 상태와 연결한다.
- 로그아웃·계정 전환 시 **React Query 캐시와 Zustand 저장분을 모두 비운다**(다른 회사 데이터가 화면에 남지 않도록).

### 6.3 현장 사용성 (서비스 기획서 §14 대응)
- **빠른 추가 버튼**은 모든 화면에 고정 표시, 터치 영역 최소 44px, 한 손 조작 위치(하단).
- 사진은 **업로드 대기열**로 처리한다: 선택 즉시 목록에 보이고(미리보기), 백그라운드에서 순차 업로드, 실패 시 재시도, 진행 상태 표시. 앱을 닫아도 대기열이 남도록 IndexedDB에 기록한다.
- 업로드 전 브라우저에서 **긴 변 기준 리사이즈·압축**(예: 2,000px)해 회선 부담을 줄인다(정확한 값은 서비스 기획서 §18.1 #12와 함께 결정).
- PWA 서비스 워커는 **앱 껍데기만 캐시**한다. 업무 데이터의 오프라인 읽기·쓰기는 지원하지 않는다(서비스 기획서 §17의 완전 오프라인은 확장 항목).
- 입력 폼은 React Hook Form + Zod, 일괄 입력(투입 인원 × 공수)은 행 단위 컴포넌트로 리렌더링을 제한한다.

### 6.4 접근성·반응형
- 모바일 우선 레이아웃, 큰 글씨 설정 지원, 대비 기준 준수, 로딩·오류·빈 상태를 모든 목록에 정의.

## 7. 백엔드 설계

### 7.1 계층 규칙
```
라우트(요청·응답 스키마) → 서비스(업무 규칙) → 저장소(DB 접근)
```
- 라우트는 검증과 인증 확인만, **업무 규칙은 서비스**에, **SQL은 저장소**에만 둔다.
- **Express에서는 구조를 규칙으로 지킨다**: 프레임워크가 강제하지 않으므로 라우트에는 `validate` 미들웨어 → `requireAuth` 미들웨어 → 컨트롤러 순서를 표준 틀로 정하고, 이를 어기는 라우트는 코드 리뷰·테스트에서 걸러낸다.
- 모든 요청은 Zod 스키마로 검증한다(`validate` 미들웨어, 검증 실패는 일괄 400 형식). 응답은 **응답 스키마로 파싱해서 내보낸다**(`res.json(ResponseSchema.parse(data))`, Express는 자동으로 걸러 주지 않으므로 규칙으로 강제) **불필요한 필드(내부 ID, 다른 회사 정보)가 나가지 않게** 한다.

### 7.2 API 규칙
- REST + JSON, 경로는 `/api/v1/...`. 오류는 하나의 형식(코드·메시지·필드 오류)으로 통일.
- 목록은 **커서 기반 페이지네이션**(사진·일지처럼 늘어나는 데이터).
- **존재하지 않음과 접근 불가를 구분하지 않는다**(다른 회사 자료는 항상 "없음" 응답, 서비스 기획서 §5.1).
- 쓰기 요청에는 **멱등 키**(Idempotency-Key)를 지원한다. 현장 회선 불안으로 재전송되어도 일지·사진이 중복되지 않게 한다.
- 수정은 **버전(낙관적 잠금)** 으로 충돌을 감지한다.
- OpenAPI 문서를 **Zod 스키마에서 생성**하고(zod-to-openapi) 프론트 API 타입을 생성한다(손으로 타입을 쓰지 않는다). 라우트를 추가할 때 문서 등록을 빠뜨리면 CI에서 실패하도록 "등록된 라우트 = 문서 경로" 일치 테스트를 둔다.

### 7.3 인증·세션 (서비스 기획서 §6 대응)
- **서버 세션 방식**: 세션을 PostgreSQL에 저장하고 브라우저에는 `HttpOnly + Secure + SameSite=Lax` 쿠키만 둔다. JWT는 쓰지 않는다(즉시 로그아웃·기기 목록·원격 로그아웃에 서버 세션이 유리).
- 세션 정보에 **회사 ID를 서버가 보관**하며, 요청의 회사 ID는 **절대 클라이언트 입력으로 받지 않는다**(§8).
- 비밀번호는 argon2, 로그인 시도 제한(express-rate-limit + 계정 단위 잠금).
- 이메일 인증 코드(6자리)·비밀번호 재설정 링크는 **해시로 저장**, 만료·시도 횟수 제한.
- 소셜 로그인(arctic): 카카오·네이버·구글. 초기에는 **아이디 + 카카오**(서비스 기획서 §16 0단계), 나머지는 5단계.
- 2단계 인증(TOTP)은 서비스 기획서에서 권장 항목이므로 **0단계에서는 구조만 두고 3단계 이후 구현**.
- CSRF: SameSite 쿠키 + Origin 검증 + 변경 요청에 커스텀 헤더 요구.

### 7.4 백그라운드 작업 (pg-boss)
- 이메일 발송, 썸네일 생성, 미입력·보증 임박 알림 계산, 세션·인증 코드 정리, 해지 유예(14일) 후 삭제, 백업 점검.
- 작업은 **회사 ID를 인자로 받아 실행하고 격리 규칙을 동일하게 적용**한다(§8.3).

## 8. 회사 격리 구현 (가장 중요)

서비스 기획서 §5 요구: 회사는 계정으로 결정, 클라이언트가 지정하지 않음, 다른 회사 자료는 존재 자체가 보이지 않음, 운영자도 업무 자료를 보지 못함.

### 8.1 방식: 단일 DB·공용 테이블 + `company_id` + **PostgreSQL 행 수준 보안(RLS)**
- 업무 테이블에 모두 `company_id`를 두고, 복합 키·외래 키에도 `company_id`를 포함해 **다른 회사 행과 연결되는 것 자체를 DB가 막는다**.
- 모든 업무 테이블에 **RLS 정책**을 걸어 `company_id = 현재 요청의 회사`인 행만 보이게 한다.
- 이유: 앱 코드에서 `WHERE company_id = ?`를 빠뜨리는 실수를 DB가 마지막 방어선으로 막는다. 회사 수가 적어 DB를 따로 쪼갤 필요는 없다(분리가 필요해지면 회사 단위 이전 가능, 서비스 기획서 §20).

### 8.2 요청 처리 방식
1. 세션에서 `company_id`를 얻는다(요청 본문·주소·헤더의 값은 쓰지 않는다).
2. 요청마다 **트랜잭션을 열고 `SET LOCAL app.company_id = …`** 를 설정한다.
3. 같은 트랜잭션 안에서 모든 쿼리를 실행한다(트랜잭션이 끝나면 설정도 사라져 연결 풀 재사용 시 새어 나가지 않음).
4. 앱이 쓰는 DB 계정은 **RLS를 우회할 수 없는 일반 권한 계정**이다. 마이그레이션·운영 점검용 계정은 별도로 분리한다.

### 8.3 예외 영역
- 로그인 전 조회(아이디로 계정 찾기), 초대 코드 확인, 운영자 회사 생성은 **회사 범위 밖 전용 모듈**에서만 하고, 이 모듈은 업무 테이블에 접근하지 못하게 DB 권한을 분리한다.
- 백그라운드 작업은 회사별로 같은 방식(§8.2)으로 실행한다.
- **운영자 지원 열람**(서비스 기획서 #17): 기본 불가. 필요 시 관리자가 승인한 기간 동안만 열리는 별도 경로와 기록으로 구현(후순위).

### 8.4 Prisma에서 RLS를 쓰는 방법 (§8.2의 구현)
Prisma는 RLS 정책을 스키마로 표현하지 못하고 `SET LOCAL`도 기본 제공하지 않으므로 다음처럼 보완한다.

1. **정책은 마이그레이션 SQL로 직접 작성**한다: `prisma migrate dev --create-only`로 파일을 만들고 `ALTER TABLE … ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`, `CREATE POLICY …`를 직접 추가한다. 이후 `schema.prisma`와 DB가 어긋나지 않도록 마이그레이션 상태 검사를 CI에 둔다.
2. **요청 단위 트랜잭션 헬퍼 `withCompany(companyId, fn)`** 를 하나만 만든다.
   - `prisma.$transaction(async (tx) => { set_config('app.company_id', 회사ID, true); return fn(tx) })`
   - 서비스·저장소 코드는 **반드시 이 헬퍼가 넘겨주는 `tx`로만** DB에 접근한다. 헬퍼 밖에서 전역 `prisma`를 직접 쓰는 것은 린트 규칙으로 금지한다(회사 범위 밖 전용 모듈 제외).
   - 쿼리마다 감싸는 Prisma Client Extension 방식은 쿼리마다 트랜잭션이 생겨 느리고 여러 쿼리를 하나로 묶기 어려워 쓰지 않는다.
3. **DB 계정 두 개**: 마이그레이션용(테이블 소유자)과 앱용(RLS 우회 불가, 업무 테이블에 SELECT·INSERT·UPDATE만, 이력·감사 테이블은 INSERT·SELECT만)을 분리하고 접속 주소를 각각 둔다.
4. **복합 키·외래 키**: `@@unique([companyId, id])`와 `references: [companyId, projectId]`처럼 `company_id`를 포함한 관계로 선언해 다른 회사 행과의 연결을 DB가 막는다.
5. **Prisma 7 설정 주의**: 연결은 `@prisma/adapter-pg`(드라이버 어댑터)로 하고, 연결 설정은 `prisma.config.ts`, 생성된 클라이언트는 지정한 폴더에 생성된다(저장소에 포함 여부 결정). 생성 클라이언트가 ESM이라 Jest에서는 ESM 전용 패키지와 같은 방식으로 다룬다(§13.1).
6. **`$queryRaw`·`$executeRaw` 금지 영역**: 회사 범위 쿼리에서 원시 SQL을 쓸 때도 반드시 `tx`로 실행(전역 `prisma`로 실행하면 RLS 설정이 없어 아무것도 안 보이거나 오류가 난다는 점이 오히려 안전장치가 됨).

### 8.5 자동 점검 (0단계 완료 기준)
- **Testcontainers로 실제 PostgreSQL**을 띄워, 회사 A·B 데이터를 만든 뒤 **모든 API 엔드포인트가 B 자료를 A에게 주지 않는지** 자동 검사한다.
- 새 테이블을 만들 때 `company_id`·RLS 정책이 없으면 실패하는 **스키마 검사 테스트**를 둔다.
- 파일(사진·자료) 주소도 같은 검사에 포함한다(§10).

## 9. 데이터베이스

- **PostgreSQL 18**, 문자 집합 UTF-8, 시간은 UTC로 저장하고 화면에서 한국 시간(KST)으로 표시.
- 식별자는 **UUID(v7 권장)** — 순번 노출 방지와 정렬 효율. 사람이 보는 프로젝트 코드(예: 2026-012)는 별도 열.
- 공수는 서비스 기획서대로 **분 단위 정수**로 저장한다(1.0 = 회사 기준 시간). 소수 오차를 피한다.
- **수정 이력·감사 기록은 추가만 가능한 테이블**(앱 계정에 수정·삭제 권한 없음).
- 삭제는 업무 데이터는 **논리 삭제**(복구·감사), 해지 후 14일이 지나면 **물리 삭제**(작업으로 처리, 파일 포함).
- 마이그레이션은 **Prisma Migrate**, **변경은 항상 마이그레이션 파일로** 하고 운영 DB에 직접 수정하지 않는다.
- 연결은 풀링(pg Pool)을 쓰되, 연결 수는 서버 규모에 맞게 낮게 시작한다.
- 상세 테이블 설계는 별도 문서("데이터 모델 기획")에서 다룬다(§17).

## 10. 파일(사진·작업자료) 저장

- **S3 호환 객체 저장소**를 쓴다(공급자는 §15에서 결정). 코드는 S3 API 하나로 작성해 공급자를 바꿀 수 있게 한다.
- **업로드**: 브라우저가 서버에서 받은 **짧은 만료의 업로드 주소**로 저장소에 직접 올린다(서버 부하·메모리 절약). 서버는 올라온 뒤 **내용 검사(file-type)·크기 확인·썸네일 생성(sharp)** 을 작업으로 처리한다.
- **경로**: `company/{회사ID}/project/{프로젝트ID}/…` — 경로에 회사가 들어가고, **다운로드 주소는 서버가 권한 확인 후 짧은 만료로 발급**한다. 저장소를 공개로 두지 않는다.
- 허용 형식은 허용 목록(이미지, PDF, 문서)만, 실행 파일 거부, 최대 크기 제한, 회사별 용량 한도.
- **EXIF 위치 정보**: 원본에는 보존하고(증빙), 내려받기·외부 전달 시 제거 옵션(서비스 기획서 §5.9). 썸네일에는 위치 정보를 넣지 않는다.
- 문서 **버전 관리**: 같은 문서의 새 버전은 새 객체로 저장, 이전 버전은 보존.
- 파일 열람·내보내기는 **감사 기록**에 남긴다(민감 자료 표시 파일 대상, 서비스 기획서 §7).

## 11. 이메일

- 용도: 인증 코드, 비밀번호 재설정, 보안 알림, 서비스 안내(선택).
- 발송은 **외부 이메일 발송 서비스의 SMTP**를 nodemailer로 사용(자체 메일 서버 운영 금지). 공급자는 §15에서 결정하고, **발송 도메인에 SPF·DKIM·DMARC 설정**이 필수다(없으면 스팸 처리).
- 발송은 **작업 큐**를 통해 하고 실패 시 재시도한다. 인증 코드 발송에는 **횟수·시간 제한**을 둔다.
- 템플릿은 코드에 두고 텍스트판을 함께 만든다. 메일 본문에 **개인정보(전화번호 등)를 넣지 않는다**.

|---|---|---|
| 단위 | Jest | **공수·MM·소진율·자재 잔량 계산**(기획서 예시 값 그대로), 날짜·기간 계산 |
| 통합(API+DB) | Jest + supertest + Testcontainers | 모든 엔드포인트, **회사 격리**, 상태 전환 규칙, 인증·세션 |
| 화면 | Playwright | 핵심 흐름: 로그인 → 프로젝트 → 투입 → 일지 일괄 입력 → 사진 업로드 → 저장. 모바일 화면 크기 포함 |
| 계약 | OpenAPI 타입 생성 | 프론트·백엔드 불일치는 빌드 실패로 |

### 13.1 Jest 사용 시 주의사항 (Vitest 대비)
| 문제 | 대응 |
|---|---|
| **ESM 전용 패키지**(file-type, arctic 등)를 Jest가 못 읽음 | 테스트에서는 swc가 CommonJS로 변환하도록 설정하고, ESM 전용 패키지는 `transformIgnorePatterns` 예외 처리 또는 **얇은 래퍼 모듈을 만들어 `jest.mock`** 으로 대체(래퍼는 어차피 필요한 구조) |
| **`import.meta.env`**(Vite 환경 변수)를 Jest가 해석 못 함 | 프론트에서 환경 변수 접근을 **한 파일(`env.ts`)로 모으고** 테스트에서 그 모듈을 mock |
| 프론트 테스트가 Vite 설정(경로 별칭 등)을 자동으로 못 씀 | Jest `moduleNameMapper`에 별칭을 따로 맞춘다(별칭은 최소화) |
| CSS·이미지 import | 변환 설정에서 빈 모듈로 처리 |
| 타입 오류가 테스트에서 안 걸림(@swc/jest는 타입 검사 안 함) | CI에서 `tsc --noEmit`을 별도로 실행(이미 CI 순서에 포함) |
| 실행 속도 | @swc/jest 사용, 통합 테스트(Testcontainers)는 별도 프로젝트 설정으로 분리해 단위 테스트를 빠르게 유지 |
| 프론트·백엔드·공유 패키지 설정 중복 | Jest의 `projects` 기능으로 루트 설정 하나에서 패키지별 환경(node / jsdom)을 나눔 |

> ts-jest(29.4.14, TypeScript 7 미만 지원)도 대안이다. 타입 검사까지 테스트에서 하지만 느리므로 기본은 @swc/jest로 한다.

### 13.2 역할 분담: Storybook과 Jest

| 하는 일 | 도구 |
|---|---|
| 컴포넌트를 **눈으로 확인하고 상태별로 모아 보기**(빈 화면·로딩·오류·긴 이름·많은 사진 등) | **Storybook** |
| 컴포넌트의 **클릭·입력 동작**과 접근성 점검 | Storybook의 `play` 함수 + test-runner, a11y 애드온 |
| **로직 검증**(공수 계산, 훅, 스토어, 순수 함수, 폼 규칙) | **Jest** (+ Testing Library) |
| **화면 전체 흐름**(로그인 → 일지 저장) | Playwright |

- **같은 것을 두 번 검증하지 않는다**: 화면 모양과 상태는 Storybook, 계산과 규칙은 Jest. 컴포넌트마다 Jest 렌더링 테스트를 따로 쓰지 않아도 되도록 스토리의 `play`로 대신한다.

### 13.3 Storybook 운영 규칙
- **대상 컴포넌트**: 공통 UI 부품(버튼, 입력, 시트, 목록 행, 상태 배지)과 핵심 도메인 컴포넌트(투입 인원 행, 일지 일괄 입력 행, 사진 썸네일 그리드, 빠른 추가 버튼, 프로젝트 상태 표시). 페이지 전체는 대상이 아니다(Playwright).
- **스토리에는 가짜 데이터만** 쓴다. 실제 직원·고객 이름과 사진을 넣지 않는다(저장소·외부 서비스로 나갈 수 있음).
- **모바일 화면 기준 뷰포트**를 기본으로 하고 데스크톱을 추가한다. 터치 영역 44px, 큰 글씨 설정(§6.4)을 스토리로 확인한다.
- **상태 스토리를 필수로 만든다**: 기본 / 빈 상태 / 로딩 / 오류 / 긴 텍스트 / 읽기 전용 중 해당하는 것(§6.4의 "모든 목록에 정의"를 스토리로 점검).
- **React Query·Zustand·라우터는 스토리 공통 장식자(decorator)로 제공**한다: 스토리마다 새 QueryClient를 만들어 서로 영향이 없게 하고, API 응답은 msw-storybook-addon으로 가짜 응답을 준다.
- **Tailwind·글꼴**은 앱과 같은 설정을 불러와서 스토리와 실제 화면이 같게 보이게 한다.
- **자동 점검**: 접근성(a11y) 위반은 CI에서 경고가 아니라 실패로 처리하고, `play` 함수가 있는 스토리는 test-runner로 실행한다.
- **정적 배포**는 하지 않거나 **접근을 제한**한다(내부 디자인·구조 노출 방지). 필요하면 개인 개발용으로만 쓴다.
- **시각 회귀(Chromatic)** 는 선택 사항이다. 화면 스냅샷이 외부 서비스에 올라가므로 가짜 데이터만 쓰는 규칙이 전제이고, 1인 개발 초기에는 생략해도 된다.
- **대안**: Storybook 공식 Vitest 애드온(@storybook/addon-vitest)으로 스토리를 테스트할 수도 있으나 Vitest를 추가로 들여야 하므로, Jest를 선택한 현재 구성에서는 **test-runner를 기본**으로 한다.

### 13.4 코딩 컨벤션: jbeat-conventions 플러그인 (주석·네이밍 등)

개발 중 Claude Code가 코드를 쓰고 고칠 때 **본인의 컨벤션 저장소를 기준으로 삼는다.**
- 저장소: https://github.com/jbeat30/jbeat-conventions (플러그인 `jbeat-conventions@jbeat-plugins`, 확인한 버전 0.3.2)
- 설치: `claude plugins install jbeat-conventions@jbeat-plugins`, 갱신: `claude plugins update jbeat-conventions@jbeat-plugins`

**적용 방법**
| 방식 | 방법 | 용도 |
|---|---|---|
| 자동(권장) | 개발 저장소에서 `/jbeat-setup` 실행 → **"이 프로젝트에만 적용"** 선택 → `.claude/settings.json`에 플러그인 활성화와 마켓플레이스 등록이 기록됨. 이 파일을 **저장소에 커밋** | 이 프로젝트에서 항상 적용 |
| 수동 | 세션에서 `/jbeat-apply` | 자동이 꺼져 있거나 명시적으로 다시 불러올 때 |
| 안내 | 저장소 루트 `CLAUDE.md`에 "코드·주석은 jbeat-conventions 규칙을 따른다" 한 줄 | 설정이 빠진 환경 대비 |

**주의: 주석 규칙만 따로 켤 수는 없다.** 플러그인은 코어 규칙, 네이밍, **주석**, 언어, 품질 체크리스트, 보고 형식 6개를 한꺼번에 불러온다. 따라서 주석뿐 아니라 "요청 범위 안에서 최소 변경", "검증하지 않은 것을 했다고 말하지 않기" 같은 규칙도 함께 적용된다.

**주석 규칙 요약 (`references/comment-conventions.md`) 과 이 프로젝트 적용**
| 규칙 | 이 프로젝트에서의 예 |
|---|---|
| 한국어, **명사형 종결**(담당·반환·수행·정의·검증), **마침표 없음**, How가 아니라 **Why·What** | `// 회사 범위 밖 전용 조회 (로그인 전)` |
| **JSDoc(`/** */`)은 export된 함수·클래스에만**, `@description`·`@param`·`@returns`·`@throws` 필요한 것만 | 서비스 함수, `withCompany`, 공수 계산 함수, 공유 패키지의 공개 함수 |
| 내부 분기·변수·블록 설명은 **`//`** (스타일 혼용 금지: 변수에 `/** */` 금지, export 함수 머리에 `//` 금지) | `const dayMinutes = 480; // 회사 기준 하루 시간(분)` |
| 주석이 필요한 곳: 정책 분기, 외부 계약, 성능·우회·캐시 이유, 복잡한 상태 변경, 레거시 폴백 | RLS·`set_config`, 상태 전환 규칙, 멱등 키 처리, 분 단위 공수 변환, 서비스 기획서 정책 근거 |
| 쓰지 않는 주석: 코드를 되풀이, 쉽게 낡는 상태 설명, 추측·감상, 긴 절차 설명 | — |

**다른 컨벤션 파일과 이 기획서의 연결**
- **에러 메시지**: 사용자에게 보이는 문구는 한 파일(예: `errorMessages.ts`)에 의미 단위 상수로 모으고, 개발자용 로그는 `[모듈.함수] 원인` 형식으로 쓴다. 로그 규칙(§12, 개인정보 마스킹)과 함께 적용한다. 오류 상황과 문구가 일치해야 한다(예: 업로드 실패에 "녹음 실패" 문구 금지).
- **네이밍·구조**: 기존 패턴을 우선하고, 불리언은 `is/has/can/should/needs`, 외부 필드명(소셜 로그인 응답 등)은 내부 이름과 변환 지점을 분리한다.
- **언어**: 주석·보고는 한국어 기본, 식별자·파일명·외부 계약은 제외.

**한계**
- 한국어·명사형·마침표 규칙은 ESLint로 강제하기 어렵다. **Claude Code 작업과 사람의 리뷰로 지킨다.** 기계로 막을 수 있는 것(타입, 린트, 테스트)은 §13의 도구가 맡는다.
- 계정에 별도로 등록된 `comment-convention`(주석·JSDoc 문체) 스킬이 따로 있다. 같은 주제의 기준이 둘이면 서로 어긋날 수 있으니 **jbeat-conventions를 기준으로 하나만 쓰고** 나머지는 내용 비교 후 정리한다(두 문서의 내용 비교는 아직 하지 않았다).

### 13.5 공통 규칙
- **커밋 시**: lint-staged(ESLint·Prettier), **CI(GitHub Actions 등)**: 타입 검사 → 린트 → 단위 → 통합 → 빌드 → E2E(주요 경로) → audit.
- 서비스 기획서 §16의 "완료 기준"을 **인수 테스트**로 옮긴다(예: 두 회사 격리, §9.5 예시 계산 일치, 3분 입력).

## 14. 환경과 배포

| 환경 | 구성 |
|---|---|
| 로컬 | Docker Compose(PostgreSQL 18 + 로컬 S3 호환 저장소), pnpm 개발 서버, 가짜 이메일 수신기 |
| 스테이징 | 운영과 같은 구성의 작은 인스턴스(선택, 실사용 시험 전부터 권장) |
| 운영 | 서울 리전 서버 1대(컨테이너) + PostgreSQL + 객체 저장소 |

- **컨테이너(Docker)로 배포**하고, 마이그레이션은 배포 절차에 포함한다. 무중단 배포는 초기 목표가 아니다(지인 대상, 점검 시간 허용).
- **백업(0단계부터)**: PostgreSQL 일일 백업과 객체 저장소 버전 관리/복제, **복구 시험을 정기적으로 실행**한다(백업은 복구해 봐야 백업이다). 백업 보관 기간은 개인정보 보유 기간 규칙과 맞춘다.
- **모니터링**: 서버 상태·디스크 용량·오류율·작업 큐 정체 알림(운영자 이메일).
- 환경 변수는 `.env.example`로 목록만 관리하고 값은 저장소에 두지 않는다.

## 15. 호스팅·외부 서비스 선택 기준 (미확정)

공급자 이름은 비용·지역·약관을 직접 비교해 정한다. 이 문서는 **선택 기준**만 둔다.

| 영역 | 기준 |
|---|---|
| 서버·DB | **국내(서울) 리전**, 자동 백업·시점 복구, 월 비용 예측 가능. 매니지드 DB 또는 서버 내 설치 둘 다 가능(후자는 백업·보안 업데이트 책임이 커짐) |
| 객체 저장소 | S3 호환, 국내 리전 또는 한국 서비스 이용 가능, 버전 관리·수명 주기 규칙 |
| 이메일 발송 | SMTP 제공, 도메인 인증(SPF·DKIM·DMARC), 발송 한도·단가, **수탁자 개인정보 조항 확인** |
| 도메인·DNS | 운영자 소유 도메인 1개, 소셜 로그인 앱 등록에 쓸 공개 주소(처리방침 페이지 포함) |
| 오류 추적 | 개인정보 전송을 끌 수 있는 서비스, 또는 자체 로그로 대체 |

> **개인정보 처리방침과 연결**: 위 공급자가 정해지면 서비스 기획서 §5.12의 **수탁·위탁 현황과 국외 이전 항목**을 그 내용으로 채운다. 해외 서비스를 쓰면 이전 국가·항목·방법을 적어야 하므로, 국내 리전 선택이 처리방침 작성도 단순하게 한다.
