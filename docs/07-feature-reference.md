# 기능·운영 상세 참고

> 기능과 운영 방법을 모은 참고서다. 처음 보는 사람은 루트 [README](../README.md)를 먼저 본다. 기능을 바꿀 때 이 문서의 해당 부분을 함께 갱신한다

현장직 팀(판금·전기·목공 등)의 관리자가 프로젝트별 투입 인원·공수·작업일지·자재·사진을 수첩처럼 기록하는 서비스.

## 구성

| 경로              | 내용                                                     |
| ----------------- | -------------------------------------------------------- |
| `apps/web`        | React 19 + Vite 8 (SPA, 토스 블루 디자인 토큰·다크 모드) |
| `apps/api`        | Express 5 API 서버                                       |
| `packages/shared` | Zod 스키마, 공통 타입, 공수 계산                         |
| `packages/config` | tsconfig·ESLint·Jest 공통 설정                           |
| `docs`            | 기획서, 분석, 개발 순서 설계                             |

## 시작하기

로컬에서 확인하는 방법은 두 가지다. 화면만 보려면 A(목업 모드), 실제 DB·api까지 보려면 B를 쓴다.

### 준비물

- Node 24 이상
- pnpm 12.9.1 (`packageManager`로 고정, `pnpm -v`로 확인)
- Docker (macOS는 Docker Desktop). 방식 B와 `pnpm test`에 필요하다 (방식 A는 불필요)

### A. 화면만 빠르게 확인 (목업 모드)

```bash
pnpm install        # 처음 한 번, 의존성이 바뀌었을 때
pnpm dev:mock       # http://localhost:5173/login
```

백엔드 없이 브라우저 안의 가짜 서버가 응답한다. 데모 계정과 시나리오는 아래 [목업 모드](#목업-모드-백엔드-없이-화면-확인) 표를 본다.

### B. 실제 DB·api까지 확인

**처음 한 번 — 순서를 바꾸면 안 된다**

```bash
pnpm install
pnpm prepare        # 커밋 훅(husky) 연결
pnpm env:init       # 1) .env 생성: DB 비밀번호·저장소 키를 이 PC에서 새로 만듦 (Git에 올라가지 않음)
pnpm infra:up       # 2) Docker 기동(꺼져 있으면 macOS는 Docker Desktop 자동 실행) + DB·저장소·메일 컨테이너
pnpm db:setup       # 3) 테이블 생성 + DB 계정 비밀번호 설정 (infra:up 뒤에)
pnpm db:seed        # 4) 더미 회사·계정·약관·초대 링크 입력 (db:setup 뒤에, 여러 번 실행해도 같은 결과)
```

**평소에는**

```bash
pnpm dev            # 인프라 기동 + api(:3000) + web(:5173)
```

종료는 `Ctrl+C`, 컨테이너까지 끄려면 `pnpm infra:down`.

**순서 규칙과 자주 겪는 상황**

| 상황                                                  | 할 일                                                                                                                                                    |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 새 마이그레이션이 포함된 브랜치를 받았다 (`git pull`) | `pnpm db:setup` 다시 실행                                                                                                                                |
| DB를 처음 상태로 되돌리고 싶다                        | `pnpm db:reset` (컨테이너 삭제 → 기동 → 마이그레이션 → 시드)                                                                                             |
| `.env`를 새로 만들고 싶다                             | `pnpm env:init --force` 후 `pnpm db:reset` (DB 컨테이너에 저장된 기존 비밀번호와 어긋나므로 DB도 함께 초기화)                                            |
| 새 환경 변수가 추가돼 api가 기동하지 않는다           | 오류 메시지의 변수 이름을 `.env.example`과 비교해 `.env`에 추가                                                                                          |
| `pnpm env:init`이 "이미 있어 건너뜀"이라고 한다       | 정상 (기존 `.env`를 보호). 새로 만들려면 `--force`                                                                                                       |
| 3000번 포트를 다른 프로그램이 쓰고 있다               | api를 `PORT=3001`로 띄우고 web은 `API_PROXY_TARGET=http://localhost:3001`로 실행 (`pnpm dev` 대신 `pnpm dev:api`·`pnpm dev:web`를 각각 환경 변수와 함께) |

**확인할 곳**

| 주소                                  | 내용                                         |
| ------------------------------------- | -------------------------------------------- |
| `http://localhost:3000/api/v1/health` | api 상태                                     |
| `http://localhost:3000/api/docs`      | API 문서 (개발 환경만)                       |
| `http://localhost:8025`               | Mailpit (이메일 인증 코드 등 발송 메일 확인) |
| `http://localhost:9001`               | RustFS 관리 화면 (S3 호환 저장소)            |

**로컬 시드 계정과 확인 방법**

| 확인할 것           | 방법                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 로그인              | `hanbit` / `Hanbit-demo-2026!`, `saeron` / `Saeron-demo-2026!` (잠겼다면 15분 뒤 또는 `pnpm db:reset`)                  |
| 이메일 인증 전 계정 | `newbie` / `Newbie-demo-2026!` (로그인하면 인증 화면으로 이동, 30초 뒤 "코드 다시 받기"를 누르면 Mailpit에 코드가 도착) |

| 소셜 로그인         | 앱 등록 전 개발 환경에서는 가짜 로그인 화면에서 계정을 골라 끝까지 확인 (아래 "소셜 로그인")                            |

### 운영자 CLI

회사와 관리자 계정을 만들고 1회용 초대 링크를 발급한다. 서버에서는 아래 "서버 운영"의 단축어(`new-company` 등)로 더 짧게 쓴다. 운영자 전용 DB 계정(`DATABASE_OPERATOR_URL`)으로 접속하며 회사 업무 데이터는 조회할 수 없다.

```bash
pnpm operator create-company --company "한빛판금" --admin "김한빛"   # 회사 + 관리자(가입 전) + 초대 링크 (기본 7일)
pnpm operator reissue --company-id <회사 ID>                        # 링크 재발급 (기존 링크는 즉시 만료, 가입 전 회사만)
pnpm operator recover --company-id <회사 ID> --note "본인 확인 방법"   # 계정 복구 링크 (이메일을 쓸 수 없는 가입 완료 계정, 링크를 쓰면 기존 로그인 해제)
pnpm operator transfer --company-id <회사 ID> --new-name "새 소유자" --note "본인 확인 방법"   # 소유자 이전 링크
pnpm operator list                                                  # 회사 목록과 가입 상태
pnpm operator legal-register                                        # 약관·처리방침 문서를 DB에 등록 (운영 환경 최초 1회, 문서를 바꿔 버전을 올릴 때마다)
pnpm operator closures                                              # 해지 요청 현황 (유예 중·삭제 예정 시각, 삭제 대상 표시)
pnpm operator purge-due [--dry-run]                                 # 유예(14일)가 끝난 회사의 데이터 삭제·익명화 (--dry-run은 대상만 표시)
pnpm operator demo-reset                                            # 공개 시연 회사(Test Company)를 처음 상태로 되돌림 (PUBLIC_DEMO_ENABLED=true, 소유 계정 필요)
pnpm operator demo-remove                                           # 공개 시연 회사의 데이터·파일·로그인을 없앰 (시연 환경을 끌 때)
pnpm operator delete-company --company-id <ID> --confirm-name "회사 이름" [--dry-run]   # 해지 유예 없이 회사를 완전 삭제 (시험 계정 정리용, 소유 계정 필요)
```

- 링크는 발급 직후 한 번만 표시된다 (DB에는 해시만 저장)
- 링크는 한 번 쓰면 폐기되고, 만료·사용 완료·없는 링크는 같은 화면으로 안내된다
- `closures`·`purge-due`는 삭제 전용 DB 계정(`DATABASE_PURGE_URL`)으로 접속한다. 삭제는 api가 하지 않고, 서버 크론이 매일 03:30에 이 명령을 실행해 처리한다
- `delete-company`는 회사 이름이 `--confirm-name`과 정확히 같을 때만 실행한다. `--dry-run`은 테이블별로 지울 행 수만 보여 주고 되돌린다. 실제 실행은 모든 테이블의 행(계정·약관 동의·운영자 기록 포함)과 `company/<회사 ID>/` 업로드 파일을 한 번에 지우며 되돌릴 수 없다. 회사 행이 사라져 `operator_actions`에 남길 수 없으므로 실행 기록(시각·운영자·회사 ID·이름)을 화면에 출력한다. 시연 회사는 대상에서 제외된다(`demo-remove` 사용). 시험 계정이 아닌 실제 회사는 해지 흐름(`purge-due`)을 쓴다
- 운영자 작업은 `operator_actions`에 기록된다 (회사와 무관한 약관 문서 등록은 `legal_documents`의 생성 시각으로 확인)

## 화면 전체 시험 (E2E)

- 실제 DB·객체 저장소·API·웹을 띄워 Chromium(모바일 크기)으로 **핵심 흐름**(로그인 → 프로젝트 → 직원 선택·투입 자동 추가 → 작업 내역 → 자재 → 지출 기록 → 사진 → 작업일보), **프로젝트 생애 흐름**(진행률 → 완료 → 보증 설정·시작 → 보수 요청), **월 공수 확정·재오픈**, **직원 서류 등록**, **홈 확인 목록**, **저장 용량·전체 데이터 내려받기**와 **하루 일지 입력 시간**을 확인한다. 위치는 `apps/web/e2e`다
- 실행: `pnpm --filter @field-note/api db:generate && pnpm infra:up && pnpm db:setup && pnpm db:seed` 후 `pnpm e2e` (API는 3001번, 웹은 5173번으로 시험이 직접 띄우며 이미 떠 있으면 재사용). 목업 서버가 실행 중이면 `E2E_API_PORT`·`E2E_WEB_PORT`를 다른 포트로 지정하고 `CI=true`로 서버 재사용을 끈다 (PowerShell 예: `$env:E2E_API_PORT='13001'; $env:E2E_WEB_PORT='15173'; $env:CI='true'; pnpm e2e`). 처음에는 `pnpm --filter @field-note/web exec playwright install chromium`이 필요하다
- 하루 일지 입력 시간은 스크립트가 사람 속도를 흉내 낸 값(누르기 전 0.8초, 글자 0.2초/자)이라 **참고용 측정**이다. 실제 사람의 시간은 실사용 시험에서 재다
- CI의 `e2e` 잡이 같은 순서로 준비해 돌리고, 실패하면 보고서와 추적 파일(`playwright-report`, `test-results`)을 보관한다

## 로컬 인프라

`docker-compose.yml`로 실행되며, 운영 환경 대신 쓰는 개발용 대역이다.

| 서비스     | 역할                                  | 접속 주소                                               |
| ---------- | ------------------------------------- | ------------------------------------------------------- |
| PostgreSQL | 데이터베이스                          | `localhost:5432` (계정·비밀번호·DB명 모두 `field_note`) |
| RustFS     | 사진·자료 저장소 (S3 호환)            | API `localhost:9000`, 관리 화면 `localhost:9001`        |
| Mailpit    | 보낸 메일을 받아 보여주는 가짜 메일함 | 메일 수신 `localhost:1025`, 확인 화면 `localhost:8025`  |

- 메일은 실제로 발송되지 않는다. 인증 메일 등은 `localhost:8025`에서 확인한다 (포트가 막히면 `.env`에 `MAILPIT_UI_PORT=18025`처럼 적어 바꾼다)
- MinIO 공식 이미지가 더 이상 배포되지 않아 호환 제품인 RustFS를 쓴다

## DB와 회사 격리

- DB 계정이 여섯 개다
  - **소유 계정**(`DATABASE_MIGRATE_URL`): 테이블을 만드는 마이그레이션 전용
  - **앱 계정**(`DATABASE_URL`): 업무 쿼리용. 다른 회사 데이터를 볼 수 없게 DB가 막고, 세션 테이블은 접근할 수 없다
  - **회사 범위 밖 전용 계정**(`DATABASE_AUTH_URL`): 로그인 전처럼 회사를 아직 모르는 시점의 세션 조회 전용. 업무 테이블 권한이 없다
  - **작업 큐 계정**(`DATABASE_QUEUE_URL`): 이메일 발송 같은 백그라운드 작업 큐(pg-boss)용. 큐 스키마(`pgboss`)만 쓰고 업무 테이블은 읽을 수 없다
  - **운영자 계정**(`DATABASE_OPERATOR_URL`): 운영자 CLI 전용. 회사·초대 발급만 가능하고 업무 테이블은 읽을 수 없다
  - **삭제 계정**(`DATABASE_PURGE_URL`): 해지 유예가 끝난 회사의 데이터 삭제·익명화 전용. 해지 중이 아닌 회사의 행은 DB가 보이지 않게 막는다
- 업무 쿼리는 반드시 `withCompany(prisma, 회사ID, (tx) => …)`가 넘겨주는 `tx`로만 실행한다. 이 밖에서 조회하면 아무 행도 보이지 않는다
- `pnpm test`의 격리·스키마 검사 테스트는 Docker로 임시 PostgreSQL을 띄운다. Docker가 꺼져 있으면 실패한다
- Prisma 클라이언트는 `pnpm typecheck`·`pnpm test`가 자동으로 생성한다 (`src/generated`, Git 제외)
- **새 기능을 만들 때 격리 시험을 빠뜨릴 수 없다**: 로그인이 필요한 엔드포인트를 새로 만들면 `isolationEndpoints.test.ts`의 격리 시험 목록(다른 회사의 ID로 요청해 404인지)에 넣어야 하고, 안 넣으면 시험이 실패한다. 본인 계정·세션만 다루는 것만 `OWN_ACCOUNT_ONLY`에 둘 수 있다. 새 테이블은 `company_id`·RLS·해지 삭제 정책이 없으면 실패하고, 운영자·로그인 전용·작업 큐 계정이 접근할 수 있는 테이블은 목록으로 고정되어 있다
- 파일은 저장소 경로가 `company/{회사 ID}/`로 시작해야 하며, DB가 다른 회사 경로를 가리키는 파일 행을 거부한다. 내려받기·열람 주소는 회사 범위에서 찾은 파일에만 발급한다

## API 규칙

- 모든 라우트는 `routeRegistry.add(spec, handler)`로만 등록한다. 등록하면 속도 제한 → 입력 검증 → 로그인 확인 → 멱등 키 → 응답 스키마 파싱이 정해진 순서로 자동 적용된다
- 같은 정의에서 API 문서(OpenAPI)가 만들어진다. 결과물은 `packages/shared/openapi/`에 커밋하며, 라우트를 바꾸고 `pnpm openapi:generate`를 안 하면 테스트가 실패한다
- 오류 응답은 항상 `{ error: { code, message, details? } }` 형식이다. 사용자 문구는 `packages/shared/src/errorMessages.ts`에 모은다 (오류 코드별 문구는 `ERROR_MESSAGES`, 검증·업무 규칙 문구는 `VALIDATION_MESSAGES`)
- 스키마에 문구를 적지 않은 입력 검증(길이·형식·범위)이 실패하면 zod의 영어 기본 문구가 아니라 `ZOD_MESSAGES`(`errorMessages.ts`)의 쉬운 한국어가 나온다. `zodErrorMessages.ts`가 서버와 웹 모두에 전역으로 적용하며, 정해 두지 않은 종류는 zod 한국어 기본 문구가 대신한다. 스키마에 직접 적은 문구는 그대로 우선한다
- 서버·웹 폼·목업이 같은 상수를 쓴다. `message:`·zod 검증·`setError`·도메인 오류 생성자에 한글 문구를 직접 쓰면 ESLint가 막으므로 문구가 필요하면 `VALIDATION_MESSAGES`에 의미 단위 상수를 추가한다 (항목 이름만 바뀌는 문구는 `required`·`selectRequired`·`tooLong` 함수 사용)
- 쓰기 요청은 `Idempotency-Key` 헤더가 필요하다. 네트워크가 끊겨 같은 요청을 다시 보내도 한 번만 처리된다
- 개발 서버(`NODE_ENV=development`)에서는 `http://localhost:3000/api/docs`에서 API 문서를 볼 수 있다

## 2단계 인증 (TOTP, 선택)

- 인증 앱(구글 OTP·Microsoft Authenticator 등)의 6자리 코드를 로그인에 더하는 **선택 기능**이다. 기본은 꺼짐이고, 켜지 않은 계정은 이전과 똑같이 아이디·비밀번호만으로 로그인한다. 문자 인증은 쓰지 않는다
- 설정 > 내 계정 > 보안의 "2단계 인증" 줄에서 켜고 끈다
  - **켜기**: `켜기`를 누르면 서버가 새 인증 키를 만들고, QR 코드(브라우저 안에서만 그림)와 직접 입력용 키를 보여 준다. 앱에 등록한 뒤 앱의 6자리 코드를 입력해야 켜진다 (확인 전에는 켜지지 않음)
  - **복구 코드**: 켜지는 순간 8개를 한 번만 보여 준다 (`XXXXX-XXXXX`). 코드마다 한 번만 쓸 수 있고, 적어 두었다고 확인해야 창을 닫을 수 있다. 서버에는 해시만 남는다. 남은 개수가 2개 이하이면 "다시 받기"를 안내하고, 다시 받으면 이전 코드는 모두 무효가 된다
  - **끄기**: 현재 비밀번호(비밀번호 로그인이 있는 계정)와 인증 코드 또는 복구 코드가 모두 맞아야 한다. 켜기·끄기는 이메일로 알린다
- 로그인: 비밀번호가 맞고 2단계 인증이 켜진 계정이면 `TOTP_REQUIRED`(401)로 응답하고, 화면이 인증 코드 칸을 열어 같은 요청에 `totpCode`를 더해 다시 보낸다. 비밀번호가 틀리면 코드 요구 없이 일반 로그인 실패이므로 코드 필요 여부가 노출되지 않는다. 코드 칸에는 복구 코드도 넣을 수 있다
- 비밀번호 재설정: 링크 확인 응답의 `requiresTotp`가 true이면 인증 코드(또는 복구 코드)를 함께 받는다. 코드가 틀려도 링크는 소모되지 않는다
- 보안 규칙
  - 코드 재사용 차단: 인증 앱 코드는 30초 구간 번호를 기록해 같은 구간(또는 이전 구간)의 코드를 다시 쓸 수 없다. 앞뒤 한 구간의 시계 오차는 허용한다
  - 시도 횟수: 틀린 코드는 비밀번호 실패와 같은 횟수(5회, 15분 잠금)에 쌓인다. 비밀번호가 맞아도 코드까지 맞기 전에는 횟수를 지우지 않아 코드를 무제한 시도할 수 없다
  - 인증 키는 서버 비밀 값 `TOTP_ENCRYPTION_KEY`로 AES-256-GCM 암호화해 저장한다 (평문 저장 없음). 이 값을 바꾸면 켜 둔 2단계 인증을 확인할 수 없으므로 정해진 뒤에는 유지한다
  - 복구·소유자 이전 링크로 다시 등록하면 2단계 인증도 해제된다 (로그인 수단을 잃은 상황의 복구이므로 새로 등록한 뒤 다시 켜게 함)
  - 소셜 로그인은 제공자(카카오·네이버·구글)의 인증을 따르므로 이 단계를 더하지 않는다
- API: `GET /me/totp`(상태), `POST /me/totp/setup`(등록 시작), `POST /me/totp/enable`(확인·켜기), `POST /me/totp/disable`(끄기), `POST /me/totp/recovery-codes`(복구 코드 다시 받기). 모두 로그인 필요

## 소셜 로그인 (카카오·네이버·구글)

**정책**

- 계정은 제공자가 준 사용자 번호로만 찾는다. 이메일이 같아도 자동으로 연결하지 않는다. 사용자 번호는 제공자마다 따로라 카카오로 연동한 계정은 구글로 로그인할 수 없다
- 연동은 아이디로 **로그인한 상태에서만** 한다. 연동되지 않은 소셜 계정으로 로그인하면 "연결된 계정이 없습니다"라고 안내하고 가입시키지 않는다
- 가입은 초대 링크로만 한다. 세 제공자 모두 가입할 수 있다. 제공자가 **인증된 이메일을 주면**(카카오·구글) 이메일 인증이 끝난 활성 계정이 되고, **주지 않으면**(네이버, 이메일 없는 계정) 이메일 없이 가입되어 바로 "이메일 등록" 화면으로 간다. 거기서 이메일을 입력하고 6자리 코드를 확인해야 서비스를 쓸 수 있다 (인증 전에는 다른 화면이 막힘)
- 소셜로만 가입한 계정은 설정의 "아이디·비밀번호 로그인"에서 **현재 비밀번호 없이** 아이디와 비밀번호를 설정할 수 있다 (소셜 로그인으로 이미 본인이 확인됨). 설정하면 소셜 계정 없이도 로그인하고, 비밀번호 변경·재설정과 이메일 변경(현재 비밀번호 확인)을 쓸 수 있다. 설정 전에는 이메일 변경이 비밀번호 확인 없이 된다. 이미 설정했거나 다른 계정이 쓰는 아이디면 거부한다
- 연동을 해제해도 로그인 수단이 하나는 남아야 한다. 비밀번호 로그인이 없는 계정은 연동이 하나뿐일 때 해제할 수 없고, 둘 이상이면 하나는 해제할 수 있다
- 한 계정에 제공자마다 하나만 연동하고, 이미 다른 계정에 연동된 소셜 계정은 연동할 수 없다

**동작 방식**

- 시작은 `POST /auth/{provider}/start`, 콜백은 `GET /auth/{provider}/callback` (`provider`는 `kakao`·`naver`·`google`). 연동은 `POST /me/social/{provider}/start`, 해제는 `DELETE /me/social/{provider}`
- 진행 중인 상태(state, 제공자, 목적, 가입 시 동의 내용, 구글의 PKCE 검증값)는 서버 비밀 값(`OAUTH_COOKIE_SECRET`)으로 암호화한 HttpOnly 쿠키에 담는다. 10분 안에, 같은 state로, 한 번만 쓸 수 있고, 다른 제공자의 콜백으로는 이어갈 수 없다
- 연동을 시작한 사용자와 돌아온 사용자가 다르면 연동하지 않는다
- 제공자는 `apps/api/src/social/provider.ts`의 인터페이스로 분리되어 있다. 카카오·구글은 arctic, 네이버는 토큰 요청에 state가 필요해서 직접 호출한다. 구글은 PKCE를 쓴다

**환경별 제공자 선택** (`chooseSocialProviders`, 제공자마다 따로 선택)

| 환경                                              | 제공자                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------- |
| `{KAKAO,NAVER,GOOGLE}_CLIENT_ID`·`_SECRET`이 있음 | 실제 제공자                                                            |
| 키가 없고 `NODE_ENV=development`                  | 가짜 제공자 (`/api/v1/dev/fake-social/{provider}/authorize`)           |
| 키가 없고 운영 등 그 외                           | 그 제공자 로그인 꺼짐 (가짜 화면 주소도 존재하지 않음, 버튼도 안 보임) |

가짜 제공자의 시연용 계정은 제공자마다 사용자 번호가 다르고, 네이버는 실제와 같이 인증된 이메일을 주지 않는다

**상용 전환 (제공자별 앱 등록 후, 쓰고 싶은 제공자만)**

1. 각 개발자 사이트에서 앱을 만든다. 카카오는 동의 항목에 이메일(`account_email`), 구글은 `openid email` 범위, 네이버는 조회 항목에 회원 이름·고유 ID를 설정한다
2. 리다이렉트 URI에 `{APP_ORIGIN}/api/v1/auth/{kakao|naver|google}/callback`을 등록한다
3. 서버의 환경 변수에 `{KAKAO,NAVER,GOOGLE}_CLIENT_ID`·`_CLIENT_SECRET`을 넣는다 (저장소에는 두지 않고 `.env.example`에 빈 값 자리만 있다)
4. 서버를 재시작하면 키를 넣은 제공자의 버튼이 실제 제공자로 연결된다. 코드 변경은 없다

## 이메일 발송과 작업 큐

- 이메일은 요청 처리 중에 직접 보내지 않고 작업 큐(PostgreSQL 기반 pg-boss)를 거친다. 발송에 실패하면 30초부터 지수적으로 늘려 5번까지 다시 시도한다
- 인증 코드 원문은 큐·DB·로그에 남기지 않는다. 작업 처리기가 발송 직전에 만들고, DB에는 서버 비밀 값으로 만든 해시만 저장한다
- 인증 코드는 6자리이고 10분간 유효하며, 틀린 시도는 코드당 5번까지다. 시도 횟수는 확인 전에 조건부로 먼저 올려, 동시에 여러 번 보내도 한도를 넘는 시도는 통과하지 못한다. 재발송은 30초 간격, 1시간에 5번까지다
- **이메일 인증 전 계정은 API도 막는다**: 인증 화면이 쓰는 요청(`GET /me`, `POST /auth/email/verify`, `/auth/email/resend`, `/me/email/change`, `/auth/logout`)만 허용하고, 나머지 로그인 필요 요청은 `403 EMAIL_NOT_VERIFIED`로 거부한다. 화면 이동(`RequireAuth`)에만 맡기지 않고 서버가 요청마다 확인한다 (`route.ts`의 `allowUnverifiedEmail`)
- 메일 HTML 본문에 들어가는 값은 모두 `escapeHtml`로 치환한다 (받는 사람·변경한 사람이 준 값이 태그·속성으로 해석되지 않게 함). 링크는 서버 설정의 웹 주소(`APP_ORIGIN`)로만 만들고 요청 헤더의 주소를 쓰지 않는다
- SMTP 연결: 접속 계정이 있는 587 같은 포트는 `requireTLS`라 TLS로 올릴 수 없으면 평문으로 보내지 않고 중단한다 (작업 큐가 재시도). 465는 처음부터 TLS, 최소 TLS 1.2. 접속 정보가 없는 로컬 수신기(Mailpit)만 평문. 연결·응답 제한 시간이 있어 응답 없는 메일 서버에 처리기가 오래 붙잡히지 않는다
- 로그: 예상 밖 오류의 로그에는 요청 주소 대신 라우트 형태(`/auth/password-reset/:token`)만 남겨 링크 토큰이 남지 않는다. 비밀번호·2단계 코드·초대 토큰·아이디·복구 코드는 마스킹 대상이다
- 로컬은 Mailpit, 운영은 `SMTP_HOST`·`SMTP_PORT`·`SMTP_USER`·`SMTP_PASSWORD`·`SMTP_FROM`만 메일 발송 서비스 값으로 바꾼다 (코드 변경 없음)

## 프로젝트

- 프로젝트 메뉴에서 프로젝트를 등록·조회·수정한다. 등록에 필요한 것은 **프로젝트명, 현장 이름, 고객, 담당자, 계약일, 시작·종료 예정일**이고 공종(여러 개)·주소·지도 링크·현장 연락처·출입 메모·메모는 선택이다. 계약 금액은 저장하지 않는다
- **프로젝트 코드는 `연도-순번`(예: 2026-012)으로 저장할 때 자동으로 붙고 수정할 수 없다.** 회사마다·연도마다 따로 세고(서울 기준 연도), 동시에 등록해도 번호가 겹치지 않으며 999를 넘으면 4자리로 이어진다
- 고객은 명부의 **고객 구분만**, 담당자는 **퇴사하지 않은 직원**만, 공종은 선택 목록의 공종만 새로 고를 수 있다. 숨기거나 퇴사해도 이미 연결된 값은 그대로 유지된다. 목록에 없으면 폼에서 고객·공종을 **그 자리에서 추가**할 수 있다
- 상태는 `예정`으로 시작하고, 프로젝트 카드의 "상태" 패널에서 바꾼다
  - 허용된 전환: 예정 → 진행·취소, 진행 → 중단·완료·취소, 중단 → 진행(재개)·취소, 완료 → 보증 중·종료, 보증 중 → 종료, 종료 → 보증 중(재오픈). 취소에서는 더 바꿀 수 없다. 완료 → 보증 중은 프로젝트 요약 확인과 보증 기간 1개월 이상, 완료 → 종료는 보증 기간 0개월일 때만, 재오픈과 보증 종료 예정일 전의 조기 종료는 사유가 필요하고 종료는 임시 저장 일지가 남아 있으면 막힌다 (접수·처리 중인 보수 요청이 남아 있으면 종료할 수 없다)
  - 전환마다 **그 일이 실제로 일어난 날**(기본 오늘, 오늘 이후·이전 변경일보다 빠른 날은 불가)을 입력하고, **중단·취소는 사유가 필수**다. 처음 시작하면 실제 시작일, 완료하면 실제 완료일이 기록되며 재개해도 시작일은 바뀌지 않는다
  - 모든 전환은 날짜·사유·변경자·기록 시각과 함께 **상태 변경 이력**으로 남고(추가만 가능, 수정·삭제 불가) 카드에서 최근순으로 볼 수 있다
  - 상태별 수정 제한: 종료·취소는 기본정보를 수정할 수 없고(조회만), 보증 중은 담당자·메모만 수정할 수 있다. 진행·중단·완료는 계속 수정할 수 있다
  - 두 번 눌러도(동시 요청 포함) 전환과 이력은 한 번만 생긴다
- 목록은 상태·고객·담당자·공종·기간(겹치는 프로젝트)·검색(이름·코드·현장)으로 거르고 최근 등록순·종료 예정일순·이름순으로 정렬한다. 현장 연락처·출입 메모·계약일·메모는 카드에서만 보인다
- 삭제는 없다 (취소·종료는 상태로 표현)
- **홈 대시보드·알림**: 로그인 후 홈에서 알림, 오늘의 투입(프로젝트별 일지 입력 여부), 위험 프로젝트(공수 소진·일정 경고), 진행 프로젝트, 이번 주 인력(겹침·비는 사람), 할 일(임시 저장 일지·방치된 메모)을 한눈에 본다. 알림은 일지 미입력, 메모 3일 방치, 소진율 80%·100% 도달, 진행률 대비 소진 과다, 종료 예정일 경과, 같은 날 중복 투입, 협의 중 변경 작업 7일 경과에 더해, 보증 종료 60일 전·미처리 보수 요청(접수 3일 경과)·보증서 만료 30일 전·직원 서류·자격 만료 30일 전·지난달 월 공수 미확정까지 12종이며 누르면 해당 화면으로 이동한다. 홈에는 "보증 종료 임박"(보증 종료 예정일이 가까운 프로젝트와 처리하지 않은 보수 요청 건수)과 "만료 임박"(보증서·직원 서류) 위젯, 할 일의 월 공수 확정 링크가 추가됐다. 설정 > 알림 설정에서 종류별로 켜고 끈다(꺼도 현황은 그대로). 알림은 저장하지 않고 열 때마다 기록으로 계산한다
- **상태 전환 안내·프로젝트 요약**: 완료 처리 확인 단계에 임시 저장 일지, 진행률 100% 여부, 남은 자재, 협의 중 변경·추가 작업이 "확인할 것"으로 나오고(막지는 않음), 중단 뒤 재개할 때 종료 예정일이 지났으면 기간 연장을 안내한다. 프로젝트 카드의 "프로젝트 요약"은 기본정보·투입 공수(인원별·작업 구분별)·쓴 자재(품명·규격·쓴 양)·변경·추가 작업·사후 작업·고른 사진·작업자료를 지금 기록으로 한 장에 모아 인쇄·PDF로 저장하게 한다. 금액은 싣지 않고 민감 문서는 목록에서 뺀다. 사진은 사진 상세의 `준공 요약에 넣기`로 12장까지 고르고(고르지 않으면 작업 후 사진 최근 8장), 문서는 안전·검사·계약·공문 분류에서 문서 상세의 `준공 요약에 넣기`로 고른다. 보증은 프로젝트를 완료한 뒤에 설정한다
- **보증**: 완료한 프로젝트는 프로젝트 카드의 "보증"(`/projects/:id/warranty`)에서 보증 기간(개월, 0이면 보증 없음)과 시작 기준(실제 완료일·고객 검수일·직접 지정)을 정하면 종료 예정일이 시작일 + 기간으로 계산된다. 설정이 없으면 기본 12개월로 계산한 값을 보여 주고 보증 중이 될 때 자동 저장된다. 이미 설정이 있거나 종료 예정일을 직접 바꿀 때(연장 등)는 사유가 필요하고 모든 변경이 이력에 남는다. 보증서는 문서함에 올린 문서에 만료일·발급처를 붙여 등록한다. 완료·보증 중에만 바꿀 수 있고 종료된 프로젝트는 조회만 가능하다.
- **월 공수 확정·월 공수표**: 직원 목록의 "월 공수표"(`/monthly-hours`)에서 한 달의 프로젝트·직원별 공수(MD·MM)와 직원별 합계를 보고, 임시 저장된 일지를 정리한 뒤 월 공수를 확정한다(선택 기능). 확정하면 그달의 작업일지는 저장할 수 없고 그 시점의 하루 기준시간·월 기준일수가 고정되며, 정정이 필요하면 사유와 함께 재오픈한다(이력에 남음). 임시 저장 일지가 남아 있으면 확인해야 확정된다. 급여·정산 담당에게 전달하도록 엑셀로 내보낼 수 있고 내보낸 기록이 남는다. 화면은 직원 × 프로젝트 표(행 직원·열 프로젝트, 칸은 MD, 끝 열에 MD·MM 나란히, 아래 합계 행)이고 `직원별 / 프로젝트별`로 행을 바꿔 본다
- **직원 서류·자격**: 직원 카드의 "서류·자격"에서 자격증·안전교육 이수증·건강검진 서류를 종류(설정 > 목록 관리의 "자격 종류", 처음에는 프리셋)·취득일·만료일·메모와 함께 등록하고 이미지·PDF 파일을 붙인다. 만료일이 없으면 만료 없는 서류이고, 목록은 만료가 빠른 순으로 유효·만료 임박(30일 이내)·만료 상태가 보인다. 갱신하면 만료일을 바꾸고, 삭제해도 기록은 남는다. 서류 파일은 서류 화면으로만 열 수 있고 열 때마다 열람 기록이 남는다. 프로젝트 카드의 "필요 자격"을 정해 두면 투입할 때 서류가 없거나(자격 없음) 투입 시작 전에 만료됐거나(자격 만료) 투입 기간 중에 만료되는(투입 중 만료) 직원에게 경고가 붙는다(투입은 막지 않음).
- **활동 기록**: 설정 > 활동 기록(`/settings/records`)에서 데이터를 바꾼 일(작업 내역 저장·수정, 자재 기록·사진·문서 삭제, 프로젝트 정보·상태 변경, 직원 정보 수정, 단가 변경), 내보내기, 월 공수 확정·재오픈, 민감 문서·직원 서류 열람을 최근순으로 보고 종류 칩(저장·수정·삭제·내보내기·확정·열람)·프로젝트·날짜로 거른다. 행의 `바뀐 내용`을 펼치면 바꾸기 전·후가 보이고(개인정보는 값 없이 바뀌었다는 것만), 인건비·단가 조회는 이 서비스가 볼 권한이 있는 관리자만 쓰므로 더 남기지 않는다. 기록은 라우트가 성공한 뒤 남기며(기록 실패는 처리 결과를 바꾸지 않고 오류 로그로 알림) 조회만 가능하고 수정·삭제할 수 없으며, 다른 회사의 기록은 보이지 않는다
- **보수 요청**: 보증 중인 프로젝트는 프로젝트 카드의 "보수 요청"(`/projects/:id/repairs`)에서 고객이 요청한 하자 보수를 접수(접수일·요청자·위치·내용)하고 처리 중·보류·완료로 바꾸며 이력을 남긴다. 보류와 완료 되돌리기는 사유가 필요하고 완료된 건은 고칠 수 없다. 보수 작업은 작업일지·자재 기록에서 "사후 작업"으로 표시한 뒤 보수 요청에 연결해 건별로 쓴 공수·자재를 본다(프로젝트 전체의 사후 작업 합계도 같은 화면). 접수·처리 중인 보수 요청이 남아 있으면 보증 종료가 막힌다.
- **변경·추가 작업**: 프로젝트 카드의 "변경·추가 작업"에서 계약 후 범위가 바뀌거나 늘어나는 일을 누가 언제 무엇을 요청했는지 기록한다(금액은 기록하지 않음). 처음에는 "협의 중"이고 합의됨·철회로 바꾸면 날짜와 메모가 이력으로 남는다(철회는 사유 필수). 협의 중일 때만 내용을 고칠 수 있고, 합의·철회된 기록은 그대로 보존된다. 화면은 번호·내용·요청자·요청일·상태·증빙 수 표이고 번호를 누르면 상세 창이 열린다. 대화 캡처·합의서·공문은 상세 창의 `증빙 올리기`로 사진·PDF를 바로 올리면(`POST /change-works/{id}/evidence`) 문서함에 **계약·공문** 문서로 만들어 이 기록에 한 번에 연결하고(같은 파일로 다시 불러도 하나만 남음, 기록할 수 없는 프로젝트 상태면 문서를 만들기 전에 막음), 문서함에 이미 있는 문서를 연결할 수도 있다. 증빙 연결을 풀 때는 확인 창을 거친다. 일지·자재 기록에서 "변경·추가 작업"으로 표시한 공수·자재는 같은 화면에서 합계로 본다. 예정·진행·중단 프로젝트에 기록할 수 있고 완료 프로젝트는 확인 후, 보증 중·종료·취소는 조회만 가능하다.
- **직원 단가·인건비**: 직원 카드의 "단가"에서 일급·시급·월급·연봉 중 하나와 적용 시작일을 입력한다. 단가를 바꾸면 이력으로 쌓이고, 바뀐 날 이후 근무분부터 새 단가로 계산되며 그 전 날짜는 기존 단가 그대로다. 프로젝트 카드의 "인건비 (최소 추정)"에 저장된 일지의 공수 × 근무일 단가와 계획 공수 기준 예상, 직원별 내역이 나온다. 4대보험·수당·퇴직금·세금은 포함하지 않으며 단가가 없는 직원의 공수는 합계에서 빠지므로 실제 인건비는 이보다 크거나 같다. 단가·인건비는 민감 정보라 조회와 변경이 기록으로 남는다.
- **진행 현황**: 프로젝트 카드의 "진행 현황"에서 진행률(%)을 기준일과 함께 기록한다(예정·진행·중단 상태에서만, 고치지 않고 새로 기록). 공수 소진율(투입 공수 ÷ 계획 공수), 현재 속도로 끝내려면 필요한 공수를 보여 주고, 소진율 80%·100% 도달, 진행률보다 공수가 빨리 소진됨, 종료 예정일 경과, 진행률이 일정보다 뒤처짐을 경고한다.
- **인력 배치**: 직원 목록·홈의 "인력 배치 보기"(`/staffing`)에서 사람 행 × 날짜 열 타임라인(1주·2주·월)으로 본다. 저장된 작업 내역에 그 사람이 들어간 날만 막대로 나오고(같은 프로젝트에 이어서 일한 날은 막대 하나, 안에 프로젝트 이름과 그날 시간), 같은 날 두 프로젝트에서 일하면 막대가 위아래로 쌓이며 빨간 테두리로 겹침을 알린다. 위 요약 줄에 일한 사람·일한 기록이 없는 사람·겹침 건수가 나오고 직종·겹침으로 거를 수 있다. 막대를 누르면 그날 하루 기록, 빈 칸을 누르면 프로젝트를 골라 그날 하루 기록으로 간다. 미리 정해 두는 투입 계획은 두지 않는다 (`GET /staffing-calendar`의 `workDays`)

## 작업일지 (API)

- 프로젝트 × 날짜마다 일지 한 건을 `PUT /projects/{id}/work-logs/{날짜}`로 임시 저장·저장한다. 공통 내용(작업 내용·구역·특이사항·변경 작업·사후 작업 표시)은 일지에, **직원별·작업 구분별 공수(분)**는 항목으로 붙는다. 같은 일지에 같은 직원·작업 구분 조합은 한 번만이고, 같은 직원이 작업 구분을 나눠 입력할 수 있다 (예: 가공 4시간 + 설치 4시간)
- **임시 저장**은 비어 있어도 되고 집계에서 제외된다. **저장**하려면 작업 내용과 공수 한 건 이상이 필요하며, 저장한 일지는 임시 저장으로 되돌릴 수 없다 (공수 집계에는 저장된 일지만 반영)
- **낙관적 잠금**: 이미 있는 일지를 고칠 때는 화면이 본 `expectedVersion`을 보내야 하고, 다르면 `409 CONFLICT`로 거부한다 (두 화면이 동시에 고쳐도 한쪽이 다른 쪽을 덮어쓰지 않음). 저장할 때마다 버전이 오른다
- **수정 이력**: 저장된 일지를 고치면 고치기 전 값(내용·구역·공수 항목 포함)이 이력으로 남고(`GET .../revisions`, 최근순, 추가만 가능), 임시 저장 중의 수정은 기록하지 않는다
- 작업 일자는 **프로젝트 예정 기간 안**이고 **오늘 이후는 불가**하다. 작업일에서 3일이 지나 처음 저장하면 "지연 입력"으로 **표시만** 한다 (소급 입력은 허용)
- 프로젝트 상태별 입력: 진행은 가능, 중단·완료는 확인(`confirmStatus`) 후 가능, 보증 중은 사후 작업 표시가 있을 때만, 예정·종료·취소는 불가
- **투입 등록이 없는 직원**을 넣고 저장하면 `addMissingAssignments` 확인을 요구하고, 확인하면 그날 하루짜리 투입을 자동으로 추가한다 (퇴사 직원은 경고만, 임시 저장은 확인하지 않음)
- 경고(막지 않음): 같은 직원의 하루 합계 공수가 **하루 기준시간의 1.5배를 넘으면**(예: 프로젝트 A 1.0 + B 1.0 = 2.0, 저장된 다른 프로젝트 일지 포함) 경고, 휴직·퇴사 직원 경고
- 일지는 삭제하지 않는다

### 일지 입력 화면

- 메뉴 "일지"(`/work-logs`)에서 프로젝트와 날짜를 고르면 그날 투입된 직원이 행으로 채워진다. 공수는 회사 기준(MD 또는 시간)으로 입력하고, 반일·하루·연장 버튼과 작업 구분 일괄 지정으로 한 번에 정한다
- "어제와 동일"(가장 최근 일지 복사), 같은 내용을 다른 날짜에도 저장, 투입 없는 직원 추가 시 투입 자동 추가 확인, 충돌(409) 안내, 수정 이력 보기를 지원한다

### 공수 집계

- 프로젝트 카드의 "공수 집계"에서 직원별(작업한 날·공수·MM·소진율)·작업 구분별·기간별(주·월) 공수를 본다. 직원 카드의 "투입 이력"에서는 프로젝트별 투입 기간·일수·공수와 이번 달·올해 공수를 본다
- **저장된 일지만** 집계하고 임시 저장 일지는 건수만 알린다. 서버는 분 단위만 돌려주고 MD·MM·소진율은 화면이 회사 설정으로 환산한다 (`GET /projects/{id}/work-summary`, `GET /projects/{id}/work-summary/employees/{employeeId}`, `GET /employees/{id}/work-history`). 인원 탭에서 사람을 누르면 그 사람이 일한 날만 달력·목록으로 보인다

## 파일 업로드 (API)

- 사진·작업자료는 브라우저가 **서버가 발급한 짧은 만료의 주소로 객체 저장소에 직접 올린다** (서버 메모리·대역폭 절약). 순서: `POST /projects/{projectId}/files`(이름·용도·형식·크기를 신청) → 응답의 `upload.url`로 `PUT`(응답의 `headers`를 그대로 실음) → `POST /files/{id}/complete` → `GET /files/{id}`로 `READY`가 될 때까지 확인
- **신청 단계**에서 허용 목록(JPEG·PNG·WebP, 자료는 PDF·docx·xlsx·pptx)·확장자 일치·크기(사진 20MB, 자료 50MB)·회사 저장 용량 한도(기본 5GB)를 검사한다. 주소에는 형식과 크기가 서명돼 있어 신청과 다르게 올리면 저장소가 거부한다
- **올라온 뒤** 작업 큐가 크기를 다시 확인하고 **확장자·선언한 형식이 아니라 파일 내용(file-type)** 으로 형식을 판별한다. 위조(실행 파일을 `.jpg`로 등)나 열 수 없는 이미지는 `REJECTED`(사유 포함)로 기록하고 저장소에서도 지운다. 통과하면 원본의 SHA-256을 기록하고 이미지는 480px WebP 썸네일(위치 정보 등 메타데이터 제거)을 만든다. 원본의 EXIF는 증빙을 위해 보존한다
- 내려받기 주소(`GET /files/{id}/url`)는 **회사 범위에서 찾은 검사 통과 파일에만** 5분 만료로 발급한다. 저장소는 공개하지 않으며 객체 키에 회사·프로젝트가 들어간다
- API 응답에는 `X-Content-Type-Options: nosniff`·`X-Frame-Options: DENY`·`Referrer-Policy: no-referrer`를 붙인다(`securityHeaders`). 웹 쪽 CSP·HSTS는 배포 단계에서 정적 파일을 내려주는 쪽(Caddy)의 응답 헤더로 설정한다. CSP 값은 `scripts/csp-header.mjs`가 만든다 (인라인 스크립트 없음, 스크립트는 같은 출처 파일만 실행)
- 로컬 저장소는 RustFS이고 API가 시작할 때 버킷이 없으면 만든다 (운영은 버킷을 미리 준비). HEIC는 지원하지 않으므로 앱이 올리기 전에 JPEG로 변환한다

### 사진 (API)

- 파일을 올린 뒤(`/files` 흐름) `POST /projects/{projectId}/photos`로 사진 기록을 붙인다: 구분(작업 전·작업 중·작업 후·하자·보수·자재·안전·기타), 구역(선택), 촬영일시(비우면 등록 시각), 작업일(비우면 서울 기준 촬영일), 설명(선택). **같은 파일을 다시 등록해도 기존 사진을 돌려주므로** 네트워크가 끊겨 다시 보내도 중복되지 않는다. 검사 중인 파일도 등록되고 썸네일 주소는 검사가 끝나면 목록에 나온다
- 사진첩(`GET /projects/{projectId}/photos`)은 촬영일시 최근순이며 구분·구역·작업일로 거르고 `nextCursor`로 이어서 읽는다 (사진이 늘어나도 빠지거나 겹치지 않음). 작업 전·후 비교는 같은 구역의 작업 전/작업 후 사진을 화면이 짝짓는다
- 대표 사진은 프로젝트마다 한 장이다 (`PATCH /photos/{id}`의 `isCover`, 새로 지정하면 기존 대표는 해제). 삭제는 **소프트 삭제**라 파일·기록은 남는다

### 사진첩 (화면)

- 프로젝트 카드의 "사진첩"에서 **구분(작업 전·중·후·하자·자재·안전·기타)과 구역을 정한 뒤 사진을 여러 장 한꺼번에** 고른다 (모바일은 카메라 또는 앨범). 올리기 전에 브라우저가 JPEG로 변환·압축(긴 변 2,000px)하며, 이때 위치 정보(EXIF)는 빠진다
- **업로드 대기열**: 고른 즉시 목록에 보이고 한 장씩 순서대로 올린다. 연결이 끊기면 "연결을 기다리는 중"으로 두었다가 돌아오면 자동으로 이어 올리고, 일시 오류는 간격을 늘려 다시 시도한다. 앱을 닫아도 대기열이 IndexedDB에 남아 다시 열면 끊긴 단계부터 이어서 올린다. 용량 초과처럼 다시 해도 안 되는 경우는 사유와 함께 멈추고 "다시 시도"·"취소"를 고른다
- 사진첩은 **전체**(구분으로 거르기, 더 보기)와 **전후 비교**(같은 구역의 작업 전·후를 나란히, 한쪽이 없으면 아직 안 찍었다고 표시)를 지원한다. 사진을 누르면 원본 보기, 구분·구역·설명 수정, 대표 사진 지정, 삭제(한 번 더 확인)가 가능하다

## 메모함·프로젝트 메모

- 정해진 양식에 들어가지 않는 내용(통화, 현장 지시, 이슈, 해야 할 일)을 **한 줄만 적어도** 저장한다. 프로젝트를 정하지 않으면 **메모함**에 들어가고, 나중에 프로젝트에 연결하거나(`PATCH`의 `projectId`) 삭제한다. 프로젝트에 붙은 메모는 그 프로젝트의 **메모 노트**에 날짜별로 쌓인다
- 태그는 협의·지시·이슈·할 일·기타다. **"할 일" 메모만 완료 표시**(완료 시각 기록)를 할 수 있고, 다른 태그로 바꾸면 완료 표시가 사라진다. 끝내지 않은 할 일 건수와 정리 안 된 메모함 건수는 `GET /memos/summary`로 얻는다
- 목록은 날짜 최근순 커서 방식이며 태그·완료 여부로 거른다. 삭제는 소프트 삭제다

### 화면

- **빠른 추가**: 어느 화면에서든 하단 "추가" 버튼 → 메모 / 사진 / 오늘 일지. 프로젝트 화면에서는 그 프로젝트에 바로 연결하고, 그 밖에서는 메모를 **메모함**에 저장한다. 홈의 메모함 카드에 정리 안 된 메모와 끝내지 않은 할 일 건수가 보인다
- **메모함**(`/inbox`): 먼저 적어 둔 메모를 날짜별로 보고 프로젝트에 연결(또는 삭제)한다. **프로젝트 메모 노트**(`/projects/:id/memos`)는 프로젝트 카드에서 들어가며 태그·"끝내지 않은 할 일만"으로 거르고 할 일은 체크해서 완료한다
- 쓰는 중인 메모는 기기에 임시 저장돼 새로고침·앱 종료 뒤에도 남고, 저장에 실패해도 글을 지우지 않는다

## 지출·수입 기록

- 프로젝트에서 **나간 돈(부자재·장비·운반·식대 등)과 가끔 생기는 수입(고철 판매·현장 지원 등)**만 적는다. 계약 금액·청구·입금 관리, 회계·세금·급여는 다루지 않는다
- 한 건: 날짜 · 구분(지출/수입) · 분류 · 금액(원 단위 정수) · 거래처 · 내용 · 증빙 문서(문서함) · 추가 공사 연결. 분류는 설정 > 목록 관리의 `지출 분류`·`수입 분류`에서 회사가 바꾼다. 지우면 소프트 삭제하고 활동 기록에 남는다
- 프로젝트 **비용·자재** 메뉴 첫 구역: 합계 줄(지출 · 인건비 추정 · 수입)과 내역 표, 구분·분류·기간 필터. 하루 기록의 `이 날 비용`에서 그날 비용을 바로 추가하고, 현황에는 합계만 보인다
- API: `/projects/{projectId}/ledger-entries`(등록·목록), `/projects/{projectId}/ledger-summary`(합계), `/ledger-entries/{id}`(수정·삭제)

## 사용 자재

- 프로젝트에 **어떤 자재가 언제 얼마나 들어오고 쓰이고 나갔는지**만 기록한다. 단가·구매·발주·재고는 다루지 않는다
- **자재 목록**: 이름·규격·단위·분류. 입력하다가 목록에 없으면 **이름과 단위만으로 바로 추가**한다. 같은 이름도 규격이 다르면 별도 자재(아연도강판 0.8T / 1.0T)이고, 최근 기록한 자재가 목록 위에 온다. 기록이 있는 자재는 단위를 바꿀 수 없고, 쓰지 않는 자재는 숨긴다
- **기록**: 반입·사용·반출·폐기 + 수량(소수 셋째 자리까지) + 작업 구분·구역·반입처·변경/사후 작업 표시·메모. 여러 자재를 한꺼번에(`/batch`, 최대 50건, 전부 성공 또는 전부 취소) 입력하고, 그날 일지 화면에서 읽을 수 있게 날짜로 거른다. 삭제는 소프트 삭제
- **잔량** = 반입 − 사용 − 반출 − 폐기 (예: 반입 100, 사용 72, 반출 10, 폐기 3 → 15). 마이너스면 반입 기록 누락일 수 있어 경고만 한다. 변경·추가 작업과 사후 작업에 쓴 양도 따로 집계한다

### 화면

- **일지 안 입력**: 작업일지 화면 아래 "자재"에서 별도 메뉴 없이 입력한다. **최근 쓴 자재**를 눌러 행을 추가하고 큰 숫자로 수량만 적은 뒤 여러 자재를 한꺼번에 저장한다. 목록에 없으면 **새 자재**로 이름·단위만 적어 바로 만든다. **어제와 동일**은 직전 기록일의 사용 자재를 같은 수량으로 채운다. 작업 구분·구역·변경/사후 작업 표시는 이번에 저장하는 전체에 붙인다
- **프로젝트 자재 현황**(프로젝트 카드 → "자재 현황"): 자재별 반입·사용·반출·폐기·잔량(마이너스면 경고)과 날짜별 기록. 기록의 수량 수정·삭제도 여기서 할 수 있다

## 작업자료 문서함

- 도면·작업지시서·계약서처럼 **개정되는 문서**를 프로젝트별로 모은다. 파일을 올린 뒤(`/files` 흐름, 용도 문서) `POST /projects/{projectId}/documents`로 문서를 만들고, 개정되면 `POST /documents/{id}/versions`로 **새 버전**을 올린다. 최신본이 기본으로 보이고 **이전본은 그대로 보존**되며(덮어쓰지 않음) 개정일·사유가 붙는다
- 분류는 도면·작업지시서, 계약·공문, 안전·검사, 견적·정산, 기타 5종. **계약·공문은 기본적으로 민감 자료**이고 문서마다 민감 표시를 바꿀 수 있다. 자주 보는 문서는 프로젝트마다 10개까지 **고정**해 먼저 보인다
- **민감 자료는 열람·내려받기를 기록**한다: 열람 주소를 발급할 때 감사 기록을 먼저 남기고(기록 없이는 열 수 없음), `GET /documents/{id}/access-logs`로 누가 몇 번째 버전을 언제 열었는지 본다. 감사 기록은 **수정·삭제할 수 없고** 문서를 지워도 남는다. 문서 파일은 일반 파일 주소(`/files/{id}/url`)로는 열리지 않고 문서 API로만 연다
- 삭제는 소프트 삭제(파일·버전·열람 기록 보존)다

### 화면

- 프로젝트 카드의 **문서함**에서 파일을 올리고(진행률 표시), 분류별로 보고, 이름으로 찾는다. 개정된 파일은 문서의 **버전·기록**에서 새 버전으로 올린다(최신본이 기본, 이전본도 열 수 있음). 자주 쓰는 도면은 **고정**하면 프로젝트 카드 위쪽에서 바로 열린다
- 민감 자료는 열기·내려받기 전에 **기록이 남는다는 확인**을 받고, 문서 상세의 **열람 기록**에서 누가 언제 어느 버전을 열었는지 본다

## 작성 중 입력 임시 저장

- 통신이 불안정한 현장에서도 입력이 유실되지 않도록, **저장 버튼을 누르기 전의 입력을 이 기기에 자동으로 보관**한다. 작업일지 입력(직원 공수·작업 내용 등)과 일지 안 자재 입력, 메모 입력이 대상이며 앱을 닫거나 연결이 끊겨도 다시 열면 그대로 이어서 쓸 수 있다. 서버의 "임시 저장" 일지(집계에서 제외되는 저장 상태)와는 별개다
- 다시 열면 **복구했다는 안내**와 함께 입력이 채워지고 "복구한 내용 버리기"로 처음 상태로 돌릴 수 있다. 그사이 서버의 일지가 바뀌었으면(예: 다른 기기에서 저장) 자동으로 덮지 않고 "저장해 둔 내용 불러오기 / 버리기"를 묻는다
- 홈의 **이어서 작성**에서 저장하지 않고 닫은 일지·자재를 바로 열 수 있다. 서버에 저장하면 초안은 지워지고, 30일이 지난 초안과 로그아웃 시 이 기기의 초안은 삭제된다

## 통합 검색

- 홈의 검색창(또는 `/search`)에서 **프로젝트·직원·메모·자료(문서 이름)·일지**를 한 번에 찾는다. 대소문자를 가리지 않는 부분 일치이고 결과는 종류별로 나뉘며, 메모·일지는 검색어 주변 글이 함께 보인다. 종류마다 5개까지 보이고 더 있으면 검색어를 좁히도록 안내한다
- 결과를 누르면 해당 화면으로 이동한다: 프로젝트·직원 카드, 프로젝트 메모 노트(프로젝트 없는 메모는 메모함), 문서함의 문서 상세, 그 날짜의 일지
- 프로젝트 카드의 **프로젝트 안에서 찾기**는 그 프로젝트의 메모·자료·일지만 찾는다
- 찾을 수 있는 것은 **로그인한 회사의 데이터뿐**이다. 직원의 연락처·생년월일·메모는 목록에서 가리는 정보라 검색 대상이 아니고, 지운 메모·문서도 나오지 않는다. 민감 문서는 이름만 찾을 수 있고 열려면 기존처럼 열람 기록 확인을 거친다

## 작업일보 출력·엑셀

- 프로젝트 카드의 **작업일보 출력**(또는 일지 화면의 "작업일보 보기")에서 하루치 **작업 내용·투입 인원과 공수·자재·사진**을 한 장으로 본다 (고객 제출용). 일지가 없는 날도 자재·사진이 있으면 만들어지고, 검사에서 거부된 사진은 싣지 않는다. 금액은 다루지 않는다
- **인쇄·PDF로 저장**: 브라우저의 인쇄 창을 열고 "PDF로 저장"을 고른다 (A4 세로, 메뉴는 인쇄되지 않음). 한글 글꼴은 기기에 있는 것이 PDF에 포함된다. 사진이 모두 불러와진 뒤에 인쇄 창이 열린다
- **엑셀로 내보내기**: 기간(최대 93일)을 정하면 요약·작업일보·공수·자재 시트가 담긴 엑셀을 내려받는다. 공수는 회사 설정(MD 또는 시간)대로 환산된다. **내보내기는 한 번 더 확인하고 누가 어느 기간을 내보냈는지 기록으로 남는다**

## 투입

- 프로젝트 카드의 "투입"에서 직원을 프로젝트 **예정 기간 안**의 일정 기간에 배정한다. 선택 항목은 **계획 공수**이고, 회사의 공수 입력 방식(비율·시간)에 맞춰 MD나 시간으로 입력하면 분으로 저장된다 (보여 줄 때는 회사 기준시간으로 MD·시간으로 환산)
- **같은 날 다른 프로젝트에 겹쳐 배정하면 막지 않고 경고**한다 (겹치는 구간과 프로젝트를 표시). 휴직·퇴사 직원도 경고한다. 취소된 프로젝트·취소한 투입은 겹침으로 보지 않는다
- 같은 프로젝트에 같은 직원을 겹치는 기간으로 두 번 투입할 수는 없다 (기존 투입의 기간을 고친다). 퇴사한 직원은 새로 투입할 수 없다
- 프로젝트 상태별 허용: 예정·진행은 가능, **중단은 "확인" 체크 후** 가능, 완료·보증 중·종료·취소는 불가 (조회는 가능)
- 투입은 **삭제하지 않고 취소 표시**만 남긴다 (이후 작업일지가 참조해도 기록이 보존됨)
- 프로젝트 **예정 기간을 바꾸면 이력**(바꾸기 전·후 기간, 사유, 변경자)이 남는다. 시작한 프로젝트는 **사유가 필수**이고, 취소하지 않은 투입이 새 기간 밖으로 나가면 거부한다 (먼저 투입 기간을 조정·취소). 투입 등록과 기간 변경이 동시에 와도 프로젝트 행 잠금으로 어긋나지 않는다

## 직원

- 직원 메뉴에서 **간편 등록**(이름만으로도 가능, 직종은 선택)과 목록·검색·필터(상태, 직종)를 쓰고, 직원을 누르면 **직원 카드**에서 직책·직종·구분·입사일·생년월일·연락처·메모를 고친다
- 직원 화면은 `직원 목록 | 단가표` 탭이다. 목록은 이름·직책·직종·구분·**현재 단가**·상태·입사일 표(단가 없는 재직 직원은 "단가 없음")와 한 줄 도구 줄(이름 검색·상태·직종)이고, `간편 등록`은 머리 버튼의 창이다. **단가표** 탭은 직원별 현재 단가·적용 시작일·이전 단가를 한 표로 보고 바로 `단가 변경`(창)을 한다 (`GET /pay-rates`)
- **직원 카드**는 머리에 상태·직종·현재 단가·이번 달 공수 수치 줄, 탭 `개요 · 투입 이력 · 단가 · 서류·자격 · 기본정보`(주소의 `?tab=`)이다. 단가 탭은 현재 단가(시급·월급·연봉제는 일 환산)와 변경 이력 타임라인, `단가 변경`은 창. 서류·자격은 `서류 등록` 창. 직원 서류 만료 알림은 서류·자격 탭으로 바로 이동한다
- **생년월일·연락처·메모는 목록에 나오지 않고 카드에서만** 보인다 (목록 API에도 싣지 않음). 주민등록번호·계좌번호는 저장하지 않는다 (급여는 단가표만 기록: 아래 "직원 단가·인건비")
- 상태는 재직·휴직·퇴사다. **퇴사**하면 퇴사일이 오늘(서울 기준)로 기록되고, 같은 카드를 **재입사**로 다시 재직으로 돌린다 (퇴사일은 지워짐). 과거 투입·작업 기록은 그대로 남는다
- 삭제 기능은 없다 (퇴사 처리로 표현). 회사당 500명까지 등록할 수 있다
- 직종·직원 구분은 위의 선택 목록 항목을 `id`로 가리킨다 (같은 회사의 해당 종류만 고를 수 있고, 숨긴 항목은 새로 고를 수 없음)

## 명부 (고객·협력업체·자재 공급처)

- 명부 메뉴에서 **고객(발주처·원청), 협력업체(타 공종 팀·외주), 자재 공급처**를 관리한다. 구분과 상호만으로 등록할 수 있고, 담당자·연락처·메모는 카드에서 나중에 채운다. 금액·거래 내역은 다루지 않는다
- 목록에는 상호와 담당자 이름만 보이고 **연락처·메모는 카드에서만** 보인다 (목록 API에도 싣지 않음). 카드에서는 전화 걸기 링크를 쓸 수 있다
- 같은 구분 안에서 상호가 같으면(앞뒤·연속 공백, 대소문자 차이 무시) 중복이다. 구분이 다르면 같은 상호를 쓸 수 있고, 구분은 등록한 뒤 바꿀 수 없다
- 삭제는 없고 **숨기기만** 한다 (프로젝트·자재 기록에 쓰인 상호가 사라지지 않게). 숨긴 업체는 "숨긴 업체도 보기"로 다시 볼 수 있다. 회사당 1000곳까지다

## 선택 목록 관리

- 설정 > 목록 관리에서 **직종·작업 구분·공종·직원 구분**을 회사가 정한다. 처음 열면 프리셋(`packages/shared/src/optionPresets.ts`)이 채워지고, 이후 추가·이름 변경·순서 변경·숨기기를 한다
- **삭제는 없고 숨기기만 한다.** 나중에 직원·일지가 이 이름을 쓰게 되므로, 쓰지 않는 항목은 숨겨도 기록에 남은 이름은 그대로 보인다
- 같은 종류 안에서 공백·대소문자만 다른 이름은 중복으로 본다. 종류마다 100개, 이름은 30자까지다

## 공개 시연 환경 (Test Company)

실제 환경에서 사람들이 둘러볼 수 있게 가상 데이터만 담은 공용 회사를 둔다. 회사 이름은 `Test Company`, 관리자는 `Tester`(이메일 인증을 마친 상태)이고 개발용 샘플(판금 회사)을 옮겨 담는다. 프로젝트 5건이 진행·예정·중단·완료·종료를 모두 보여 주고 직원·명부·투입·작업 내역·변경 작업·보증·보수·직원 서류·단가가 들어 있다. 연락처는 쓰이지 않는 0000 대역이고 이메일은 시연 계정 하나뿐이라 내보내기를 해도 문제가 없다

- 켜기: 서버 `deploy/.env`의 `PUBLIC_DEMO_ENABLED=true`. 로그인 화면에 시연 안내(가상 데이터, 매일 새벽 초기화)와 아이디·비밀번호가 보이고 "이 계정으로 채우기"로 입력 칸을 채운다. 끄면(기본값 false) 안내가 사라지고 `demo-reset`도 거부한다
- 만들기·되돌리기: `pnpm operator legal-register`로 약관을 먼저 등록한 뒤 `pnpm operator demo-reset`. 시연 회사의 업무 데이터·업로드 파일(R2)·로그인 기록을 지우고 샘플을 다시 입력한다 (회사 이름·계정·비밀번호·이메일도 원래대로). 다른 회사는 건드리지 않고, 동시에 두 번 실행하면 나중 것이 거부된다. 서버 크론이 매일 04:30에 실행한다 (`ops/crontab.example`)
- 샘플 날짜: 초기화할 때마다 모든 날짜를 7의 배수 일수만큼 옮겨 가장 최근 작업 일지가 오늘(한국 시간) 이전 일주일 안에 오게 한다. 요일 배치와 날짜 간격은 그대로이고 생년월일은 옮기지 않는다 (`buildPublicDemoDataset`)
- 끄기: `PUBLIC_DEMO_ENABLED=false`로 바꾸고 크론 줄을 지운 뒤 `pnpm operator demo-remove`. 데이터·파일·로그인 정보가 사라지고 회사는 닫힌 상태가 된다 (다시 켜서 `demo-reset`을 하면 복원)
- 시연 계정에서 막힌 기능 (서버가 403 `DEMO_RESTRICTED`로 거부, `blockedInDemo`로 라우트에 표시): 계정 해지, 비밀번호 변경·설정, 이메일 변경, 2단계 인증 설정, 소셜 연동·해제, 로그인한 기기 목록·원격 로그아웃 (공용 계정이라 다른 방문자의 접속 주소가 보이므로). 설정 화면은 이 구역을 숨기고 이유를 안내하며, 로그인 중에는 화면 위에 가상 데이터 안내가 계속 보인다 (`/me`의 `isDemo`)
- 공용 계정이라 달라진 점: 비밀번호를 여러 번 틀려도 계정이 잠기지 않고 (요청 횟수 제한은 그대로), 동시 로그인 세션 한도가 10개가 아니라 200개다. 시연 계정으로 가는 메일(인증·재설정·보안 알림)은 발송하지 않는다
- 회사 데이터 내보내기·파일 업로드·설정 변경은 허용한다. 방문자가 바꾼 내용과 올린 파일은 다음 초기화 때 모두 사라진다

## 계정 해지

- 설정 화면의 "계정 해지"에서 비밀번호를 다시 확인하고 요청한다 (소셜 로그인만 쓰는 계정은 비밀번호 없이). 요청하면 **즉시 모든 기기에서 로그아웃**되고 로그인이 막히며, 해지 취소 링크가 메일로 간다
- 유예는 14일이다. 그 안에는 메일의 링크(`/closure/cancel/<토큰>`, 로그인 없이, 한 번만)로 취소해 계정을 복구한다. 유예 중 로그인하면 비밀번호가 맞을 때만 해지 중임을 알려 준다
- 유예가 끝나면 `pnpm operator purge-due`가 업무 데이터를 삭제하고 계정·회사는 개인 식별 항목만 지워 익명화한다. 동의 이력·운영자 작업 기록·해지 기록은 개인정보 없이 남긴다 (처리 기준은 `apps/api/src/closure/purgePolicy.ts`, 회사 범위 테이블을 추가하면 반드시 등록해야 하며 누락은 테스트가 잡는다)

## 서버 운영

서버의 저장소는 `/srv/field-note`이고 `docker compose`로 db·api·web을 돌린다. 첫 설치 순서는 [서버 배포 순서](docs/11-server-deploy.md)에 있다.

### 단축어

서버에 접속하면 바로 쓸 수 있다. 정의는 저장소의 `deploy/server-aliases.sh`이고, 새 서버에는 `cat deploy/server-aliases.sh >> ~/.bashrc`를 한 번 실행한 뒤 다시 접속(또는 `source ~/.bashrc`)하면 된다.

| 명령                                                | 하는 일                                                                                 |
| --------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `new-company "회사 이름" "관리자 이름" [유효 일수]` | 회사와 관리자 계정을 만들고 1회용 초대 링크를 보여 준다 (링크는 한 번만 표시, 기본 7일) |
| `reissue-invite <회사 ID> [유효 일수]`              | 초대 링크를 다시 발급한다 (가입 전 회사만, 기존 링크는 즉시 무효)                       |
| `list-companies`                                    | 회사 목록과 가입 상태 (`INVITED` 가입 대기, `REGISTERED` 가입 완료)                     |
| `fn-ops pnpm operator <명령>`                       | 운영자 CLI의 어떤 명령이든 실행한다 (위 "운영자 CLI")                                   |
| `fnc <명령>`                                        | `docker compose` 줄임말 (`fnc ps`, `fnc logs -f api`)                                   |

- `fn-ops`는 알려진 무해한 pnpm 경고 줄을 숨기고 명령의 종료 코드는 그대로 돌려준다 (경고 원인과 정리 계획은 [다음 버전 계획](docs/12-next-version-plan.md))
- 초대 링크는 비밀번호처럼 다룬다. 가입할 사람에게만 전달하고 대화·공개된 곳에 붙여 넣지 않는다

서버의 `/srv/field-note`에서 실행한다.

| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 백업과 복구

- `pnpm backup create`로 DB 백업(덤프·계정 정의·확인용 기록)을 `backups/`에 만들고 30일이 지난 백업을 정리한다
- `pnpm backup drill`은 최근 백업을 **임시 DB에 복구해 검증**한다 (체크섬·행 수·마이그레이션·회사 격리). 운영 DB는 건드리지 않고, 실패하면 종료 코드가 0이 아니다
- `BACKUP_ENCRYPTION_KEY`가 있으면 백업 파일을 AES-256-GCM으로 암호화해 저장한다(운영 필수). `BACKUP_S3_*`가 있으면 서버 밖 저장소(별도 버킷)에도 사본을 올린다. `pnpm backup decrypt`로 복구용으로 풀고, `pnpm backup remote-check`로 서버 밖 저장소 접속을 확인한다
- `echo 본문 | pnpm alert:mail "제목"`은 `ALERT_MAIL_TO`로 알림 메일을 보낸다 (서버의 점검 작업 래퍼가 실패 때 호출, 받는 주소가 없으면 보내지 않음)
- `pnpm mail:check [받는 주소]`는 메일 서버 연결·TLS·로그인을 확인하고(주소를 주면 확인 메일도 발송) 접속 값은 출력하지 않는다. Gmail은 465(TLS 직접) 또는 587(STARTTLS) 포트를 쓰며, 계정 정보를 보내는 연결은 TLS가 없으면 중단한다
- 호스트에 PostgreSQL 도구가 없어도 되도록 Docker 컨테이너 안의 도구를 쓴다 (서버에 설치돼 있으면 `BACKUP_PG_MODE=local`)
- 절차·복구 시험 기록·환경 분리 표는 [docs/05-backup-restore.md](docs/05-backup-restore.md), 정기 실행 예시는 `ops/crontab.example`
- 운영(`NODE_ENV=production`)에서는 로컬 주소·`http`·`debug` 로그·로컬 기본 비밀번호가 있으면 api가 기동을 중단한다

## 계정과 회사 설정

- **비밀번호 재설정**: 로그인 화면의 "비밀번호를 잊으셨나요?"에서 메일로 받은 링크는 30분간 한 번만 쓸 수 있고, 완료하면 모든 기기가 로그아웃된다. 설정 화면에서 비밀번호를 바꾸면 다른 기기만 로그아웃된다
- **이메일 변경**: 비밀번호를 다시 확인하고 새 주소로 온 코드를 입력해야 반영되며, 이전 주소로 변경 알림이 간다
- **로그인한 기기**: 로그인할 때 접속 정보를 "Chrome · macOS" 같은 이름으로만 요약해 저장하고(원본·버전은 저장하지 않음) 접속 IP를 함께 저장한다(로그인 때 IP·마지막 사용 IP, 처리방침에 수집 항목으로 기재). 설정의 로그인한 기기 목록에서 이 기기를 맨 위에 두고, 일주일 넘게 쓰지 않은 로그인은 "오래 쓰지 않음"으로 접어 한 번에 로그아웃할 수 있다. 다른 기기를 로그아웃하면 그 기기는 다음 요청부터 로그인 화면으로 이동한다. 현재 기기는 설정 하단의 로그아웃 버튼으로 종료한다
- **회사 설정**(설정 > 회사): 하루 기준시간·월 기준일수·공수 입력 방식을 회사마다 따로 정한다. 저장한 적이 없으면 기본값(8시간·26일·비율)이다. 월 기준일수는 MM(맨먼스) 환산 기준이라 근무 형태(주 6일 26일 기본·주 5일 21.7일·주 7일 30.4일)를 고르거나 소수 첫째 자리까지 직접 입력하고, `표준값(26일)으로` 버튼과 계산 근거가 함께 보인다. 기존 회사 값과 이미 확정한 달의 값은 바뀌지 않는다. 기준시간은 분 단위로 저장하므로 바꿔도 이미 기록된 공수는 변하지 않는다

## 로그인 세션

- 로그인 실패가 연속 5번이면 해당 계정을 15분 잠근다 (잠긴 동안은 맞는 비밀번호도 거부). 없는 아이디와 틀린 비밀번호는 같은 오류·같은 처리 시간으로 응답한다
- 비밀번호는 argon2id 해시로만 저장한다
- **비밀번호 정책**(가입·재설정·변경·아이디 로그인 설정): 10~72자, 특수문자(글자·숫자·공백이 아닌 문자) 하나 이상, 숫자만으로는 불가 (`passwordSchema`, 서버·웹 폼·목업이 같은 규칙). 로그인 입력에는 적용하지 않아 정책 이전에 만든 비밀번호로도 로그인된다
- 비밀번호 칸은 오른쪽 눈 모양 버튼으로 입력 중인 값을 보거나 숨길 수 있다 (`PasswordInput`, 기본은 숨김, 로그인·가입·재설정·변경·해지·내려받기 등 모든 비밀번호 칸)

### 흐름

```text
브라우저                          API                                  DB
  │ POST /auth/login (아이디·비밀번호[·2단계 코드])
  │ ───────────────────────────▶ 계정 조회, 비밀번호(argon2id)·잠금·2단계 인증 확인
  │                              무작위 토큰 생성 ──▶ sessions 행 저장 (토큰 해시, 사용자, 회사, 만료 시각, 기기, IP)
  │ ◀── Set-Cookie: sid=토큰 (HttpOnly, SameSite=Lax, 운영 Secure)
  │ GET/POST … (쿠키 자동 첨부, 쓰기 요청은 X-Field-Note-Client 헤더·Origin 검사)
  │ ───────────────────────────▶ 쿠키 토큰 해시로 sessions 조회 → 사용자·회사 확정
  │                              (유효하지 않거나 만료면 401)   (요청의 회사 ID는 받지 않음)
  │ ◀── 교체 간격이 지났으면 새 토큰으로 바꾼 Set-Cookie
  │ POST /auth/logout ──────────▶ sessions 행 삭제, 쿠키 삭제
```

- 토큰은 JWT가 아니라 서버가 정하는 무작위 문자열이다. 토큰 원문은 저장하지 않고 SHA-256 해시만 `sessions`에 저장한다. 요청마다 DB에서 확인하므로 로그아웃·잠금·기기 원격 로그아웃이 바로 반영된다. 리프레시 토큰은 두지 않는다 (아래 연장·교체 규칙이 그 역할)
- 브라우저에는 `sid` 쿠키(HttpOnly, SameSite=Lax, 운영은 Secure)만 두고 로컬스토리지에는 아무것도 저장하지 않는다. 요청에는 `Authorization` 헤더 대신 쿠키가 자동으로 붙는다
- 회사 ID는 세션에만 기록되며, 요청의 경로·쿼리·헤더·본문으로는 받지 않는다. API 문서에 회사 ID 입력이 생기면 테스트가 실패한다
- 쓰기 요청(POST·PUT·PATCH·DELETE)은 CSRF 방어를 위해 `X-Field-Note-Client: web` 헤더가 필요하고, Origin이 있으면 `APP_ORIGIN`과 같아야 한다. 웹 API 클라이언트가 자동으로 붙인다
- **접근 통제**: 이 서비스는 회사당 관리자 계정이 하나이고 권한 등급이 없다(결정 v2.2). 그래서 "누가 볼 수 있나"는 로그인 여부, 이메일 인증 여부, 회사 상태 세 가지로 정해진다. 로그인 없이 부를 수 있는 엔드포인트는 가입·로그인·비밀번호 재설정·해지 취소·소셜 로그인·상태 확인 12개뿐이고 `accessControl.test.ts`가 이 목록을 고정한다(새 공개 엔드포인트는 목록에 이유와 함께 추가해야 시험이 통과). 로그인이 필요한 엔드포인트는 인증을 입력 검증보다 먼저 확인해, 로그인하지 않은 호출은 입력이 어떻게 틀렸든 401만 받고 요청 형태에 대한 단서를 얻지 못한다. 이메일 인증 전 계정은 인증 화면이 쓰는 요청 외에는 403, 정지·해지 중·삭제된 회사는 이미 로그인한 기기도 다음 요청부터 401. 비밀번호 변경·이메일 변경·2단계 인증 끄기·해지 요청은 현재 비밀번호를 다시 받는다. 운영자 기능은 HTTP로 열려 있지 않고 서버에서 CLI로만 쓴다. API 문서 화면은 개발 환경에서만 열린다
- **이동(리다이렉트)**: 서버가 브라우저를 보내는 곳은 소셜 로그인 콜백뿐이고, 모두 설정된 웹 주소(`APP_ORIGIN`) 뒤에 서버가 고정한 경로만 붙여 만든다(요청의 값으로 이동 대상을 정하지 않음). 로그인이 필요한 화면을 로그인 없이 열면 로그인 화면으로 보내면서 원래 경로를 라우터 상태로 넘기고, 로그인에 성공하면 그 화면으로 돌아간다. 경로는 주소(쿼리)가 아니라 상태로만 전달해 외부 링크로는 지정할 수 없고, 읽을 때도 앱 안의 경로(`/`로 시작, `//`·역슬래시·제어 문자·인증 흐름 화면 제외)인지 다시 확인한다(`apps/web/src/lib/safeReturnPath.ts`). 파일 열기·소셜 로그인 이동은 서버가 준 주소가 http(s)가 아니면 이동하지 않는다. 소셜 로그인으로 들어온 경우는 제공자 화면을 거쳐 전체 페이지가 다시 열리므로 원래 화면이 아니라 홈으로 간다. 웹 문서에는 `no-referrer`를 지정해 재설정·초대·해지 취소 링크의 토큰이 외부 링크의 Referer로 새지 않게 한다
- **요청 재시도와 실패 화면**(`apps/web/src/api/client.ts`): 조회(GET)는 연결이 끊기거나 게이트웨이 오류(502·503·504)일 때만 0.4초·1.2초 간격으로 두 번까지 자동으로 다시 시도한다(입력·권한 오류와 요청 과다 429는 다시 시도하지 않음, 화면 데이터 조회 라이브러리의 재시도는 껐다). 쓰기 요청은 자동으로 다시 보내지 않고, 모든 쓰기 요청에 멱등 키를 붙인다. 같은 내용(메서드·주소·본문)의 요청이 아직 끝나지 않았거나(더블 클릭) 서버 오류·429·연결 끊김으로 실패한 뒤 2분 안에 다시 보내면 같은 키를 써서 서버가 한 번만 처리하게 하고, 성공하거나 입력 오류(4xx)로 끝나면 키를 버려 다음 요청은 새 키를 쓴다. 쓰던 중 서버가 로그인이 필요하다(`UNAUTHORIZED`)고 하면(세션 만료, 다른 기기에서 로그아웃, 정지된 회사) 내 정보를 비워 로그인 화면으로 이동하고 "로그인이 끝났습니다" 안내와 함께 로그인하면 보던 화면으로 돌아온다(비밀번호가 틀려서 나는 401은 해당 없음). 연결이 끊기면 화면 위에 안내 띠가 나오고, 처음 로그인 확인이 실패하면 "다시 시도" 버튼이 있는 안내가 나온다
- **요청 횟수 제한**(`apps/api/src/http/rateLimit.ts`): 접속 주소(IP)당 모든 API 호출 분당 600회, 로그인한 사용자당 분당 300회, 파일 내려받기(엑셀 등) 사용자당 분당 10회가 기본이고, 로그인 전 경로는 라우트마다 더 낮은 한도가 따로 있다. 넘으면 `429 TOO_MANY_REQUESTS`. 정상 사용에서는 닿지 않는 값이고(화면 하나가 보내는 호출은 수십 회 이하), 스크립트로 쓸어 가는 호출을 막는다. 횟수는 서버 프로세스 안에서 세므로 서버를 여러 대로 늘리면 앞단(WAF·CDN)에서도 제한한다. `createApp`의 `rateLimits`로 조정하거나 끌 수 있고(한꺼번에 많이 부르는 시험용), 화면 전체 흐름 시험은 환경 변수 `RATE_LIMIT_MULTIPLIER`(운영에서는 1이 아니면 기동 거부)로 한도를 늘려 쓴다. 운영 서버는 기본값을 쓴다
- 회사 범위 밖 전용 계정을 쓰는 코드는 `apps/api/src/session/`처럼 정해진 위치에만 둔다. 다른 곳에서 DB 클라이언트를 직접 만들면 린트가 막는다

### 유효 기간 (`apps/api/src/auth/loginPolicy.ts`)

|             | 로그인 유지 선택                           | 선택 안 함                                      |
| ----------- | ------------------------------------------ | ----------------------------------------------- |
| 쿠키        | 만료 시각 있음                             | 브라우저를 닫으면 사라지는 세션 쿠키            |
| 절대 만료   | 로그인 후 **7일** (사용해도 연장되지 않음) | 로그인 후 12시간                                |
| 미사용 만료 | 없음 (절대 만료만)                         | **1시간** (요청할 때마다 연장, 갱신은 5분 간격) |

- **토큰 교체**: 사용 중인 세션은 1시간마다 새 토큰으로 바뀐다 (`sessions.token_hash` 교체, 응답의 `Set-Cookie`). 쿠키 만료는 처음 로그인한 시각 기준 그대로라 교체해도 절대 만료가 늘지 않는다
- 교체 직전 토큰은 5분 동안 계속 허용한다 (동시에 보낸 요청이나 유실된 응답 때문). 그 뒤에는 거부한다. 교체 직전 토큰으로는 다시 교체하지 않는다
- 한 계정이 동시에 로그인해 둘 수 있는 기기는 10개이고, 넘으면 가장 오래 쓰지 않은 세션부터 정리한다 (로그아웃 없이 다시 로그인해도 세션이 계속 쌓이지 않고 기기 목록도 무한히 길어지지 않음)
- 회사가 정지·해지 요청 중·삭제 완료 상태가 되면 그 회사 계정의 기존 세션도 다음 요청부터 쓸 수 없다 (로그인 차단과 별개로 세션 조회가 회사 상태를 확인)
- 비밀번호 변경은 다른 기기만, 비밀번호 재설정·복구·소유자 이전·해지는 모든 기기를 로그아웃한다
- 지금은 모바일 앱이나 외부 연동이 없어서 서버 세션을 쓴다. 그런 요구가 생기면 앱용 토큰 방식을 따로 더한다

## 환경 변수

- 목록은 `.env.example`에 있고, `pnpm env:init`이 `{{토큰}}` 자리를 새로 만든 비밀 값으로 채워 `.env`를 만든다. 변수를 추가·변경하면 이 파일과 `apps/api/src/env.ts`를 함께 고친다
- `CODE_HASH_SECRET`은 이메일 인증 코드의 해시에 쓰는 서버 비밀 값이다. 바꾸면 발송된 미사용 코드가 모두 무효가 된다
- 운영자 접속 정보(`DATABASE_OPERATOR_URL`)는 api 서버가 읽지 않는 값이다. 운영에서는 운영자 PC에만 둔다
- `PUBLIC_DEMO_ENABLED`(기본 false)는 로그인 화면의 시연 계정 안내와 시연 회사 초기화를 켜는 스위치다 (위 "공개 시연 환경")
- 비밀 값은 운영에서 쓰는 형식을 따른다 (DB 비밀번호 32자, 저장소 접근 키 20자·비밀 키 40자). 사람이 정한 단순한 값을 쓰지 않는다
- 운영 값은 저장소에 두지 않고 서버의 `deploy/.env`·`deploy/ops.env`에만 둔다 (권한 600)
- api는 시작할 때 `apps/api/src/env.ts`로 값을 검사한다. 빠졌거나 형식이 틀리면 어떤 변수가 문제인지 알려주고 실행을 멈춘다

## 저장 용량·전체 데이터 내보내기

- 설정 > 회사 관리에서 저장 용량(한도·사용량·용도별·프로젝트별)을 보고, 해지 전에 `전체 데이터 내려받기`로 회사 데이터를 엑셀 한 파일로 받는다. 비밀번호를 다시 확인하고, 사진·문서 원본은 포함하지 않으며, 내보낸 기록이 활동 기록에 남는다 (`GET /company/storage`, `POST /company/export`)

## 프로젝트 요약 엑셀

- 요약 화면의 `엑셀 내려받기`(`GET /projects/{id}/summary.xlsx`)로 요약과 같은 내용(기본정보·공수·자재·변경·추가 작업)을 시트별로 받는다. 금액·민감 문서는 싣지 않고, 내보낸 기록이 활동 기록에 남는다
