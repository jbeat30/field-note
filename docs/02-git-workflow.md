# Git 브랜치·PR·버전 전략

## 1. 흐름

```
main ─┬─▶ feature/0.1.0 (피쳐 버전 브랜치)
      │      ▲   ▲   ▲
      │      │   │   └─ PR(squash) ─ feat-env-logger   (기능 브랜치)
      │      │   └───── PR(squash) ─ feat-api-validate
      │      └───────── PR(squash) ─ docs-git-workflow
      │      │
      │      └─ 버전 범위 완료 후 PR(merge) ─┐
      │                                      ▼
      └─▶ release/0.1.0 (릴리즈 브랜치) ─ 버전 올림 fix PR ─┐
                                                           │
main ◀──────────────── PR(merge) ──────────────────────────┘
```

1. 다음 릴리즈 버전의 **피쳐 버전 브랜치** `feature/<버전>`을 `main`에서 만든다.
2. 기능마다 **기능 브랜치** `<타입>-<작업명>` (예: `feat-login-page`)을 피쳐 버전 브랜치에서 만든다.
3. 기능 브랜치 → 피쳐 버전 브랜치로 **PR**. CI가 통과해야 머지(squash)한다.
4. 피쳐 버전 브랜치에서 해당 버전 범위가 모두 끝나면 **릴리즈 브랜치** `release/<버전>`을 `main`에서 만들고, `feature/<버전>` → `release/<버전>`으로 **PR**(merge commit)을 보낸다. CI 통과 필수.
5. 릴리즈 브랜치에서 `package.json` 버전을 올리고(`fix-…` PR) → `release/<버전>` → `main`으로 **PR**(merge commit). CI 통과 필수.
6. `main` 머지 시 워크플로가 태그 `v<버전>`과 GitHub Release를 자동 생성한다.

## 2. 규칙

| 대상        | 규칙                                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| `main`      | 직접 푸시 금지. `release/*`에서 온 PR만 허용                                                                            |
| `feature/*` | 직접 푸시 금지. 기능 브랜치 PR만 허용                                                                                   |
| `release/*` | 직접 푸시 금지. 같은 버전의 `feature/<버전>` PR, 버전 올림·릴리즈 중 발견된 수정(`fix-…` PR)만 허용                     |
| 모든 PR     | CI(`verify`, `branch-policy`) 통과 필수                                                                                 |
| 브랜치 이름 | 기능: `feat-` `fix-` `docs-` `chore-` `refactor-` `perf-` `test-` `ci-` + 작업명 (영문 소문자·하이픈, 버전은 넣지 않음) |
| 머지 방식   | 기능 → 피쳐: squash / 피쳐 → 릴리즈, 릴리즈 → main: merge commit                                                        |
| 커밋 메시지 | `타입: 한국어 설명`                                                                                                     |

PR 방향이 맞는지는 `branch-policy` 체크가 검사한다.

| PR 대상(base)   | 허용되는 출처(head)                                                       |
| --------------- | ------------------------------------------------------------------------- |
| `main`          | `release/x.y.z`                                                           |
| `release/x.y.z` | `feature/x.y.z`(같은 버전) `fix-…`                                        |
| `feature/x.y.z` | `feat-…` `fix-…` `docs-…` `chore-…` `refactor-…` `perf-…` `test-…` `ci-…` |

### CI 검사 범위

필수 체크는 항상 `verify`와 `branch-policy`이고, `verify`는 아래 범위에서 실행된 잡의 결과를 모아 판정한다 (해당 없는 잡은 건너뛴 것으로 통과). 같은 PR에 새로 푸시하면 이전 실행은 취소된다.

| PR / 이벤트                                                              | 범위    | 실행하는 검사                                                                                   |
| ------------------------------------------------------------------------ | ------- | ----------------------------------------------------------------------------------------------- |
| 기능 브랜치 → `feature/x.y.z`                                            | light   | 타입·린트·주석·서식 + 단위·통합 시험 (문서만 바꾼 PR은 서식만)                                  |
| `feature/x.y.z` → `release/x.y.z`, `release/x.y.z` → `main`, `main` 푸시 | full    | light + 빌드·의존성 감사 + 스토리 + 화면 전체 흐름(e2e) + 이미지 빌드                           |
| `fix-release-version-*` → `release/x.y.z`                                | version | 변경 파일이 `package.json`·문서뿐인지 + 서식. 다른 파일이 섞이면 실패 (일반 `fix-` PR로 올린다) |

light에서 건너뛴 스토리·e2e·이미지 빌드는 릴리즈 PR에서 한꺼번에 확인한다. 화면 변경이 큰 작업은 PR 전에 로컬에서 `pnpm test:stories`를 돌린다.

## 3. 버저닝 (SemVer 2.0)

`MAJOR.MINOR.PATCH` — 태그는 `v` 접두어(`v0.1.0`).

| 버전          | 범위                                                                                  |
| ------------- | ------------------------------------------------------------------------------------- |
| 0.1.0         | 기술 0 — 준비 (T0-1 ~ T0-7)                                                           |
| 0.2.0         | 0단계 전반 — 계정 (화면 선행 S1~S4 + P0-2 ~ P0-8)                                     |
| 0.3.0         | 0단계 마무리 — 처리방침 페이지·백업 복구 시험·해지 (P0-9 ~ P0-11)                     |
| 0.4.0         | 1단계 — 직원·프로젝트·투입 (P1)                                                       |
| 0.5.0         | 2단계 — 메모·사진·자재·자료 (P2)                                                      |
| 0.6.0 ~ 0.9.x | 3단계 관리·경고, 4단계 보증·확정, UI/UX 리뉴얼, 이월·5단계, 배포 준비 문서, 규칙 정비 |
| 0.10.0        | 로컬 최종 점검 (격리·보안·접근성·성능·시나리오 시험)                                  |
| 0.11.0        | 상용 배포 준비 (컨테이너 설정, 배포 스크립트, 헬스 체크, 모니터링)                    |
| 0.12.0        | 서버 준비 (검토·서버 구성·시연 환경, 실환경 시험은 1.0.0 전)                          |
| 1.0.0         | 상용 첫 배포 (운영 환경에서 실제 사용자에게 서비스 제공)                              |
| 1.x.0         | 1.0.0 이후 기능 추가                                                                  |
| x.y.PATCH     | 버그 수정 (릴리즈 이후 긴급 수정은 `fix` 브랜치 → `release/x.y.z+1`)                  |

- 1.0.0 전에는 MINOR가 작업 묶음, PATCH가 수정이다. 1.0.0은 상용 첫 배포 때 붙인다 (2026-10-17 결정, `01-development-plan.md` 결정 009).
- 릴리즈 노트는 GitHub Release의 자동 생성 노트를 쓴다.
