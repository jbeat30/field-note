| P2-1 | 파일 파이프라인(presigned 업로드, file-type 검사, sharp 썸네일, 용량 한도) | 완료                        |
| P2-2 | 사진 API·사진첩 + 프론트 업로드 대기열                                     | API 완료 (PR 대기), 웹 남음 |

P2-1 메모

- 흐름: `POST /projects/{projectId}/files`(신청, 형식·크기·회사 용량 확인) → 발급된 주소로 저장소에 `PUT` → `POST /files/{id}/complete`(작업 큐 `file.process` 등록) → 서버가 크기·내용(file-type)·썸네일(sharp) 처리 → `READY` 또는 `REJECTED`(사유 포함). `GET /files/{id}`로 상태, `GET /files/{id}/url?variant=original|thumbnail`로 5분짜리 내려받기 주소
- 허용 형식은 JPEG·PNG·WebP(사진·자료), PDF·docx·xlsx·pptx(자료). 사진 20MB, 자료 50MB. HEIC는 sharp 기본 빌드가 읽지 못해 제외하므로 **앱이 올리기 전에 JPEG로 변환·압축**해야 한다 (P2-2). 회사 용량 한도는 `companies.storage_quota_bytes`(기본 5GB, 운영자가 SQL로 조정)
- 검증: 로컬 RustFS가 서명한 형식·크기와 다른 PUT을 403으로 거부함을 직접 확인했고, 위조 파일(실행 파일을 `.jpg`로, PNG를 JPG로)은 `CONTENT_MISMATCH`로 거부되고 저장소에서도 지워진다
- P2-2 API 메모: 파일을 올린 뒤 `POST /projects/{projectId}/photos`로 사진 기록(구분·구역·촬영일시·작업일·설명)을 붙인다. 같은 파일을 다시 등록해도 기존 사진을 돌려주므로 업로드 대기열이 어느 단계에서 끊겨도 처음부터 다시 보내면 된다. 파일이 검사 중이어도 등록할 수 있고(`file.status`로 확인), 썸네일 주소는 `READY`가 된 뒤 목록에 나온다. 작업일은 서울 기준 촬영일이 기본이며 작업일지와 프로젝트×날짜로 이어진다(일지가 아직 없어도 됨). 사진첩은 촬영일시 최근순 커서 방식(`nextCursor`), 구분·구역·작업일 필터이며 작업 전·후 비교는 구분+구역으로 화면이 짝짓는다. 대표 사진은 프로젝트마다 한 장(`PATCH`의 `isCover`), 삭제는 소프트 삭제
- P2-2 웹 메모: 프로젝트 카드의 "사진첩"(`/projects/:id/photos`)에서 구분·구역을 정하고 여러 장을 올린다. **업로드 대기열**(`photos/uploadQueue.ts`)은 선택 즉시 목록에 보이고 한 장씩 순서대로(신청 → 저장소 PUT → 완료 알림 → 사진 등록) 올리며, 단계마다 IndexedDB에 저장해 앱을 닫았다 열어도 끊긴 단계부터 이어간다. 일시 오류·오프라인은 2초부터 두 배씩(최대 60초) 간격으로 자동 재시도하고(6번까지), 영구 오류(용량 초과 등)와 6번 실패는 "올리지 못함"으로 멈춰 사용자가 다시 시도·취소한다. 업로드 주소가 만료되거나 403이면 신청부터 다시 한다
- 올리기 전 브라우저가 JPEG로 변환·압축한다(긴 변 2,000px, 품질 0.85, EXIF 위치 정보 제거). HEIC는 브라우저가 열 수 있으면(iOS Safari) 같은 경로로 JPEG가 되고, 열 수 없으면 "JPEG로 찍어 달라"는 안내를 보여 준다. 촬영일시는 파일의 수정 시각을 쓴다(EXIF 날짜는 읽지 않음)
- 사진첩은 전체(구분 필터, 더 보기)와 전후 비교(같은 구역의 작업 전·후를 나란히, 한쪽만 있어도 표시)를 제공하고, 사진을 누르면 원본 보기·수정·대표 지정·삭제(확인 한 번 더)가 가능하다. 로컬 저장소는 API 시작 때 버킷과 CORS(웹 주소의 PUT·GET)를 설정한다. 운영 버킷은 같은 CORS를 운영자가 설정해야 한다
- 실제 브라우저(Chromium) 확인: 3600×2400 사진이 2000×1333으로 올라가고, 위장 파일은 변환 단계에서 안내되며, 오프라인에서 고른 사진이 연결 복구·페이지 닫았다 열기 뒤에도 올라간다. 확인 중 대기열이 처음 비어 있을 때 시작되지 않는 문제를 찾아 고쳤다
- P2-3 API 메모: `POST /memos`로 한 줄만 적어도 저장되고 프로젝트를 정하지 않으면 **메모함**에 들어간다. 날짜(서울 기준 오늘)·태그(협의·지시·이슈·할 일·기타, 기본 기타)는 선택. `GET /memos?scope=INBOX`(메모함) 또는 `scope=PROJECT&projectId=`(프로젝트 메모 노트)는 날짜 최근순 커서 방식이고 태그·완료 여부로 거른다. `PATCH`로 프로젝트에 연결(메모함 정리)하거나 `projectId: null`로 메모함에 되돌리고, 할 일 메모의 `isDone`을 바꾼다(완료 시각 기록, 할 일이 아닌 태그로 바꾸면 완료 표시 삭제, 할 일이 아닌 메모는 완료 불가). `GET /memos/summary`는 정리 안 된 메모함 건수와 끝내지 않은 할 일 건수(메뉴 배지·대시보드용). 삭제는 소프트 삭제. 0.4.0에서 지웠던 `memos` 테이블을 새 구조로 다시 만들었다
- P2-3 웹 메모: **홈**에 메모함 카드(정리 안 된 메모·끝내지 않은 할 일 건수)가 있고 누르면 `/inbox`. 프로젝트 카드의 "메모 노트"(`/projects/:id/memos`)에서 날짜별 메모를 보고 태그·"끝내지 않은 할 일만"으로 거른다. 메모 입력은 **내용만 적어도 저장**되며, 쓰는 중인 글은 저장 위치(메모함/프로젝트)별로 기기에 임시 저장돼 새로고침·앱 종료 뒤에도 남고 저장이 실패해도 글을 지우지 않는다. 메모함에서는 "프로젝트에 연결"로 정리하고, 할 일은 체크로 완료한다(서버가 확인한 뒤 반영). 삭제는 한 번 더 확인
- **빠른 추가**(하단 고정 "추가" 버튼)는 메모·사진·오늘 일지 시트를 연다. 프로젝트 화면에서는 그 프로젝트의 메모 노트·사진첩·일지로 바로 연결하고, 그 밖에서는 메모를 메모함에 저장하며 사진은 프로젝트를 먼저 고르게 한다. **자재 추가는 P2-4에서 시트에 붙인다**
- 메뉴 구조(홈 = 대시보드 + 빠른 추가 + 메모함)에 맞춰 메모함 진입을 상단 메뉴가 아니라 홈 카드로 두었다 (상단 메뉴가 모바일 폭에서 이미 가득 참)
- P2-4 API 메모: **자재 목록**(`/materials`)은 이름·규격·단위·분류(원자재·부자재·마감재·소모품)이고 **이름과 단위만으로 즉석 추가**할 수 있다(분류는 소모품으로 시작). 같은 이름도 규격이 다르면 별도 자재이며 공백·대소문자만 다른 이름·규격은 중복이다. 목록은 **최근 기록한 자재가 먼저**, 이름·규격 검색, 숨긴 자재는 기본 제외. 기록이 있는 자재는 단위를 바꿀 수 없다. 별칭·자재 합치기는 아직 없다

- 홈의 **이어서 작성**: 저장하지 않고 닫은 일지·자재 초안을 프로젝트·날짜 단위(최근 저장 먼저)로 보여 주고 누르면 그 일지 화면으로 이동. 30일이 지난 일지·자재 초안은 앱을 열 때 지운다. 로그아웃하면 기기의 초안도 모두 지운다(기존 `resetClientState`)
- 아직 초안으로 저장하지 않는 것: 문서·사진 올리기 입력(파일 자체를 담아야 해서 사진은 업로드 대기열이 대신 맡고, 문서는 올리는 중 진행률 방식), 프로젝트·직원 등록 폼
- 실제 브라우저(Chromium, 모바일 크기) 확인: 일지 내용·구역을 쓰고 저장 대기 중에 탭을 닫아도 새 탭에서 그대로 복구되고, 자재 행(수량 7)도 복구되며, 홈 "이어서 작성"에 두 초안이 한 줄로 보이고, 서버에 저장하면 일지 초안만 지워지고 자재 초안은 남는다
- P2-7 메모: `GET /search?q=&projectId=&limit=`가 **프로젝트(이름·코드·현장 이름·주소) · 직원(이름·직책) · 메모(내용) · 자료(문서 이름) · 일지(작업 내용·구역·특이사항)**를 한 번에 찾아 종류별로 나눠 돌려준다. 대소문자를 가리지 않는 부분 일치이고, 종류마다 최대 20개(기본 5개)까지만 주며 더 있으면 `hasMore`로 알려 검색어를 좁히게 한다. 메모·일지는 검색어 주변만 발췌하고, 계약서 같은 민감 문서는 `SENSITIVE`, 퇴사한 직원은 `LEFT` 표시가 붙는다. **직원의 연락처·생년월일·메모는 검색 대상이 아니다**(목록에서 가리는 정보, §7.3). 지운 메모·문서는 제외한다. `projectId`를 주면 그 프로젝트의 메모·자료·일지만 찾는다(§10.9 프로젝트 안 검색)

- **PDF·인쇄**는 서버가 PDF를 만들지 않고 **브라우저의 인쇄(PDF로 저장)** 를 쓴다: 일보 화면이 A4 세로 인쇄용 스타일(메뉴·빠른 추가 버튼 숨김)을 갖고, 단추는 사진이 모두 불러와진 뒤에 인쇄 창을 연다. 글꼴은 기기의 한글 글꼴을 PDF에 그대로 넣으므로 별도 글꼴 파일을 싣지 않는다. 실제 확인: Chromium 인쇄로 만든 PDF는 A4 한 쪽이고 `pdftotext`로 한글이 그대로 추출되며 `pdffonts`에서 글꼴이 모두 포함(emb)·부분집합(sub)으로 들어간다. 서버 생성 PDF가 필요해지면(자동 메일 발송 등) 한글 글꼴을 번들해 추가한다
- **엑셀**(`GET /projects/{projectId}/daily-reports.xlsx?from=&to=`, 한 번에 93일까지)은 `exceljs`로 요약·작업일보·공수·자재 시트(머리글 고정, 숫자는 숫자 칸, 한글 파일 이름)를 만든다. **내보내기는 화면에서 한 번 더 확인하고 감사 기록(`REPORT_EXPORTED`: 누가·기간·건수)으로 남는다**(§7.3). 라우트 등록소에 파일 응답(`file`)을 추가했다
- 화면: `/projects/:id/daily-report?date=`(프로젝트 카드 "작업일보 출력", 일지 화면 "작업일보 보기"). 날짜 이동, "인쇄·PDF로 저장", "엑셀로 내보내기"(기간 선택 → 확인 창 → 내려받기, 오류는 화면에 표시)
- 아직 없는 것: 프로젝트 요약·월 공수표·직원별 투입 내역·자재 사용 내역·변경·추가 작업 내역·보증·보수 현황 리포트(§15.4의 나머지, 3~4단계), 사진 묶음 다운로드, 인쇄(PDF) 기록(브라우저가 하므로 서버가 알 수 없음)
- P2-9 메모: **화면 전체 시험**(`apps/web/e2e`, `@playwright/test` 1.63.0, `pnpm e2e`)을 만들었다. 실제 PostgreSQL·객체 저장소·API(3001번)·웹(5173번)을 띄워 Chromium 모바일 크기(390×844, 한국어·서울 시간)로 돈다. 시험 전에 `pnpm --filter @field-note/api db:generate && pnpm infra:up && pnpm db:setup && pnpm db:seed`가 필요하고(CI 잡이 같은 순서로 준비), 이미 떠 있는 서버는 재사용한다. 시험 데이터는 이름을 겹치지 않게 만들어 같은 DB로 여러 번 돌려도 된다
- `coreFlow.spec.ts`: 로그인 → 프로젝트 등록 → 작업 시작 → 직원 투입 → 일지 일괄 입력·저장 → 같은 화면에서 자재 반입·사용 → 사진 업로드(사진첩에 썸네일 2장) → 작업일보에 일지·공수 합계·자재·사진이 모임
- `dailyLogTiming.spec.ts`: **하루 일지 입력 3분 실측**(§14 목표). 프로젝트 화면에서 시작해 빠른 추가 → 오늘 일지 → 작업 구분 일괄·공수(반일 한 명) → 작업 내용 → 저장 → 최근 쓴 자재 한 번 눌러 수량 → 사진첩에서 두 장 올리기까지 잰다. **스크립트가 사람 속도를 흉내 낸 값**이다(누르기·고르기 전 0.8초, 글자 0.2초/자, 사진 고르기 창 5초). 결과: **약 22초, 누르기·고르기 14번, 글자 26자**(목표 180초). 사람이 하면 몇 배 느려도 목표 안에 들어오는 여유(약 8배)이며, **실제 사람의 시간은 ★ 실사용 시험에서 현장 관리자가 다시 잰다**
- 이 시험이 찾아낸 문제 두 가지를 고쳤다: ① 일지 화면에서 빠른 추가의 "사진"이 프로젝트 고르기로 가던 것 → 일지 화면(`?project=`)에서도 지금 프로젝트를 인식 ② **"최근 쓴 자재" 순서가 날짜만 보고 같은 날이면 이름순**이라 방금 쓴 자재가 목록 밖으로 밀리던 것 → 자재 응답에 `lastRecordedAt`(마지막 입력 시각)을 더해 같은 날이면 방금 입력한 자재가 먼저 오게 함. 시험을 같은 DB로 여러 번 돌려도(3회 연속 통과 확인) 되도록 이름을 매번 다르게 만든다
- 최근 쓴 자재는 아직 **회사 전체** 기준이다. 현장마다 쓰는 자재가 다르면 프로젝트별 최근 순서가 더 맞을 수 있어 실사용 시험에서 확인한다
- CI에 `e2e` 잡을 추가하고 필수 체크 `verify`가 함께 판정한다(실패 시 보고서·추적 파일을 7일 보관). 기본 재시도 1번
- P2-10 메모: 격리 시험을 **자동으로 새 기능까지 따라가게** 바꿨다. ① `isolationEndpoints.test.ts`의 "전 엔드포인트" 시험: 접두사 목록 대신 OpenAPI에서 **로그인이 필요한 모든 엔드포인트**(79개)를 읽어 격리 시험 목록 또는 `OWN_ACCOUNT_ONLY`(본인 계정·세션·회사 설정 전용 15개, 각자 전용 시험이 있음)에 없으면 실패한다. 낡은 항목·이중 등록도 잡으므로 새 엔드포인트를 만들면 반드시 둘 중 하나에 넣어야 한다(엔드포인트 하나를 빼서 실제로 실패하는지 확인) ② DB 수준 시험의 "자기 행이 보임" 목록에 파일·사진·메모·자재·문서 테이블 추가
- **파일 주소 격리**(`isolationFiles.test.ts`): 내 사진·문서에서 받는 모든 주소(사진 목록·작업일보·파일 주소·문서 열람·내려받기)가 내 회사 경로(`company/{회사 ID}/`)만 가리키고 다른 회사 ID를 포함하지 않으며, 다른 회사의 파일·사진·문서는 어떤 경로로도 주소를 받을 수 없고(404, 응답에 회사 ID 없음, 열람 기록도 남지 않음), 내 목록·작업일보·검색 응답에 다른 회사의 파일 ID·경로·이름이 섞이지 않고, 다른 회사의 파일을 내 사진·문서·새 버전으로 등록할 수 없고(내 파일은 정상 등록), 문서 열람 기록이 회사끼리 섞이지 않음을 확인한다
- **DB 제약 추가**(마이그레이션): `files`의 `object_key`·`thumbnail_key`는 반드시 `company/{자기 회사 ID}/`로 시작해야 하며 어긋나는 행은 DB가 거부한다(애플리케이션 버그가 있어도 다른 회사 경로를 가리키는 행이 생기지 않음, 슬래시까지 비교해 접두사만 비슷한 경로도 거부)
- 계정별 접근 가능 테이블을 **목록으로 고정**: 운영자 계정은 `companies·invitations·legal_documents·operator_actions·users`, 로그인 전용 계정은 11개 테이블, 작업 큐 계정은 업무 테이블 없음. 새 테이블이 실수로 이 계정들에 열리면 시험이 실패한다(서비스 기획서 §5.1: 운영자도 회사 업무 데이터를 열람하지 않음)
- 아직 없는 것: 전체 데이터 내보내기·민감 자료 일괄 다운로드의 비밀번호 재확인(§7.3, 내보내기 기능과 함께), 열람 범위 설정(사용자 한 명 구조라 보류), 감사 기록의 다른 종류(로그인·월 확정 등은 해당 기능에서 추가)
- 계획 자재(§11.5), 자재 첨부(사진·거래명세표), 프로젝트 완료 시 잔량 안내, 엑셀 내보내기는 이후 단계
- 메모에 사진·파일 첨부와 변경·추가 작업(§10.5)·보수 요청(§10.6)으로의 승격은 해당 기능(2~3단계)에서 붙인다. 현재 사진은 프로젝트가 있어야 올릴 수 있어 메모함에는 사진이 들어가지 않는다

P3-5 메모 (상태 전환 안내·프로젝트 요약)

- 새 테이블 없음: 두 기능 모두 기존 기록을 읽어 보여 주는 조회다 (`GET /projects/{id}/transition-notices?to=`, `GET /projects/{id}/summary`). 요약은 **저장하지 않고 그때그때 최신 기록으로 만든다** — 완료 뒤에 들어온 사후 기록도 반영되므로 기획서의 "보증 종료 시 갱신"을 따로 구현하지 않아도 된다. 완료 시점의 고정본(스냅샷)이 필요하면 이후에 추가
- **상태 전환 안내**(§10.3): 진행 → 완료 전에 임시 저장 일지 건수, 진행률 100%가 아님(기록 없으면 기록 요청), 잔량이 남았거나 마이너스인 자재(0은 제외), 아직 협의 중인 변경·추가 작업을 알리고, 중단 → 진행에서 종료 예정일이 지났으면 기간 연장을 안내한다. **막지 않는 안내**이며 shared `evaluateTransitionNotices`(서버·목업 공용)가 판단하고 프로젝트 카드 상태 패널의 확인 단계에 "확인할 것"으로 나온다. 보증 중·종료 전환과 "프로젝트 요약 확인" 조건은 보증·종료 상태가 생기는 4단계에서 붙인다
- **프로젝트 요약**(§10.7): 기본정보(고객·현장·담당·계약일·예정/실제 기간·진행률), 투입 요약(총 공수·MD·MM·작업일·계획 대비, 인원별·작업 구분별), 자재 요약(반입·사용·반출·폐기·잔량), 변경·추가 작업 목록과 쓴 공수, 사후 작업 공수, 대표 사진(대표 지정이 먼저, 최대 6장, 검사에서 거부된 사진 제외), 작업자료 목록. **금액(단가·인건비)은 싣지 않고 민감 문서는 목록에서 빼 건수만 알린다**(§10.7 "권한 필터"). 화면은 `/projects/:id/summary`(프로젝트 카드의 "프로젝트 요약")이며 브라우저 인쇄로 PDF 저장한다 (A4 한 쪽, 한글 추출 확인)
- 실제 브라우저(Chromium, 모바일 크기) 확인: 완료 처리 확인 단계에 임시 저장 일지·진행률 60%·협의 중 변경 작업 안내가 뜨고, 요약이 모든 구역과 함께 나오며 Chromium으로 만든 PDF가 A4 한 쪽이다
- **아직 없는 것**: 요약의 엑셀 내보내기(§10.7)·내보내기 감사 기록, 완료 시점 고정본, 보수 요청(사후 작업의 보수 요청 건수), 일지 3분 이내 입력처럼 단계 종료 기준 시험은 P3 전체 마무리 때 확인

P3-4 메모 (변경·추가 작업 기록)

- 새 테이블 3개: `change_works`(요청일·요청자·내용·상태·번호), `change_work_status_changes`(상태 이력, 추가만 가능), `change_work_documents`(증빙 연결, 해제 시각만 수정). 모두 RLS·해지 삭제 정책·격리 시험을 반영했고, 변경 작업은 삭제할 수 없으며 수정은 DB가 열 단위로 제한한다 (요청일·요청자·내용·상태만)
- API: `GET·POST /projects/{id}/change-works`, `GET /projects/{id}/change-usage`, `GET·PATCH /change-works/{id}`, `POST /change-works/{id}/status`, `POST /change-works/{id}/documents`, `DELETE /change-works/{id}/documents/{documentId}`. 번호는 프로젝트 행을 잠가 1부터 채번(동시 등록 시험으로 확인). **협의 중일 때만 내용을 고칠 수 있고** 합의·철회된 기록은 상태 이력과 함께 보존된다. 철회는 사유 필수, 상태 변경일은 요청일 이후 오늘까지, 같은 변경을 동시에 두 번 보내도 이력은 한 번만 남는다
- **프로젝트 상태별 제한**(§10.3): 예정·진행·중단은 기록·수정 가능, 완료는 관리자 확인(`confirmCompleted`)이 있을 때만, 보증 중·종료·취소는 조회만 (shared `changeWorkProjectCheck`, 서버·목업·화면 공용)
- **증빙**: 문서함에 올린 문서(대화 캡처·합의서 등)를 같은 프로젝트 안에서 연결·해제한다. 해제해도 연결 기록은 남고 같은 문서를 다시 연결할 수 있다. 문서를 삭제하면 목록에서 빠진다. 새 파일을 변경 작업 화면에서 바로 올리는 기능은 없다 (문서함에 올린 뒤 연결)
- **변경·추가 작업으로 쓴 공수·자재**(`change-usage`): 일지와 자재 기록의 기존 "변경·추가 작업" 표시를 프로젝트 단위로 합산한다 (저장된 일지의 공수 합·일지 수, 변경 표시된 자재의 **사용** 합계). 임시 저장·반입 등은 제외
- 화면: 프로젝트 카드의 "변경·추가 작업"(`/projects/:id/change-works`)에 합계, 새로 기록(요청일·요청자·요청 내용), 상태 필터 목록이 있고 항목을 펼치면 상태 변경(합의됨·철회·다시 협의 중)·내용 수정(협의 중일 때만)·증빙 연결·상태 이력이 나온다. 협의 중으로 7일 넘게 남은 건은 "N일째 협의 중"으로 표시한다 (알림은 P3-6에서). 시드·목업에 A동 변경·추가 작업 두 건(합의된 건과 오래 협의 중인 건)이 있다
- 실제 브라우저(Chromium, 모바일 크기) 확인: 목록(13일째 협의 중 표시) → 새로 기록(#3) → 합의됨으로 변경(이력 생성, 수정 버튼 사라짐) → 철회는 사유 없이 거부
- **아직 없는 것**: 일지·자재 기록을 **특정 변경 작업에 연결**하는 것(현재는 일지·자재의 "변경·추가 작업" 표시만 있고 어느 변경 건인지는 연결하지 않아, 합계는 프로젝트 단위), 메모를 변경 작업으로 승격(§10.9), 7일 방치 알림(P3-6), 변경 작업 사진 첨부, 상태 변경 이력의 요약 리포트

P3-3 메모 (직원 단가표·프로젝트 인건비)

- **범위 변경**: 서비스 기획서 v2.4는 직원 급여·단가·인건비를 범위 밖으로 두었으나 사용자 결정(2026-10-11)으로 **인건비 추정만** 추가했다 (`01-development-plan.md` §8 결정 005). 급여 지급 계산·세금·4대보험·계약 금액·원가·이익은 계속 범위 밖이다. 기획서 원본(`docs/planning/`)은 그대로 두었다
- 새 테이블 `employee_pay_rates`(단가표, 추가만 가능, RLS·해지 삭제 정책·격리 시험 반영)와 감사 행위 3종(`PAY_RATE_VIEWED`·`PAY_RATE_CHANGED`·`LABOR_COST_VIEWED`). 단가 조회·변경과 인건비 조회는 감사 기록을 먼저 남긴 같은 트랜잭션에서만 응답하고, 변경 기록에는 금액을 복사하지 않는다
- **단가 이력**: 단가를 바꾸면 기존 행을 고치지 않고 적용 시작일과 함께 새 행을 추가한다. 근무일에 적용되는 단가는 그 날짜까지 시작한 행 중 시작일이 가장 늦은 것(같은 시작일이면 나중에 입력한 것)이라, 변경 전 날짜의 일지는 기존 단가로, 변경일부터는 새 단가로 계산된다. 늦게 알게 된 인상은 과거 적용 시작일로 입력하면 그날부터 다시 계산된다. 적용 시작일은 2000-01-01 ~ 오늘+366일만 허용
- **분당 환산**(shared `ratePerMinute`): 일급 ÷ 하루 기준시간, 시급 ÷ 60, 월급 ÷ (월 기준일수 × 하루 기준시간), 연봉 ÷ 12를 월급과 같게. 기준시간·월 기준일수는 회사 설정을 따른다. 금액은 직원별 합계에서 한 번만 반올림
- **프로젝트 인건비**(`GET /projects/{id}/labor-cost`): 실제 = 저장된 일지(임시 저장 제외)의 공수 × 근무일 단가, 계획 = 취소하지 않은 투입의 계획 공수 × 오늘(투입 기간 안으로 맞춤)의 단가. **단가가 없는 직원·날짜의 공수는 금액 없이 따로 세어(합계에서 빠짐) "최소 추정"** 이 된다. 4대보험·수당·퇴직금·세금은 포함하지 않는다
- 단가 입력·이력은 직원 카드("단가"), 인건비는 프로젝트 카드("인건비 (최소 추정)")에 있다. 직원 카드 안내 문구를 "급여는 저장하지 않습니다"에서 "급여는 아래 단가만 기록합니다"로 바꿨다. 시드·목업에 가짜 단가가 있다(정판금 일급·단가 인상 이력, 최설치 시급, 한용접 월급, 송소장 연봉, 나머지는 단가 미등록)
- 실제 브라우저(Chromium, 모바일 크기) 확인: 정판금 일급 25만원 × 2일 = 50만원, 최설치 시급 2.8만원 × 16시간 = 44.8만원, 한용접 월급 480만원 → 일 218,182원 × 2일 = 43.6만원, 단가 없는 김일용은 "단가 미등록". 오늘부터 일급을 30만원으로 올려도 과거 일지의 인건비는 그대로다
- **남은 일(공개 전 필수)**: 개인정보 처리방침 초안의 수집 항목에 "직원별 단가(일급·시급·월급·연봉)"를 추가하고 새 버전으로 올려야 한다 (현재 초안은 직원 정보 항목에 단가가 없고, 같은 버전의 본문을 고치면 등록 시 해시가 어긋나므로 공개본 작성 때 버전을 올려 반영). 단가 일괄 입력·엑셀 내보내기에서의 비밀번호 재확인, 프로젝트 목록·월 공수표에 인건비 표시, 직원별 전체 프로젝트 인건비 보기는 아직 없다

- **서류 상태**: 만료일이 없으면 유효(만료 없음), 오늘 기준 30일 이내면 만료 임박, 지났으면 만료. 목록은 만료가 빠른 순(만료 없음은 맨 뒤). 종류는 회사 목록의 자격 종류만 쓸 수 있고 숨긴 종류로는 새로 등록할 수 없다. 파일은 **그 직원의 서류로 올린 파일만** 연결할 수 있다(다른 직원·프로젝트 파일, 거부된 파일 불가)
- **열람 기록**: 서류 파일은 일반 파일 열람(`/files/{id}/url`)으로는 열 수 없고(404), 서류 API의 `file-url`로만 열린다. 열 때마다 감사 기록(`EMPLOYEE_DOCUMENT_VIEWED`, 대상은 직원, 상세에 서류 종류·파일 이름)이 같은 트랜잭션에서 먼저 남는다. 검사 중인 파일은 열 수 없다
- **투입 경고**: 프로젝트에 필요 자격을 정해 두면 투입 목록·등록·수정 응답의 `warnings`에 `CREDENTIAL`이 붙는다. 같은 종류 서류 중 만료일이 없거나 투입 종료일 이후까지 유효한 것이 있으면 통과, 서류가 없으면 **자격 없음**, 투입 시작 전에 모두 만료면 **자격 만료**, 투입 기간 중에 만료되면 **투입 중 만료**(갱신본을 추가하면 가장 늦은 만료일로 판단). 취소한 투입은 경고하지 않고 투입을 막지도 않는다
- 화면: 직원 카드의 "서류·자격"(목록·상태 표시·열기·수정/갱신·삭제 확인·등록 폼, 주민등록번호 가림 안내), 프로젝트 카드의 "필요 자격"(체크박스, 투입 패널 위), 투입 경고 문구. 설정 > 목록 관리에 "자격 종류"가 추가됨. 시드·목업에 한빛 직원 3명의 더미 서류(유효·임박·만료·만료 없음)와 A동 필요 자격(안전교육 이수증)이 있다
- **아직 없는 것**: 만료 임박 서류의 홈 알림·대시보드 "만료 임박" 위젯(P4-6), 서류 열람 기록 조회 화면(P4-7), 일지 저장 때 필요 자격 경고, 인력 배치 캘린더의 자격 만료 표시, 계약직 계약 만료, 서류 파일의 객체 저장소 삭제·퇴사 후 익명화(§13.3), 서류 이력(갱신 전 값) 보존

P4-4 메모 (월 공수 확정·재오픈·월 공수표)

- 새 테이블 2개: `monthly_closes`(회사·월마다 한 행: 확정 여부와 **확정 당시 하루 기준시간·월 기준일수**), `monthly_close_events`(확정·재오픈 이력, 추가만 가능). RLS·해지 삭제 정책·격리 시험 반영, 확정 상태는 삭제할 수 없다
- API: `GET /monthly-hours?month=YYYY-MM`(월 공수표), `POST /monthly-hours/close`, `POST /monthly-hours/reopen`, `GET /monthly-hours.xlsx?month=`(엑셀). 계산은 shared `monthlyHours.ts`(`validateMonthClose`·`monthLockCheck`·`monthlyWorkValue`·`summarizeMonthlyHours`)를 서버·목업·화면이 함께 쓴다
- **확정(§13.2)**: 이번 달까지만 확정할 수 있고(오지 않은 달 불가), 이미 확정한 달은 다시 확정할 수 없다. **임시 저장 일지가 남아 있으면 확인(`confirmDrafts`)해야 확정**하며 그 건수가 이력에 남는다. 확정 시점의 기준시간·월 기준일수가 고정되어 이후 회사 설정을 바꿔도 확정된 달의 MD·MM은 그대로다(확정하지 않은 달은 현재 설정). 확정은 선택 기능이라 쓰지 않아도 모든 기능이 동작한다
- **잠금**: 확정된 달의 날짜에는 작업일지를 **저장할 수 없다**(신규·수정·임시 저장 모두, `workDate` 오류). 서버는 같은 회사·월에 대한 어드바이저리 락으로 확정과 일지 저장을 한 줄로 세워 확정 직전에 끼어드는 저장이 없게 한다. **재오픈은 사유 필수**이며 이력에 남고, 다시 확정하면 정정한 값으로 집계된다
- **월 공수표**: 프로젝트 × 직원별 저장된 일지 공수의 MD(소수 둘째)·MM(소수 셋째)와 직원별 합계. 임시 저장 일지는 집계에서 빼고 목록(최대 50건, 일지 입력 화면으로 연결)으로 알린다
- **엑셀 내보내기**: 요약·월 공수표·직원별 합계·프로젝트별 합계 시트(한글, 확정 여부·기준값·총 공수 포함). 화면에서 한 번 더 확인하고, 내보낸 기록은 감사 기록(`REPORT_EXPORTED`, 종류 `MONTHLY_HOURS_XLSX`, 대상은 회사)으로 남는다
- 화면: `/monthly-hours`(직원 목록의 "월 공수표" 링크)에 월 이동, 확정 상태·기준값·합계, 임시 저장 일지, 프로젝트·직원별 표, 직원별 합계, 확정/재오픈, 엑셀 내보내기, 확정·재오픈 이력
- **아직 없는 것**: 홈 대시보드·알림의 "월 공수 미확정·월말 점검"(P4-6), 확정·재오픈의 감사 기록 화면(이력은 이 화면에서만 보임, P4-7), 직원 카드·프로젝트 요약에서 확정 여부 표시, 인건비(단가)를 월 공수표에 함께 표시, 확정된 달의 투입(계획) 변경 제한(지금은 일지 저장만 막음)

P4-3 메모 (보수 요청 기록·사후 작업 연결)

- 새 테이블 3개: `repair_requests`(보수 요청: 접수일·요청자·내용·위치·상태·완료일), `repair_request_status_changes`(상태 이력, 추가만 가능), `repair_request_links`(사후 작업 연결: 일지 또는 자재 기록 중 하나, 해제해도 행이 남음). 모두 RLS·해지 삭제 정책·격리 시험 반영, 보수 요청은 삭제할 수 없다
- API: `GET·POST /projects/{id}/repair-requests`, `GET·PATCH /repair-requests/{id}`, `POST /repair-requests/{id}/status`, `POST /repair-requests/{id}/links`, `DELETE /repair-requests/{id}/links/{linkId}`, `GET /projects/{id}/after-service-usage`. 번호는 프로젝트 행을 잠가 1부터 채번
- **상태**: 접수·처리 중·보류·완료. 보류로 바꾸거나 완료를 되돌릴 때는 사유 필수, 완료하면 완료일이 기록되고 되돌리면 지워진다. **완료 전까지만 내용을 고칠 수 있다**. 모든 변경은 이력에 남는다 (shared `validateRepairTransition`을 서버·목업·화면이 함께 쓴다)
- **보증 중에만** 접수·수정·상태 변경·연결을 할 수 있고 완료·종료·그 전 상태는 조회만 된다 (`repairProjectCheck`)
- **사후 작업 연결**: 작업일지·자재 기록에 "사후 작업"으로 표시한 같은 프로젝트의 **저장된 일지**와 삭제되지 않은 자재 기록을 보수 요청에 연결한다. 일지·자재 화면은 바꾸지 않고 보수 요청 화면에서 연결한다(해제 가능). 건별로 연결한 일지의 공수 합과 사용(USED) 자재 합계를 보여 주고, 프로젝트 전체의 사후 작업 합계(`after-service-usage`)는 연결과 무관하게 표시된 기록을 합산한다
- **보증 종료 조건(P4-1 이월)**: 보증 중 → 종료는 **접수·처리 중인 보수 요청이 남아 있으면 서버가 거부**하고, 보류 중인 건은 막지 않고 종료 확인 단계에서 알린다 (전환 안내 `OPEN_REPAIRS`·`HOLD_REPAIRS`)
- 화면: 프로젝트 카드의 "보수 요청"(`/projects/:id/repairs`, 완료·보증 중·종료에서 링크)에 사후 작업 합계, 새로 접수, 상태 필터 목록, 건별 상세(상태 변경·내용 수정·사후 작업 연결·이력). 시드·목업에 C동 환기 설비(종료)의 완료된 보수 요청 두 건이 있다
- **아직 없는 것**: 보수 요청의 전·후 사진 첨부(사진 기능과 연결, 현재 사진은 프로젝트·일지 기준), 일지·자재 입력 화면에서 바로 보수 요청 선택(지금은 보수 요청 화면에서 연결), 미처리 보수 요청 경과·보증 임박 알림과 대시보드 위젯(P4-6), 프로젝트 요약의 보수 요청 건수, 보수 요청 검색

P4-2 메모 (보증 기간 설정·보증서)

- 새 테이블 3개: `project_warranties`(프로젝트당 한 행: 기간·시작 기준·시작일·종료 예정일), `project_warranty_changes`(변경 이력, 추가만 가능), `warranty_certificates`(보증서: 문서함 문서 + 만료일·발급처, 지워도 행은 남음). 모두 RLS·해지 삭제 정책·격리 시험 반영
- API: `GET·PUT /projects/{id}/warranty`, `POST /projects/{id}/warranty/certificates`, `PATCH·DELETE /projects/{id}/warranty/certificates/{certificateId}`. 계산은 shared `warranty.ts`(`computeWarrantyEnd`·`resolveWarrantyUpdate`)를 서버·목업·화면이 함께 쓴다
- **종료 예정일** = 시작일 + 보증 기간 (말일은 그 달 말일로 맞춤, 기간 0이면 시작일과 같음). 시작 기준은 실제 완료일(기본)·고객 검수일·직접 지정. **설정은 완료·보증 중에만** 바꿀 수 있고 종료는 재오픈 뒤에, 그 전 상태는 완료 뒤에 가능. 설정이 없으면 기본 12개월과 실제 완료일로 계산한 값을 미리 보여 주고, **처음 보증 중이 될 때 기본값이 자동 저장**된다
- **사유**: 이미 설정이 있으면 바꿀 때, 또는 종료 예정일을 직접 지정(연장 등)할 때 사유 필수. 모든 변경은 이력으로 남는다. 보증 중에는 기간을 0개월로 바꿀 수 없다(조기 종료로 처리)
- **P4-1 잠정 규칙을 좁힘**: 완료 → 종료는 보증 기간이 0개월일 때만, 완료 → 보증 중은 0개월이 아닐 때만, 보증 중 → 종료는 종료 예정일 전(조기 종료)일 때만 사유 필수. 종료 예정일이 지난 뒤에는 사유 없이 종료할 수 있다
- **보증서**: 문서함에 올린 같은 프로젝트의 문서에 만료일·발급처를 붙여 등록한다(중복 등록·다른 프로젝트 문서 거부, 완료·보증 중에만 등록·수정·삭제). 만료일 임박 알림은 P4-6
- 화면: 프로젝트 카드의 "보증"(`/projects/:id/warranty`, 완료·보증 중·종료에서만 링크)에 현재 보증·설정·보증서·변경 이력, 상태 패널에 보증 요약 한 줄. 시드·목업에 C동 환기 설비(종료)의 6개월 보증과 이력이 있고 옛날상가 간판 교체(완료)는 보증 미설정 상태다. C동의 종료일은 보증 종료 뒤(2026-06-19)로 고쳤다
- **아직 없는 것**: 보증 기본 기간의 회사별 설정(지금은 상수 12개월, P5-4의 경고 기준 설정과 함께), 보증 종료 임박·보증서 만료 알림(P4-6), 보증 시작일을 고객 검수일 등으로 정할 때의 날짜 범위 검사(완료일 이후 등), 미처리 보수 요청 조건(P4-3)

P4-1 메모 (프로젝트 상태 확장)

- 스키마 변경 없음: 상태 값(`WARRANTY`·`CLOSED`)과 실제 완료일 일관성 제약은 1단계에서 이미 있었고, 전환 규칙만 확장했다. 작업일지·투입·자재·변경 작업의 상태별 허용 규칙(보증 중은 사후 작업만, 종료는 조회만)도 이미 반영돼 있다
- **전환**(shared `PROJECT_TRANSITIONS`): 완료 → 보증 중·종료, 보증 중 → 종료, 종료 → 보증 중(재오픈). 취소는 그대로 끝. 전환 날짜 이름은 보증 시작일·종료일·재오픈일
- **조건**: 완료 → 보증 중은 프로젝트 요약 확인(요청 본문 `confirmSummary`, 화면은 요약 링크와 확인 체크), 종료·재오픈은 사유 필수(`transitionNeedsReason`), 종료는 임시 저장 일지가 남아 있으면 서버가 거부하고 화면은 확인 단계에서 같은 안내를 먼저 보인다. 검사는 shared `validateProjectTransition`을 서버·목업·화면이 함께 쓴다
- **잠정 규칙은 P4-2에서 보증 기간 기준으로 좁혔다** (아래 P4-2 메모)
- **아직 없는 것**: 보증 중 → 종료의 "미처리 보수 요청 없음" 조건(P4-3), 보증 종료 예정일 계산(P4-2), 대시보드·알림의 보증 항목(P4-6), 재오픈·종료 감사 기록(P4-7)
- 실제 브라우저(Chromium, 모바일 크기)·로컬 API/DB 확인: 완료 프로젝트에서 요약 미확인 시 오류 → 확인 후 보증 중 → 사유 없는 종료 오류 → 사유와 함께 종료 → 사유와 함께 재오픈, 이력 3건 생성 (확인 뒤 로컬 DB는 원래 상태로 되돌림)

- 검증: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm build`
- 로컬 확인: `pnpm dev` → web http://localhost:5173, api http://localhost:3000/api/v1/health

## 7. 알려진 사항

- 운영 객체 저장소 버킷에는 로컬과 같은 **CORS 설정**(웹 주소의 `PUT`·`GET`·`HEAD`, `Content-Type` 헤더 허용)을 운영 구성 때 직접 해야 한다. 로컬은 API가 시작할 때 자동으로 설정한다
- 신청만 하고 올리지 않은 `PENDING` 행과 객체는 정리하지 않는다 (용량 계산에서는 15분 뒤 제외). 정리 작업은 소프트 삭제·보존 기간을 정할 때 함께 추가
- 파일 열람 기록(민감 자료)은 P2-5 문서함에서 추가한다
- `docs/planning/`의 두 기획서는 원본 그대로이며 Prettier 대상에서 제외
- T0-4의 Testcontainers 격리 테스트는 Docker가 필요하다 (로컬은 Docker Desktop, CI는 ubuntu 러너). 앱 계정 비밀번호는 `pnpm db:setup`이 환경 변수 값으로 설정하며 마이그레이션 파일에는 두지 않는다
- 멱등 키 저장소는 메모리 구현이다(서버 재시작·다중 서버에서 기록이 사라짐). 운영 전에 DB 저장소로 교체 필요
- 세션 저장소 기본값(`createApp`)은 메모리 구현이며 운영 기동(`main.ts`)에서는 PostgreSQL 저장소를 주입한다
- 만료 세션 정리(`deleteExpired`)를 호출하는 작업은 P0-4(pg-boss)에서 연결한다
- 세션 발급(`create`)을 호출하는 로그인 흐름은 P0-3에서 연결한다. `sessions`는 P0-1부터 `(company_id, user_id)`로 `users`를 참조한다
- 약관 문서(`legal_documents`)의 실제 본문·버전 등록은 P0-9(처리방침 페이지)와 P0-2(운영 경로)에서 한다. 지금은 구조만 있다
- `GET /session`(T0-5 샘플)은 회사 ID를 응답에 담는다. 서비스 기획서 §5.1 #5(회사 식별값은 화면·주소에 노출하지 않음)와 맞지 않아 `/me`로 대체되면 제거한다
- 목업 모드의 가짜 서버(`apps/web/src/mocks`)는 실제 백엔드가 모든 계약을 구현한 뒤 개발용 보조로만 남긴다
- 시드는 회사 설정(P0-8)과 초대(P0-2) 테이블이 없어 회사·계정·약관·동의 이력만 입력한다. 해당 테이블이 생기면 `seedDemoData`에 추가한다
- 로컬 `.env`는 `pnpm env:init`으로 만든다. 기존 `.env`를 새 값으로 바꾸면 DB 컨테이너의 저장된 비밀번호와 어긋나므로 `pnpm db:reset` 필요
- 운영자 접속 정보(`DATABASE_OPERATOR_URL`)는 api 서버 설정(`env.ts`)에 두지 않는다. 운영에서는 운영자 PC에만 보관
- 초대 사용 처리(`consume`)와 관리자 계정 활성화·약관 동의 기록은 P0-3 가입 API에서 한 트랜잭션으로 연결한다
- `legal_documents`에 약관 본문·제목은 없다 (제목·경로는 `LEGAL_DOCUMENT_META`, 본문은 P0-9에서 등록)
- 로그인 잠금은 계정 단위(5회·15분)라 타인이 아이디를 알면 일시적으로 잠글 수 있다. IP 단위 속도 제한(분당 10회)과 함께 쓰며, 문제가 되면 잠금 시간 조정이나 알림을 검토한다
- `GET /session`(T0-5 샘플)은 `/me`로 대체되어 제거했다
- 이메일 발송은 SMTP 한 가지 방식이다. 운영 메일 서비스가 정해지면 접속 정보만 바꾸고, 발신 도메인의 SPF·DKIM·DMARC 설정과 메일 서비스의 수탁자 개인정보 조항 확인이 필요하다
- 작업 큐는 가입 인증 메일에만 쓴다. 만료 세션·인증 코드 정리 작업(`deleteExpired`)은 정리 작업이 필요해지는 시점에 큐 스케줄로 연결한다
- 인증 메일 제목에 코드를 포함한다(알림에서 바로 확인). 잠금 화면 노출이 우려되면 제목에서 제외 가능
- 이메일 변경 알림에는 서비스 기획서 §6.7의 "되돌리기 링크"가 없다. 변경 사실만 이전 주소로 알리며, 되돌리기(변경 취소 토큰)는 P0-5 후속으로 남김
- 보안 알림 메일 작업은 받는 주소를 큐 작업에 담는다(큐 계정은 업무 테이블을 읽을 수 없어서). 큐의 보관 기간 정책은 운영 전에 점검
- 재설정 요청은 계정 존재 여부를 응답 내용으로는 숨기지만 처리 시간 차이(조회·큐 등록)는 완전히 없애지 않았다. IP 단위 속도 제한(분당 5회)과 함께 사용
- 소셜 로그인만 쓰는 계정의 비밀번호 재설정·변경은 P0-7에서 정책 결정 필요 (현재는 일반 로그인 계정만 대상)
- 카카오 로그인은 제공자 추상화와 로컬 가짜 제공자로 구현·테스트를 마쳤다. 카카오 앱 등록은 상용 서버 작업 때 하고, 그때 키와 리다이렉트 주소만 설정한다. 실제 카카오 통신(코드 교환·사용자 정보 조회)은 앱 등록 후 처음 확인해야 한다 (README "소셜 로그인(카카오)" 참고)
- 기기 목록은 접속 IP를 저장하지 않는다. 서비스 기획서 §5.6의 접속 기록(IP·시각) 보관은 별도 접속 로그로 P0-10(운영·로그 정책)에서 다룬다
- 새 기기 로그인 알림 메일(§6.7 보안 알림)은 기기를 구분할 수단(기기 식별 쿠키)이 없어 아직 없다. 이메일 변경 되돌리기 링크와 함께 후속으로 검토
- 세션 사용 시각은 5분 간격으로만 갱신한다 (기기 목록의 "마지막 사용"은 5분 단위 정확도)
- 회사 설정에는 낙관적 잠금(버전)을 두지 않았다. 같은 관리자가 두 기기에서 동시에 바꾸는 경우 마지막 저장이 이긴다 (설정 변경 이력도 아직 없음)
- 회사 설정 행은 처음 저장할 때 만들고, 없으면 기본값으로 동작한다. 공수 계산(P1-1)은 이 설정의 기준시간·월 기준일수를 읽는다
- 카카오로만 가입한 계정에는 비밀번호 로그인이 없어 비밀번호 재설정·변경·이메일 변경(비밀번호 재확인 필요)을 쓸 수 없고 연동도 해제할 수 없다. "일반 로그인(아이디·비밀번호) 추가" 기능이 필요하다 (§6.1, 후속)
- 인증된 이메일을 주지 않는 카카오 계정의 가입은 받지 않는다. 별도 이메일 입력·인증 흐름은 후속 (§6.7)
- 네이버·구글 로그인은 5단계. 소셜 계정으로 로그인해도 새 기기 로그인 알림은 없다
- 약관·처리방침은 초안이다. 공개 전 전문가 검토로 확정하고 `pendingItems`(보호책임자, 수탁·위탁, 국외 이전, 접속 기록 보관, 요청 처리 기한)를 채운 뒤 버전을 올려 다시 동의를 받는다. 호스팅·이메일·소셜 로그인 공급자가 정해지면 수탁·위탁 현황과 국외 이전 항목도 함께 갱신
- 처리방침 본문은 현재 구현과 일치하도록 작성했다 (접속 IP는 저장하지 않음). 접속 기록 법정 보관을 구현하면 처리방침의 해당 항목도 함께 고친다
- 직원용 개인정보 안내문(동의서) 양식과 업로드 자료 책임 안내문은 1단계·2단계에서 추가
- 해지 삭제(`pnpm operator purge-due`)와 백업·복구 시험은 `ops/crontab.example`에 주기 실행 예시만 있다. 실제 서버의 스케줄러 연결은 운영 환경 구성 때 한다. 그 전까지 유예가 끝난 회사는 `CLOSING` 상태로 남아 로그인이 막힌 채 보관된다
- 삭제 대상은 `purgePolicy.ts`의 표로 정한다 (삭제·익명화·보존). 1단계에서 업무 테이블(직원·일지·사진 등)을 만들면 반드시 이 표에 등록해야 하고, 누락은 스키마 검사 테스트가 막는다. 업로드 파일(사진)은 DB 행 삭제와 별개로 저장소 객체도 지워야 한다 (1단계에서 구현)
- 백업에는 삭제된 회사의 데이터가 보관 기간만큼 남는다. 처리방침의 "삭제 후 백업 보관" 문구와 백업 보관 기간(P0-10)을 맞춰야 한다
- 해지 요청의 취소 링크는 요청한 계정의 이메일로만 간다. 이메일이 없거나(미인증 계정) 메일이 오지 않으면 운영자가 확인해 취소를 도와야 한다 (운영자 CLI에 취소 기능은 아직 없음)
- 해지 요청 메일은 작업 큐로 보낸다. 큐 처리가 늦어도 요청 즉시 로그아웃·로그인 차단은 적용된다
- 백업·복구 시험 도구는 로컬(Docker) 기준이다. 운영에서는 공급자의 자동 백업·시점 복구를 켜고, 서버 밖(다른 디스크·리전)으로 사본을 보내는 일과 운영 환경에서의 복구 시험 1회를 추가해야 한다 (`docs/05-backup-restore.md`). 백업 암호화는 공급자 기능(디스크·백업 암호화)에 맡긴다
- 백업에는 해지·삭제한 회사의 데이터가 보관 기간(30일)만큼 남는다. 처리방침 제3조에 안내했으며 보관 기간을 바꾸면 함께 고친다. 처리방침 본문이 바뀌었으므로 이미 `legal-register`로 등록한 로컬 DB는 `pnpm db:reset`이 필요하다
- 복구 시험 실패 시 알림(운영자 이메일)은 아직 없다. 종료 코드로만 알 수 있어, 모니터링(기술 기획서 §14)을 구성할 때 연결한다
- 운영 기동 검사는 로컬 값 혼입을 막는 최소 검사다. 스테이징 환경의 실제 값과 배포 파이프라인은 공급자 확정 후 정한다
- 공수 계산(`packages/shared/src/workUnits.ts`)은 저장을 분 정수로, 표시·집계를 MD·MM·소진율로 나눈다. 여러 기록은 분을 먼저 합산한 뒤 나눠 오차가 쌓이지 않게 한다. 프로젝트별 기준시간 재정의(§9.5)는 함수가 기준시간을 인자로 받으므로 호출하는 쪽(P1-5 이후)에서 프로젝트 값을 넘기면 된다
- 소진율 경고 기준(80%·100%)과 진행률 대비 경고는 계산 함수만 있고 판정은 3단계(P3)에서 회사 설정과 함께 만든다
- 선택 목록은 삭제 없이 숨기기만 한다. 직원·프로젝트·일지는 항목 이름이 아니라 `id`를 참조해야 이름 변경이 기록 전체에 반영되고, 숨긴 항목도 과거 기록에서는 계속 보인다 (P1-3부터 적용). 비슷한 이름을 하나로 합치는 기능(서비스 기획서 §11.2의 합치기)은 참조가 생긴 뒤 필요해지는 시점에 추가한다
- 일지·직원 입력 화면에서 "목록에 없으면 그 자리에서 추가"(서비스 기획서 §11.2, §14)는 이 API의 `POST /company/options`를 그대로 쓰면 되며 화면 연결은 P1-3·P1-9에서 한다
- 자재 분류·자격 종류 목록(서비스 기획서 §17)은 `OptionKind`에 값을 추가해 같은 방식으로 확장한다 (P2-4, P4)
- 웹 개발 서버의 프록시 대상은 `API_PROXY_TARGET`로 바꿀 수 있다 (3000번 포트를 다른 프로그램이 쓰는 경우)
- 직원 서류·자격(서비스 기획서 §8.4)은 파일 업로드(P2-1)와 만료 알림이 필요해 4단계(P4)로 둔다. 직원 카드의 투입 이력·이번 달 공수(§8.5)는 투입·일지(P1-7, P1-8)와 집계(P1-10)가 생기면 카드에 붙인다
- 직원이 요청하는 개인정보 내보내기·정정·삭제(퇴사자는 익명화, 서비스 기획서 §13.3)와 보존기간 경과 후 익명화는 아직 없다. 직원 테이블에 삭제 권한을 주지 않은 상태이므로, 익명화는 별도 작업(전용 권한)으로 추가한다. 처리방침의 "직원 정보" 항목은 기존 안내와 일치한다
- 직원 카드 열람·수정 기록(감사 로그, 서비스 기획서 §13.1)은 아직 없다. 개인정보(생년월일·연락처)를 보여 주는 카드 조회 기록은 감사 로그 작업에서 함께 만든다
- 직원 목록은 한 번에 모두 내려 준다 (회사당 500명 상한). 직원이 많아져 느려지면 쪽 나누기를 추가한다
- 같은 이름의 직원(동명이인)은 막지 않는다. 목록에서 직책·직종·구분으로 구분하고, 같은 이름 등록 경고는 필요해지면 추가한다
- 퇴사 직원이 신규 투입·일지 입력에서 빠지는 규칙은 투입(P1-7)·일지(P1-8)에서 적용한다 (현재는 상태만 기록)
- 명부에는 업체 구분(고객·협력업체·공급처)이 있어 프로젝트의 고객 칸에는 고객만, 자재 반입처에는 공급처만 고르게 한다 (P1-5, P2-4에서 구분을 검사). 같은 업체가 고객이면서 공급처인 경우는 구분별로 따로 등록한다
- 프로젝트 입력 중 "명부에 없으면 그 자리에서 추가"(서비스 기획서 §11.2 취지)는 `POST /partners`를 그대로 쓰면 되며 화면 연결은 P1-5에서 한다. 비슷한 상호를 하나로 합치는 기능은 참조가 생긴 뒤 필요해지면 추가한다
- 명부의 담당자 이름·연락처는 제3자 정보라 목록에서는 담당자 이름까지만 보인다 (서비스 기획서 §5 제3자 정보 취급). 카드 열람 기록(감사 로그)은 직원 카드와 함께 이후에 만든다
- 명부는 한 번에 모두 내려 준다 (회사당 1000곳 상한). 많아져 느려지면 쪽 나누기를 추가한다
- 프로젝트 등록은 서비스 기획서 §10.2의 "등록 때 필수" 항목(프로젝트명·현장·고객·담당자·계약일·예정 기간)을 모두 요구한다. 현장에서 빠르게 등록하려면 필수 항목을 줄이는 방안(계약일 선택 등)을 실사용 시험 뒤 검토한다
- 프로젝트 기본정보 수정 이력(기간·담당 변경 기록)과 기간 변경 사유는 아직 없다. 기간 변경 이력과 "기간 밖 투입·일지 불가" 규칙은 투입(P1-7)에서, 상태·담당 변경 이력은 P1-6에서 만든다. 그 전까지 예정 기간은 제한 없이 고칠 수 있다
- 상태별 수정 제한(종료·취소는 수정 불가, 보증 중은 일부만 등)은 상태 전환이 생기는 P1-6에서 적용한다. 지금은 시드로만 다양한 상태가 존재하고 화면에서 바꿀 수 없다
- 프로젝트 복제, 계획 공수, 필요 자격, 공수 입력 방식·기준시간 재정의, 보증, 계약서·첨부는 각각 3·4단계와 파일 기능(P2)에서 추가한다
- 프로젝트 코드의 연도는 등록한 날(서울 기준)이다. 코드 형식을 회사가 바꾸는 기능(서비스 기획서 §18.1 #10)은 아직 없다
- T0-4 격리 검증용 샘플 테이블 `memos`는 삭제했다. 메모함·프로젝트 메모 노트(P2-3)가 정식 테이블로 새로 만든다. 격리 테스트는 직원·명부·프로젝트로 옮겼다
- 프로젝트 목록은 한 번에 모두 내려 준다. 많아져 느려지면 쪽 나누기를 추가한다
- 상태 전환 중 **완료 → 보증 중 → 종료**와 종료 프로젝트 **재오픈**은 보증 기능(4단계)과 함께 만든다. 그 전까지 완료한 프로젝트는 더 바꿀 수 없고, 보증 중·종료 상태는 시드·테스트에서만 만들어진다 (수정 제한 규칙은 미리 구현해 두었다)
- 진행 → 완료의 추가 조건(임시 저장된 작업일지 확인, 진행률 100% 안내, 남은 자재 확인)과 완료 때 프로젝트 요약 생성(서비스 기획서 §10.3, §10.7)은 일지(P1-8)·자재(P2-4)가 생기면 `validateProjectTransition`에 더한다
- 상태별 허용 작업 표 중 투입 배정·작업일지·자재·사진 같은 항목의 상태별 제한은 각 기능을 만들 때 같은 상태 규칙을 적용한다 (중단 중 신규 투입 차단은 P1-7)
- 상태 이름을 회사가 바꾸는 기능(서비스 기획서 §10.3)은 아직 없다. 지금은 기본 이름만 쓴다
- 상태 변경 이력의 변경자는 DB에 기록되지만 화면에는 보이지 않는다 (회사당 관리자 한 명이라 지금은 구분할 필요가 없음, 사용자가 늘면 표시)
- 프로젝트 기본정보 변경 이력(필드별 변경 전·후 값)은 아직 없다. 상태 변경 이력만 있다 (서비스 기획서 §10.2)
- 실수로 상태를 잘못 바꿨을 때 되돌리는 기능은 없다. 시작 날짜를 잘못 넣었다면 이력과 실제 시작일을 정정하는 방법이 필요하다(실사용 시험 뒤 판단, 운영자 지원으로 우선 처리)
- 투입 경고(겹침)는 "기간이 겹치는지"만 본다. 같은 직원의 하루 합계 공수가 기준을 넘는지(예: 1.0 + 1.0 = 2.0)는 일지를 저장할 때(P1-8) 검사한다. 인력 배치 캘린더(직원 × 날짜 표, "이번 주 비는 사람", 배치 변경 이력)는 3단계(P3)에서 만든다
- 투입의 변경 이력(누가 언제 기간을 바꿨는지)은 아직 없다. 지금은 취소 표시와 마지막 수정 시각만 남는다. 프로젝트 예정 기간 변경 이력만 있다
- 프로젝트 필요 자격과 직원 자격 만료 경고(서비스 기획서 §8.4)는 서류·자격 기능(4단계)과 함께 투입 검사에 더한다
- 보증 중 프로젝트의 "사후 작업만 투입"은 보증 기능(4단계)과 함께 연다. 지금은 완료·보증 중·종료·취소 프로젝트에 투입할 수 없다
- 투입 계획 공수는 분으로 저장하고 MD로 환산할 때 회사 기준시간을 쓴다. 기준시간을 나중에 바꾸면 같은 분이 다른 MD로 보인다 (프로젝트별 기준시간 재정의는 3단계)
- 프로젝트 전체 계획 공수(서비스 기획서 §10.2, "인원별 계획 공수 합계로 대체 가능")는 투입별 계획 공수의 합으로 집계(P1-10)한다
- 직원이 퇴사해도 이미 있는 투입은 그대로 남고 퇴사 경고만 붙는다 (종료일 조정은 관리자가 직접 한다)
- 일지 API는 날짜 하나씩 저장한다. "여러 일자 한꺼번에 입력"과 "어제와 동일" 복사(서비스 기획서 §9.3)는 화면(P1-9)이 날짜별로 이 API를 호출해 처리한다 (한 건이 실패해도 나머지는 저장되며 결과를 날짜별로 보여 준다). 일괄 저장용 API가 필요해지면 그때 추가한다
- 하루 합계 경고 기준(기준시간의 1.5배)과 지연 입력 기준(3일)은 제안값이다. 회사별로 바꾸는 설정과 경고 기준(§10.4)은 3단계(P3)에서 설정 화면으로 뺀다
- 일지에는 사진·자재가 아직 없다 (2단계 P2-2, P2-4). 월 공수 확정으로 잠긴 달의 일지 수정 제한(서비스 기획서 §9.4, §13.2)은 4단계에서 월 확정과 함께 적용한다
- 일지 수정 이력은 일지 전체의 이전 값 스냅샷이다 (필드별 차이 표시는 화면에서 계산). 이력에는 변경자가 DB에 있지만 응답에는 싣지 않는다 (회사당 관리자 한 명)
- 일지 삭제 기능은 없다. 잘못 만든 임시 저장 일지는 내용을 비워 둘 수 있고 (집계에서 제외), 정말 지울 수 있게 할지는 실사용 시험 뒤 정한다
- 진행 → 완료 전환 때 임시 저장 일지가 남아 있으면 확인하는 규칙(서비스 기획서 §10.3)은 이제 일지가 있으므로 `validateProjectTransition`에 더할 수 있다. P1-9 화면에는 아직 붙이지 않았다 (프로젝트 상태 전환 화면에서 임시 저장 일지 수를 보여 주는 작업으로 남김)
- 저장 전 투입 자동 추가는 하루짜리 투입을 만든다. 같은 직원이 여러 날 자동 추가되면 투입 목록이 잘게 쪼개질 수 있어, 필요하면 투입 합치기를 추가한다

## P1-9 메모

- 일지 입력은 `/work-logs?project=<id>&date=<날짜>` 화면이다 (메뉴 "일지", 프로젝트 카드의 "일지 입력"). 프로젝트를 고르지 않으면 진행 중인 첫 프로젝트가 열린다
- 일지가 없는 날은 그날 투입된 직원이 공수 1.0으로 미리 채워진 행으로 열린다. 직원 단위 출근 체크(결근은 공수가 저장되지 않음), 작업 구분 일괄 지정, 반일·하루·연장 버튼, 작업 구분 나누기, 투입 없는 직원 추가를 지원한다
- "어제와 동일"은 직전 날짜가 아니라 **가장 최근 일지**(이 날짜보다 앞선 것)를 복사한다 (퇴사 직원은 제외, 저장 전 확인 문구 표시). 여러 날짜 저장은 날짜마다 PUT을 순서대로 호출하고, 이미 일지가 있는 날은 건너뛴 결과를 날짜별로 보여 준다
- 저장 결과(버전·지연 입력·하루 합계 경고·자동 추가된 투입)는 폼 아래에 표시한다. 충돌(409)은 "최신 내용 불러오기" 버튼으로 편집 상태를 새로 만든다
- 수정 이력은 접힌 영역을 펼칠 때만 불러온다 (버전 2 이상인 일지에만 표시)

## P1-10 메모

- 집계는 **저장된 일지만** 반영한다. 임시 저장 일지는 건수만 알려 준다 (서비스 기획서 §9.4). API는 분 단위만 주고 MD·MM·소진율은 화면이 회사 설정(기준시간·월 기준일수)으로 환산한다
- `GET /projects/{id}/work-summary?from&to&unit=week|month`: 직원별(작업한 날·공수·계획)·작업 구분별·기간별(주는 월요일, 월은 1일 기준). 계산은 `summarizeProjectWork`(shared)로 서버와 목업이 같다
- 소진율의 계획은 취소하지 않은 투입의 계획 공수 합이다. 기간을 고르면 계획과 비교할 수 없어 소진율을 표시하지 않는다. 투입에 계획 공수가 없으면 "계획 없음"
- `GET /employees/{id}/work-history`: 프로젝트별 투입 기간(취소하지 않은 투입의 처음~끝)·작업한 날·공수·최근 작업일과 이번 달·올해 공수 (서울 기준). 프로젝트 카드에 "공수 집계", 직원 카드에 "투입 이력"으로 붙였다
- 기획서 §9.5 예시(20일 중 연장 2일 = 21.0 MD, 0.95 MM)를 shared·화면 단위 테스트로 고정했다
- 아직 없음: 일자별 타임라인·작업 내용 검색, 월 공수 확정과 엑셀 내보내기 (4단계), 프로젝트별 공수 방식 재정의 (3단계)
