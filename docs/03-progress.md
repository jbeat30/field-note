## 4. 이어서 작업하는 방법

```bash
cd /Users/gangjubich/new_project/field-note
git checkout feature/0.3.0 && git pull origin feature/0.3.0
git checkout -b feat-env-logger          # 작업명 중심 브랜치
# ...작업, 커밋(타입: 한국어 설명)...
git push -u origin feat-env-logger
gh pr create --base feature/0.3.0        # CI 통과 후 squash 머지
```

- 커밋 전 훅이 ESLint·Prettier를 실행한다. 클론 직후 1회 `pnpm prepare` 필요
- 검증: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm build`
- 로컬 확인: `pnpm dev` → web http://localhost:5173, api http://localhost:3000/api/v1/health

## 7. 알려진 사항

- `docs/planning/`의 두 기획서는 원본 그대로이며 Prettier 대상에서 제외
- T0-4의 Testcontainers 격리 테스트는 Docker가 필요하다 (로컬은 Docker Desktop, CI는 ubuntu 러너). 앱 계정 비밀번호는 `pnpm db:setup`이 환경 변수 값으로 설정하며 마이그레이션 파일에는 두지 않는다
- 멱등 키 저장소는 메모리 구현이다(서버 재시작·다중 서버에서 기록이 사라짐). 운영 전에 DB 저장소로 교체 필요
- 세션 저장소 기본값(`createApp`)은 메모리 구현이며 운영 기동(`main.ts`)에서는 PostgreSQL 저장소를 주입한다
- 만료 세션 정리(`deleteExpired`)를 호출하는 작업은 P0-4(pg-boss)에서 연결한다
- 세션 발급(`create`)을 호출하는 로그인 흐름은 P0-3에서 연결한다. `sessions`는 P0-1부터 `(company_id, user_id)`로 `users`를 참조한다
- 약관 문서(`legal_documents`)의 실제 본문·버전 등록은 P0-9(처리방침 페이지)와 P0-2(운영 경로)에서 한다. 지금은 구조만 있다
- `GET /session`(T0-5 샘플)은 회사 ID를 응답에 담는다. 서비스 기획서 §5.1 #5(회사 식별값은 화면·주소에 노출하지 않음)와 맞지 않아 `/me`로 대체되면 제거한다
- 목업 모드의 가짜 서버(`apps/web/src/mocks`)는 실제 백엔드가 모든 계약을 구현한 뒤 개발용 보조로만 남긴다
- 시드는 회사 설정(P0-8)과 초대(P0-2) 테이블이 없어 회사·계정·약관·동의 이력만 입력한다. 해당 테이블이 생기면 `seedDemoData`에 추가한다
- 로컬 `.env`는 `pnpm env:init`으로 만든다. 기존 `.env`를 새 값으로 바꾸면 DB 컨테이너의 저장된 비밀번호와 어긋나므로 `pnpm db:reset` 필요
- 운영자 접속 정보(`DATABASE_OPERATOR_URL`)는 api 서버 설정(`env.ts`)에 두지 않는다. 운영에서는 운영자 PC에만 보관
- 초대 사용 처리(`consume`)와 관리자 계정 활성화·약관 동의 기록은 P0-3 가입 API에서 한 트랜잭션으로 연결한다
- `legal_documents`에 약관 본문·제목은 없다 (제목·경로는 `LEGAL_DOCUMENT_META`, 본문은 P0-9에서 등록)
- 로그인 잠금은 계정 단위(5회·15분)라 타인이 아이디를 알면 일시적으로 잠글 수 있다. IP 단위 속도 제한(분당 10회)과 함께 쓰며, 문제가 되면 잠금 시간 조정이나 알림을 검토한다
- `GET /session`(T0-5 샘플)은 `/me`로 대체되어 제거했다
- 이메일 발송은 SMTP 한 가지 방식이다. 운영 메일 서비스가 정해지면 접속 정보만 바꾸고, 발신 도메인의 SPF·DKIM·DMARC 설정과 메일 서비스의 수탁자 개인정보 조항 확인이 필요하다
- 작업 큐는 가입 인증 메일에만 쓴다. 만료 세션·인증 코드 정리 작업(`deleteExpired`)은 정리 작업이 필요해지는 시점에 큐 스케줄로 연결한다
- 인증 메일 제목에 코드를 포함한다(알림에서 바로 확인). 잠금 화면 노출이 우려되면 제목에서 제외 가능
- 이메일 변경 알림에는 서비스 기획서 §6.7의 "되돌리기 링크"가 없다. 변경 사실만 이전 주소로 알리며, 되돌리기(변경 취소 토큰)는 P0-5 후속으로 남김
- 보안 알림 메일 작업은 받는 주소를 큐 작업에 담는다(큐 계정은 업무 테이블을 읽을 수 없어서). 큐의 보관 기간 정책은 운영 전에 점검
- 재설정 요청은 계정 존재 여부를 응답 내용으로는 숨기지만 처리 시간 차이(조회·큐 등록)는 완전히 없애지 않았다. IP 단위 속도 제한(분당 5회)과 함께 사용
- 소셜 로그인만 쓰는 계정의 비밀번호 재설정·변경은 P0-7에서 정책 결정 필요 (현재는 일반 로그인 계정만 대상)
- 카카오 로그인은 제공자 추상화와 로컬 가짜 제공자로 구현·테스트를 마쳤다. 카카오 앱 등록은 상용 서버 작업 때 하고, 그때 키와 리다이렉트 주소만 설정한다. 실제 카카오 통신(코드 교환·사용자 정보 조회)은 앱 등록 후 처음 확인해야 한다 (README "소셜 로그인(카카오)" 참고)
- 기기 목록은 접속 IP를 저장하지 않는다. 서비스 기획서 §5.6의 접속 기록(IP·시각) 보관은 별도 접속 로그로 P0-10(운영·로그 정책)에서 다룬다
- 새 기기 로그인 알림 메일(§6.7 보안 알림)은 기기를 구분할 수단(기기 식별 쿠키)이 없어 아직 없다. 이메일 변경 되돌리기 링크와 함께 후속으로 검토
- 세션 사용 시각은 5분 간격으로만 갱신한다 (기기 목록의 "마지막 사용"은 5분 단위 정확도)
- 회사 설정에는 낙관적 잠금(버전)을 두지 않았다. 같은 관리자가 두 기기에서 동시에 바꾸는 경우 마지막 저장이 이긴다 (설정 변경 이력도 아직 없음)
- 회사 설정 행은 처음 저장할 때 만들고, 없으면 기본값으로 동작한다. 공수 계산(P1-1)은 이 설정의 기준시간·월 기준일수를 읽는다
- 카카오로만 가입한 계정에는 비밀번호 로그인이 없어 비밀번호 재설정·변경·이메일 변경(비밀번호 재확인 필요)을 쓸 수 없고 연동도 해제할 수 없다. "일반 로그인(아이디·비밀번호) 추가" 기능이 필요하다 (§6.1, 후속)
- 인증된 이메일을 주지 않는 카카오 계정의 가입은 받지 않는다. 별도 이메일 입력·인증 흐름은 후속 (§6.7)
- 네이버·구글 로그인은 5단계. 소셜 계정으로 로그인해도 새 기기 로그인 알림은 없다
- 약관·처리방침은 초안이다. 공개 전 전문가 검토로 확정하고 `pendingItems`(보호책임자, 수탁·위탁, 국외 이전, 접속 기록 보관, 요청 처리 기한)를 채운 뒤 버전을 올려 다시 동의를 받는다. 호스팅·이메일·소셜 로그인 공급자가 정해지면 수탁·위탁 현황과 국외 이전 항목도 함께 갱신
- 처리방침 본문은 현재 구현과 일치하도록 작성했다 (접속 IP는 저장하지 않음). 접속 기록 법정 보관을 구현하면 처리방침의 해당 항목도 함께 고친다
- 직원용 개인정보 안내문(동의서) 양식과 업로드 자료 책임 안내문은 1단계·2단계에서 추가
- 해지 삭제(`pnpm operator purge-due`)와 백업·복구 시험은 `ops/crontab.example`에 주기 실행 예시만 있다. 실제 서버의 스케줄러 연결은 운영 환경 구성 때 한다. 그 전까지 유예가 끝난 회사는 `CLOSING` 상태로 남아 로그인이 막힌 채 보관된다
- 삭제 대상은 `purgePolicy.ts`의 표로 정한다 (삭제·익명화·보존). 1단계에서 업무 테이블(직원·일지·사진 등)을 만들면 반드시 이 표에 등록해야 하고, 누락은 스키마 검사 테스트가 막는다. 업로드 파일(사진)은 DB 행 삭제와 별개로 저장소 객체도 지워야 한다 (1단계에서 구현)
- 백업에는 삭제된 회사의 데이터가 보관 기간만큼 남는다. 처리방침의 "삭제 후 백업 보관" 문구와 백업 보관 기간(P0-10)을 맞춰야 한다
- 해지 요청의 취소 링크는 요청한 계정의 이메일로만 간다. 이메일이 없거나(미인증 계정) 메일이 오지 않으면 운영자가 확인해 취소를 도와야 한다 (운영자 CLI에 취소 기능은 아직 없음)
- 해지 요청 메일은 작업 큐로 보낸다. 큐 처리가 늦어도 요청 즉시 로그아웃·로그인 차단은 적용된다
- 백업·복구 시험 도구는 로컬(Docker) 기준이다. 운영에서는 공급자의 자동 백업·시점 복구를 켜고, 서버 밖(다른 디스크·리전)으로 사본을 보내는 일과 운영 환경에서의 복구 시험 1회를 추가해야 한다 (`docs/05-backup-restore.md`). 백업 암호화는 공급자 기능(디스크·백업 암호화)에 맡긴다
- 백업에는 해지·삭제한 회사의 데이터가 보관 기간(30일)만큼 남는다. 처리방침 제3조에 안내했으며 보관 기간을 바꾸면 함께 고친다. 처리방침 본문이 바뀌었으므로 이미 `legal-register`로 등록한 로컬 DB는 `pnpm db:reset`이 필요하다
- 복구 시험 실패 시 알림(운영자 이메일)은 아직 없다. 종료 코드로만 알 수 있어, 모니터링(기술 기획서 §14)을 구성할 때 연결한다
- 운영 기동 검사는 로컬 값 혼입을 막는 최소 검사다. 스테이징 환경의 실제 값과 배포 파이프라인은 공급자 확정 후 정한다
- 공수 계산(`packages/shared/src/workUnits.ts`)은 저장을 분 정수로, 표시·집계를 MD·MM·소진율로 나눈다. 여러 기록은 분을 먼저 합산한 뒤 나눠 오차가 쌓이지 않게 한다. 프로젝트별 기준시간 재정의(§9.5)는 함수가 기준시간을 인자로 받으므로 호출하는 쪽(P1-5 이후)에서 프로젝트 값을 넘기면 된다
- 소진율 경고 기준(80%·100%)과 진행률 대비 경고는 계산 함수만 있고 판정은 3단계(P3)에서 회사 설정과 함께 만든다
- 선택 목록은 삭제 없이 숨기기만 한다. 직원·프로젝트·일지는 항목 이름이 아니라 `id`를 참조해야 이름 변경이 기록 전체에 반영되고, 숨긴 항목도 과거 기록에서는 계속 보인다 (P1-3부터 적용). 비슷한 이름을 하나로 합치는 기능(서비스 기획서 §11.2의 합치기)은 참조가 생긴 뒤 필요해지는 시점에 추가한다
- 일지·직원 입력 화면에서 "목록에 없으면 그 자리에서 추가"(서비스 기획서 §11.2, §14)는 이 API의 `POST /company/options`를 그대로 쓰면 되며 화면 연결은 P1-3·P1-9에서 한다
- 자재 분류·자격 종류 목록(서비스 기획서 §17)은 `OptionKind`에 값을 추가해 같은 방식으로 확장한다 (P2-4, P4)
- 웹 개발 서버의 프록시 대상은 `API_PROXY_TARGET`로 바꿀 수 있다 (3000번 포트를 다른 프로그램이 쓰는 경우)
- 직원 서류·자격(서비스 기획서 §8.4)은 파일 업로드(P2-1)와 만료 알림이 필요해 4단계(P4)로 둔다. 직원 카드의 투입 이력·이번 달 공수(§8.5)는 투입·일지(P1-7, P1-8)와 집계(P1-10)가 생기면 카드에 붙인다
- 직원이 요청하는 개인정보 내보내기·정정·삭제(퇴사자는 익명화, 서비스 기획서 §13.3)와 보존기간 경과 후 익명화는 아직 없다. 직원 테이블에 삭제 권한을 주지 않은 상태이므로, 익명화는 별도 작업(전용 권한)으로 추가한다. 처리방침의 "직원 정보" 항목은 기존 안내와 일치한다
- 직원 카드 열람·수정 기록(감사 로그, 서비스 기획서 §13.1)은 아직 없다. 개인정보(생년월일·연락처)를 보여 주는 카드 조회 기록은 감사 로그 작업에서 함께 만든다
- 직원 목록은 한 번에 모두 내려 준다 (회사당 500명 상한). 직원이 많아져 느려지면 쪽 나누기를 추가한다
- 같은 이름의 직원(동명이인)은 막지 않는다. 목록에서 직책·직종·구분으로 구분하고, 같은 이름 등록 경고는 필요해지면 추가한다
- 퇴사 직원이 신규 투입·일지 입력에서 빠지는 규칙은 투입(P1-7)·일지(P1-8)에서 적용한다 (현재는 상태만 기록)
- 명부에는 업체 구분(고객·협력업체·공급처)이 있어 프로젝트의 고객 칸에는 고객만, 자재 반입처에는 공급처만 고르게 한다 (P1-5, P2-4에서 구분을 검사). 같은 업체가 고객이면서 공급처인 경우는 구분별로 따로 등록한다
- 프로젝트 입력 중 "명부에 없으면 그 자리에서 추가"(서비스 기획서 §11.2 취지)는 `POST /partners`를 그대로 쓰면 되며 화면 연결은 P1-5에서 한다. 비슷한 상호를 하나로 합치는 기능은 참조가 생긴 뒤 필요해지면 추가한다
- 명부의 담당자 이름·연락처는 제3자 정보라 목록에서는 담당자 이름까지만 보인다 (서비스 기획서 §5 제3자 정보 취급). 카드 열람 기록(감사 로그)은 직원 카드와 함께 이후에 만든다
- 명부는 한 번에 모두 내려 준다 (회사당 1000곳 상한). 많아져 느려지면 쪽 나누기를 추가한다
- 프로젝트 등록은 서비스 기획서 §10.2의 "등록 때 필수" 항목(프로젝트명·현장·고객·담당자·계약일·예정 기간)을 모두 요구한다. 현장에서 빠르게 등록하려면 필수 항목을 줄이는 방안(계약일 선택 등)을 실사용 시험 뒤 검토한다
- 프로젝트 기본정보 수정 이력(기간·담당 변경 기록)과 기간 변경 사유는 아직 없다. 기간 변경 이력과 "기간 밖 투입·일지 불가" 규칙은 투입(P1-7)에서, 상태·담당 변경 이력은 P1-6에서 만든다. 그 전까지 예정 기간은 제한 없이 고칠 수 있다
- 상태별 수정 제한(종료·취소는 수정 불가, 보증 중은 일부만 등)은 상태 전환이 생기는 P1-6에서 적용한다. 지금은 시드로만 다양한 상태가 존재하고 화면에서 바꿀 수 없다
- 프로젝트 복제, 계획 공수, 필요 자격, 공수 입력 방식·기준시간 재정의, 보증, 계약서·첨부는 각각 3·4단계와 파일 기능(P2)에서 추가한다
- 프로젝트 코드의 연도는 등록한 날(서울 기준)이다. 코드 형식을 회사가 바꾸는 기능(서비스 기획서 §18.1 #10)은 아직 없다
- T0-4 격리 검증용 샘플 테이블 `memos`는 삭제했다. 메모함·프로젝트 메모 노트(P2-3)가 정식 테이블로 새로 만든다. 격리 테스트는 직원·명부·프로젝트로 옮겼다
- 프로젝트 목록은 한 번에 모두 내려 준다. 많아져 느려지면 쪽 나누기를 추가한다
- 상태 전환 중 **완료 → 보증 중 → 종료**와 종료 프로젝트 **재오픈**은 보증 기능(4단계)과 함께 만든다. 그 전까지 완료한 프로젝트는 더 바꿀 수 없고, 보증 중·종료 상태는 시드·테스트에서만 만들어진다 (수정 제한 규칙은 미리 구현해 두었다)
- 진행 → 완료의 추가 조건(임시 저장된 작업일지 확인, 진행률 100% 안내, 남은 자재 확인)과 완료 때 프로젝트 요약 생성(서비스 기획서 §10.3, §10.7)은 일지(P1-8)·자재(P2-4)가 생기면 `validateProjectTransition`에 더한다
- 상태별 허용 작업 표 중 투입 배정·작업일지·자재·사진 같은 항목의 상태별 제한은 각 기능을 만들 때 같은 상태 규칙을 적용한다 (중단 중 신규 투입 차단은 P1-7)
- 상태 이름을 회사가 바꾸는 기능(서비스 기획서 §10.3)은 아직 없다. 지금은 기본 이름만 쓴다
- 상태 변경 이력의 변경자는 DB에 기록되지만 화면에는 보이지 않는다 (회사당 관리자 한 명이라 지금은 구분할 필요가 없음, 사용자가 늘면 표시)
- 프로젝트 기본정보 변경 이력(필드별 변경 전·후 값)은 아직 없다. 상태 변경 이력만 있다 (서비스 기획서 §10.2)
- 실수로 상태를 잘못 바꿨을 때 되돌리는 기능은 없다. 시작 날짜를 잘못 넣었다면 이력과 실제 시작일을 정정하는 방법이 필요하다(실사용 시험 뒤 판단, 운영자 지원으로 우선 처리)
- 투입 경고(겹침)는 "기간이 겹치는지"만 본다. 같은 직원의 하루 합계 공수가 기준을 넘는지(예: 1.0 + 1.0 = 2.0)는 일지를 저장할 때(P1-8) 검사한다. 인력 배치 캘린더(직원 × 날짜 표, "이번 주 비는 사람", 배치 변경 이력)는 3단계(P3)에서 만든다
- 투입의 변경 이력(누가 언제 기간을 바꿨는지)은 아직 없다. 지금은 취소 표시와 마지막 수정 시각만 남는다. 프로젝트 예정 기간 변경 이력만 있다
- 프로젝트 필요 자격과 직원 자격 만료 경고(서비스 기획서 §8.4)는 서류·자격 기능(4단계)과 함께 투입 검사에 더한다
- 보증 중 프로젝트의 "사후 작업만 투입"은 보증 기능(4단계)과 함께 연다. 지금은 완료·보증 중·종료·취소 프로젝트에 투입할 수 없다
- 투입 계획 공수는 분으로 저장하고 MD로 환산할 때 회사 기준시간을 쓴다. 기준시간을 나중에 바꾸면 같은 분이 다른 MD로 보인다 (프로젝트별 기준시간 재정의는 3단계)
- 프로젝트 전체 계획 공수(서비스 기획서 §10.2, "인원별 계획 공수 합계로 대체 가능")는 투입별 계획 공수의 합으로 집계(P1-10)한다
- 직원이 퇴사해도 이미 있는 투입은 그대로 남고 퇴사 경고만 붙는다 (종료일 조정은 관리자가 직접 한다)
- 일지 API는 날짜 하나씩 저장한다. "여러 일자 한꺼번에 입력"과 "어제와 동일" 복사(서비스 기획서 §9.3)는 화면(P1-9)이 날짜별로 이 API를 호출해 처리한다 (한 건이 실패해도 나머지는 저장되며 결과를 날짜별로 보여 준다). 일괄 저장용 API가 필요해지면 그때 추가한다
- 하루 합계 경고 기준(기준시간의 1.5배)과 지연 입력 기준(3일)은 제안값이다. 회사별로 바꾸는 설정과 경고 기준(§10.4)은 3단계(P3)에서 설정 화면으로 뺀다
- 일지에는 사진·자재가 아직 없다 (2단계 P2-2, P2-4). 월 공수 확정으로 잠긴 달의 일지 수정 제한(서비스 기획서 §9.4, §13.2)은 4단계에서 월 확정과 함께 적용한다
- 일지 수정 이력은 일지 전체의 이전 값 스냅샷이다 (필드별 차이 표시는 화면에서 계산). 이력에는 변경자가 DB에 있지만 응답에는 싣지 않는다 (회사당 관리자 한 명)
- 일지 삭제 기능은 없다. 잘못 만든 임시 저장 일지는 내용을 비워 둘 수 있고 (집계에서 제외), 정말 지울 수 있게 할지는 실사용 시험 뒤 정한다
- 진행 → 완료 전환 때 임시 저장 일지가 남아 있으면 확인하는 규칙(서비스 기획서 §10.3)은 이제 일지가 있으므로 `validateProjectTransition`에 더할 수 있다. P1-9 화면에는 아직 붙이지 않았다 (프로젝트 상태 전환 화면에서 임시 저장 일지 수를 보여 주는 작업으로 남김)
- 저장 전 투입 자동 추가는 하루짜리 투입을 만든다. 같은 직원이 여러 날 자동 추가되면 투입 목록이 잘게 쪼개질 수 있어, 필요하면 투입 합치기를 추가한다

## P1-9 메모

- 일지 입력은 `/work-logs?project=<id>&date=<날짜>` 화면이다 (메뉴 "일지", 프로젝트 카드의 "일지 입력"). 프로젝트를 고르지 않으면 진행 중인 첫 프로젝트가 열린다
- 일지가 없는 날은 그날 투입된 직원이 공수 1.0으로 미리 채워진 행으로 열린다. 직원 단위 출근 체크(결근은 공수가 저장되지 않음), 작업 구분 일괄 지정, 반일·하루·연장 버튼, 작업 구분 나누기, 투입 없는 직원 추가를 지원한다
- "어제와 동일"은 직전 날짜가 아니라 **가장 최근 일지**(이 날짜보다 앞선 것)를 복사한다 (퇴사 직원은 제외, 저장 전 확인 문구 표시). 여러 날짜 저장은 날짜마다 PUT을 순서대로 호출하고, 이미 일지가 있는 날은 건너뛴 결과를 날짜별로 보여 준다
- 저장 결과(버전·지연 입력·하루 합계 경고·자동 추가된 투입)는 폼 아래에 표시한다. 충돌(409)은 "최신 내용 불러오기" 버튼으로 편집 상태를 새로 만든다
- 수정 이력은 접힌 영역을 펼칠 때만 불러온다 (버전 2 이상인 일지에만 표시)

## P1-10 메모

- 집계는 **저장된 일지만** 반영한다. 임시 저장 일지는 건수만 알려 준다 (서비스 기획서 §9.4). API는 분 단위만 주고 MD·MM·소진율은 화면이 회사 설정(기준시간·월 기준일수)으로 환산한다
- `GET /projects/{id}/work-summary?from&to&unit=week|month`: 직원별(작업한 날·공수·계획)·작업 구분별·기간별(주는 월요일, 월은 1일 기준). 계산은 `summarizeProjectWork`(shared)로 서버와 목업이 같다
- 소진율의 계획은 취소하지 않은 투입의 계획 공수 합이다. 기간을 고르면 계획과 비교할 수 없어 소진율을 표시하지 않는다. 투입에 계획 공수가 없으면 "계획 없음"
- `GET /employees/{id}/work-history`: 프로젝트별 투입 기간(취소하지 않은 투입의 처음~끝)·작업한 날·공수·최근 작업일과 이번 달·올해 공수 (서울 기준). 프로젝트 카드에 "공수 집계", 직원 카드에 "투입 이력"으로 붙였다
- 기획서 §9.5 예시(20일 중 연장 2일 = 21.0 MD, 0.95 MM)를 shared·화면 단위 테스트로 고정했다
- 아직 없음: 일자별 타임라인·작업 내용 검색, 월 공수 확정과 엑셀 내보내기 (4단계), 프로젝트별 공수 방식 재정의 (3단계)

## P1-11 메모

- `routes/isolationEndpoints.test.ts`: 회사 A의 데이터(거래처·직원·프로젝트·투입·일지·수정 이력·기간 변경 이력)를 만들고 회사 B 세션으로 A의 ID를 쓰는 **1단계 모든 엔드포인트(조회·수정·상태 전환·투입 취소·일지 저장)**가 404인지, 로그인 없이는 401인지, A의 데이터가 그대로인지 확인한다
- 새 엔드포인트가 격리 시험에서 빠지지 않게, OpenAPI의 인증 필요 1단계 엔드포인트가 시험 목록에 모두 있는지 검사한다 (없으면 실패)
- B가 자기 데이터를 만들 때 A의 고객·담당자·직종·작업 구분·직원 ID를 끼워 넣거나 투입 자동 추가를 요구해도 거부되고, A의 직원 이력에 B의 기록이 생기지 않음을 확인한다
- DB 수준: 회사 범위 테이블 전체에서 회사 A로 조회할 때 다른 회사 행이 0건이고, 1단계 테이블에는 자기 회사 행이 실제로 보임을 확인한다
- 2단계 이후 엔드포인트(파일·자재 등)는 해당 작업에서 같은 목록에 더한다
