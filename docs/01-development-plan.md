# 1단계. 개발 순서 세부 설계

> 기준: `00-analysis.md`, 서비스 기획서 §16, 기술 기획서 §16
> 원칙: 한 번에 한 덩어리(PR 크기)로 끝내고, 각 덩어리마다 **완료 기준을 테스트로 고정**한다. 새 기능이 추가될 때마다 회사 격리 테스트를 함께 늘린다.

## 0. 진행 규칙

- 작업 단위 ID: `T0-1`(기술 0), `P0-1`(0단계), `P1-1`(1단계) …
- 커밋 메시지: `타입: 한국어 설명` 형식 (`feat` `fix` `docs` `chore` `refactor` `test` `style`)
- 모든 의존성은 정확한 버전으로 고정, 정식 릴리스만 사용
- 코드·주석은 jbeat-conventions를 따른다 (한국어 명사형, 마침표 없음)
- 각 단계 종료 시 `pnpm typecheck && pnpm lint && pnpm test`가 통과해야 한다

## 1. 전체 흐름

```
T0 기술 준비 ─▶ P0 기반 ─▶ P1 직원·프로젝트·투입 ─▶ P2 메모·사진·자재·자료 ─▶ P3 관리·경고
                                                                                    │
   상용 전환 ◀ 1.0.0 로컬 최종 점검 ◀ 0.9.0 이월·5단계 ◀ 0.8.0 UI/UX 리뉴얼 ◀ 0.7.0 P4 보증·확정
```

의존 원칙: **격리(T0-4) → 인증(P0) → 업무 데이터(P1) → 파일(P2)** 순서는 바꿀 수 없다.
화면은 각 단계에서 API가 먼저 완성된 뒤 붙인다.

### 3.1 화면 선행 방침 (0.2.0부터)

눈으로 확인하며 진행하기 위해 **API 계약과 목업을 먼저 만들고 화면을 붙인 뒤, 실제 백엔드(P0-2~P0-8)를 같은 계약에 맞춰 채운다.**

| 순서  | 작업                                                                  | 확인 방법                                    |
| ----- | --------------------------------------------------------------------- | -------------------------------------------- |
| S1    | 계정·설정 API 계약(OpenAPI, 501 스텁) + 웹 목업 서버(msw)·더미 데이터 | `pnpm dev:mock`, 목업이 계약을 지키는 테스트 |
| S2    | 초대 링크 가입(약관 동의·이메일 인증)·로그인 화면 + Storybook         | `pnpm dev:mock`으로 브라우저 확인            |
| S3    | 설정 화면(회사 설정·로그인 기기·로그아웃) + 로그인 가드               | 위와 같음                                    |
| S4    | DB 시드(더미 회사·계정·약관)와 실제 형식의 키 설정                    | `pnpm db:seed`                               |
| P0-2~ | 실제 백엔드 구현. 구현되면 해당 API는 501에서 실제 응답으로 바뀜      | `pnpm dev` + 시드 데이터                     |

- 화면은 목업이든 실제든 같은 API 클라이언트를 쓰므로 백엔드 구현 때 화면을 바꾸지 않는다
- 1단계(직원·프로젝트·일지) 화면도 같은 방식(계약 → 목업 → 화면 → 백엔드)으로 진행한다

### 3.2 0단계 릴리즈 분할

0단계 전체를 한 번에 릴리즈하면 중간 점검까지 너무 길어져 두 버전으로 나눈다. 버전별 종료 기준과 확인 방법은 다음과 같다.

| 버전  | 범위                                                                                                  | 종료 기준                                                                   | 확인 방법                                            |
| ----- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------- |
| 0.2.0 | 화면 선행 S1~S4 + P0-2 ~ P0-8 (운영자 CLI, 가입·로그인, 이메일 인증, 재설정, 기기, 카카오, 회사 설정) | 시드 데이터로 초대 → 가입 → 이메일 인증 → 로그인 → 설정이 실제 DB로 동작    | `pnpm dev`로 브라우저 확인, 두 회사 격리 자동 테스트 |
| 0.3.0 | P0-9(처리방침 페이지 초안) + P0-10(백업 자동화·복구 시험 1회) + P0-11(해지·유예·삭제 골격)            | 0단계 종료 기준: 두 회사 격리가 모든 화면·API에서 유지 + 백업 복구 1회 기록 | 복구 시험 기록, 해지 유예 중 로그인 차단             |

- P0-9의 로그인·가입·설정 화면은 화면 선행(S2·S3)에서 이미 만든다. 0.3.0에는 처리방침 페이지 초안만 남는다

## 6. 로컬 완성 후 상용 전환 (2026-10-12 사용자 결정)

모든 개발은 로컬에서 끝낸 뒤 상용 단계에 들어간다. 소셜 로그인 앱 등록·배포·메일 발송은 상용 단계에서 한다. 개발 순서는 **기능·로직 → UI/UX 리뉴얼 → 이월·5단계 → 로컬 최종 점검 → 상용 전환**이다.

| 버전  | 범위                                        | 내용                                                                             |
| ----- | ------------------------------------------- | -------------------------------------------------------------------------------- |
| 0.7.0 | 4단계 보증·확정 (기능·로직)                 | §7 P4-1 ~ P4-8. 새 화면은 기존 컴포넌트로 만들고 리뉴얼에서 입힌다               |
| 0.8.0 | UI/UX 리뉴얼                                | §7 U-1 ~ U-7. 디자인 시스템 이식, 공통 컴포넌트, 드래그 순서 변경, 화면별 리뉴얼 |
| 0.9.0 | 3단계 이월 항목 + 5단계 중 로컬에서 되는 것 | §7 P5-1 ~ P5-6. 리뉴얼된 컴포넌트로 만든다                                       |
| 1.0.0 | 로컬 최종 점검 → 상용 전환                  | 아래 점검 항목, 이어서 상용 단계                                                 |

**1.0.0 로컬 최종 점검**: 새 기능 포함 전 엔드포인트 격리 재확인, Playwright 핵심 흐름 4~5단계까지 확장과 하루 일지 입력 3분 재측정, 보안 점검(권한·입력 검증·파일 업로드), 접근성·모바일 점검(스토리 a11y 포함), 대용량 성능, 로컬에 현장 데이터 1~2건을 직접 입력한 시나리오 시험과 불편 항목 반영, 운영 이행 체크리스트·환경 변수 목록 정리

**상용 단계**: 배포 공급자 결정(호스팅·이메일·객체 저장소) → 스테이징 → 운영 DB·저장소·메일 연결(버킷 CORS, DB 계정 권한 시험) → 소셜 로그인 앱 등록 → 모니터링·알림 → 백업·복구 운영 시험 → 처리방침 공개 → 전문가 확인 반영(서비스 기획서 §18.2) → 실제 고객 시험
