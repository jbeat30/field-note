# 백업·복구와 환경 분리

> 기준: 기술 기획서 §14 "백업(0단계부터)… 복구해 봐야 백업이다", 서비스 기획서 §5.5 보유·파기
> 이 문서는 **로컬(Docker) 기준으로 만든 절차와 도구**를 정리한다. 운영 서버·공급자는 아직 정해지지 않아(기술 기획서 §15), 운영에서는 공급자의 자동 백업·시점 복구를 켜고 이 도구는 별도 사본과 복구 시험에 쓴다.

## 1. 백업

| 항목      | 내용                                                                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 명령      | `pnpm backup create` (생성 후 보관 기간이 지난 백업 정리까지), `pnpm backup list`, `pnpm backup prune`                                                                 |
| 결과물    | `backups/<생성 시각>/` 아래 `db.dump`(PostgreSQL 사용자 지정 형식), `roles.sql`(DB 계정 정의, 비밀번호 제외), `manifest.json`(체크섬·크기·마이그레이션·테이블별 행 수) |
| 일관성    | 행 수 계산과 덤프가 같은 스냅샷(`pg_export_snapshot`)을 쓰므로 백업 중 쓰기가 있어도 어긋나지 않는다                                                                   |
| 보관 기간 | 기본 30일(`BACKUP_RETENTION_DAYS`). 가장 최근 백업은 기간이 지나도 남긴다. 형식이 다른 폴더는 건드리지 않는다                                                          |
| 실패 처리 | 도중에 실패하면 덜 만들어진 폴더를 지워 복구에 쓰이지 않게 한다                                                                                                        |
| 제외      | 업로드 파일(객체 저장소)은 1단계에서 파일 기능을 만들 때 버전 관리·복제를 함께 구성한다. 작업 큐(pg-boss) 상태는 덤프에 들어 있지만 복구 검증 대상은 아니다            |
| 저장 위치 | `backups/`(저장소에서 제외). 운영에서는 서버와 다른 위치(다른 디스크·리전)로 사본을 보내야 한다 (미구현, 공급자 확정 후)                                               |

환경 변수(모두 선택): `BACKUP_DIR`(기본 저장소 루트의 `backups`), `BACKUP_RETENTION_DAYS`(기본 30), `BACKUP_PG_MODE`(`docker` 기본, 서버에 PostgreSQL 클라이언트 도구가 있으면 `local`)

> 개인정보 영향: 해지한 회사의 데이터는 삭제·익명화 작업(P0-11) 뒤에도 **백업에는 보관 기간만큼 남는다**. 처리방침 제3조에 "백업본에는 최대 30일 남을 수 있음"을 적었으므로 보관 기간을 늘리면 처리방침도 함께 바꾼다.

## 2. 복구 시험

`pnpm backup drill [백업ID]` — 기본은 가장 최근 백업. **운영 DB를 건드리지 않고** 임시 DB(`<DB 이름>_drill_<시각>`)에 복구해 검증한 뒤 임시 DB를 지운다.

| 검사              | 확인하는 것                                                                     |
| ----------------- | ------------------------------------------------------------------------------- |
| 체크섬 일치       | 덤프가 손상·변조되지 않았는지                                                   |
| 행 수 일치        | 모든 테이블의 행 수가 백업 시점과 같은지                                        |
| 마이그레이션 일치 | 적용된 마이그레이션 수와 마지막 이름이 같은지                                   |
| 회사 격리(RLS)    | 회사 범위 테이블마다 RLS가 켜지고 강제되어 있는지                               |
| 앱 계정 격리 동작 | 앱 계정으로 접속해 회사를 지정하지 않으면 0행, 지정하면 그 회사의 행만 보이는지 |

- 결과는 `backups/drill-log.jsonl`에 한 줄씩 기록되고, 하나라도 실패하면 종료 코드가 0이 아니다 (알림에 연결 가능)
- 검사가 실제로 실패를 잡는지 확인했다: 덤프 1바이트를 바꾸면 체크섬 검사가, 기록된 행 수를 바꾸면 행 수 검사가 실패한다
- 정기 실행 예시는 `ops/crontab.example` (백업 매일, 해지 삭제 매일, 복구 시험 매주)

### 실제 복구 절차 (장애 시)

1. 새(또는 비운) PostgreSQL 서버에서 `roles.sql`을 적용해 DB 계정을 만든다
2. 데이터베이스를 만들고 `pg_restore --no-owner -d <DB> db.dump`로 복구한다
3. `pnpm db:setup`으로 계정 비밀번호를 환경 변수 값으로 다시 설정한다
4. `pnpm operator list`와 로그인으로 확인하고, 복구 시점 이후의 변경은 사라졌음을 사용자에게 안내한다

## 3. 복구 시험 기록

| 일시 (UTC)       | 백업               | 환경                      | 결과 | 소요  | 비고                                                                                                         |
| ---------------- | ------------------ | ------------------------- | ---- | ----- | ------------------------------------------------------------------------------------------------------------ |
| 2026-10-06 12:36 | `20261006T123652Z` | 로컬 Docker PostgreSQL 18 | 성공 | 0.3초 | 테이블 16개·마이그레이션 11개·덤프 약 106KB, 5개 검사 모두 통과. 실패 감지 확인(손상 덤프·행 수 불일치) 완료 |

- 이 기록은 **절차와 도구가 동작함**을 확인한 것이다. 데이터가 적은 로컬 기준이라 소요 시간은 운영의 복구 시간(RTO)을 뜻하지 않는다
- 운영 환경이 정해지면 그 환경에서 같은 절차로 한 번 더 시험하고 이 표에 추가한다 (공급자의 시점 복구 포함)

## 4. 환경 분리

| 항목             | 로컬                              | 스테이징 (선택)    | 운영                                        |
| ---------------- | --------------------------------- | ------------------ | ------------------------------------------- |
| `NODE_ENV`       | `development`                     | `production`       | `production`                                |
| 데이터베이스     | Docker PostgreSQL                 | 별도 인스턴스      | 별도 인스턴스(서울 리전, 자동 백업)         |
| 메일             | Mailpit(발송되지 않음)            | 실제 메일 서비스   | 실제 메일 서비스                            |
| 소셜 로그인      | 가짜 제공자(개발 환경에서만 동작) | 카카오 테스트 앱   | 카카오 운영 앱                              |
| 시드·더미 데이터 | 사용 (`pnpm db:seed`)             | 사용하지 않음      | 거부 (`NODE_ENV=production`이면 실행 거부)  |
| 비밀 값          | `pnpm env:init`이 무작위로 생성   | 환경별로 새로 생성 | 환경별로 새로 생성, 배포 환경의 비밀 저장소 |

- 환경마다 DB 비밀번호·`CODE_HASH_SECRET`·`OAUTH_COOKIE_SECRET`을 **다르게** 만든다 (같은 값을 쓰면 한 환경의 유출이 다른 환경으로 번진다)
- 운영 기동 검사(`apps/api/src/env.ts`): `NODE_ENV=production`이면 로컬 주소(DB·저장소·메일), `http` 주소, `debug` 로그, 메일 계정 누락, 로컬 기본 비밀번호가 있을 때 **기동을 중단**하고 어떤 변수가 문제인지 알려 준다 (값은 노출하지 않음)
- 위 표의 스테이징·운영 열은 계획이다. 공급자가 정해지면 값을 채운다
